# Единый рабочий цикл Koswork

Владелец утвердил следующий блок: одна цель, общий план, переходы между браузером,
выбранной папкой и приложениями, сохранение прогресса, остановка/продолжение и
проверка результата. База — PR #415, `bc64db3d136938b0a230e024f5ad5b1011877eee`.
Windows-кандидат 0.16.0, unsigned, updater OFF. VPS не менялся.

## Пользовательский путь

Меню Windows-клиента **Koswork → Рабочая задача…** открывает отдельное окно.
В разделе Work существующая кнопка получает название «Выполнить в Koswork», если
новый Windows bridge доступен: цель/проект передаются в то же нативное окно,
без автоматического запуска или выдачи разрешений. Старый клиент сохраняет свою
кнопку отдельного управления ПК; в обычном браузере нативная функция не имитируется.
Владелец выбирает проект, при необходимости подключает рабочую папку и вводит
одну цель. Агент составляет до восьми этапов с наблюдаемыми критериями результата.
В окне видны план, выполняемый этап, текущая среда и краткие отметки проверки.
Основной чат, его сайдбар и логотип не меняются. Это один агент, не Multi-Agent.

Планирование не даёт доступа к экрану или сайтам. Первый переход в браузер требует
своего нативного разрешения, первый переход к ПК — отдельного разрешения на снимки
основного монитора и управление приложениями. Разрешения относятся к одной цели
и текущему сеансу; они не отменяют подтверждений важных действий. Выбор папки
отдельный, общий для файловых инструментов и браузерных вложений этой задачи.
Доступ к обычному браузеру или старой консоли управления не становится разрешением
для новой задачи автоматически.

После разрешения агент может переходить между средами без повторного объяснения
цели. Снимки ПК не снимаются до отдельного разрешения. Браузер использует DOM-текст
и refs, компьютер — свой исполнитель с проверкой окна и физического ввода.
Предыдущие refs/координаты не переносятся через переключение. Файловые инструменты
работают только в выбранной папке; они текстовые. Настоящий DOCX создаётся через
доступное приложение с отдельно разрешённым управлением ПК, а не фиктивным
переименованием Markdown в .docx.

Задача завершается только после отметки каждого критерия на свежем наблюдении.
**Это проверка моделью, не принятие владельцем и не доказательство семантической
правильности.** Принятие результата остаётся отдельным действием в истории.
`requested=true` не равно успешному сохранению или отправке. Длинные материалы
агент может сохранить в рабочую папку; краткие факты/URL из отметок этапов доступны
следующим этапам в текущем сеансе. После восстановления материалы перечитываются.

## Прогресс и ограничения

- Общая задача ограничена 90 действиями и 30 минутами с сохранением существующего
  учёта расхода/бюджета API. Старые browser/computer-сеансы сохраняют 30 действий.
- Один локальный task gate не допускает одновременно других компьютерных или
  браузерных агентов. Аварийная горячая клавиша и остановка сохранены.
- `ask_user` останавливает наблюдения и вызовы модели до локального Resume.
- План, критерии и статусы сохраняются в существующем зашифрованном журнале по
  owner/origin с отдельным executionMode=work и каталогом work-tasks-v1, чтобы
  старый клиент не читал новые Work-записи как старые задачи ПК. Не добавляются снимки, DOM, результаты
  чтения/ввода файлов, текст отметок проверки, токены или разрешения на среды.
  Сама цель и короткие названия/критерии плана сохраняются после фильтра; это
  модельный текст, а не гарантия отсутствия любых частных сведений.
- При восстановлении нужны тот же владелец/origin/папка, новый сеанс и разрешения.
  Отметки этапов сбрасываются для повторной проверки; прежнее состояние видно
  модели как подсказка, но не как новое доказательство результата. Неопределённые
  записи/отправки не воспроизводятся автоматически. Возможные секреты в названиях
  плана не сохраняются как восстановимый план; это не универсальный DLP.
- API проверяет executionMode, наблюдаемую среду и наличие изображения для ПК.
  Обычный browser-сеанс не получает OS-команды, computer-сеанс — новые work-команды.
  Старый API без подтверждения нового режима не принимается клиентом как Work.

## Проверки и живая приёмка

Локальный интеграционный сценарий использует настоящий временный каталог и файл:
план → браузерный адаптер → создание/чтение файла → адаптер приложения → проверки
критериев → отдельное принятие. Браузер, приложение и планировщик этого сценария
контролируемые тестовые адаптеры. Есть проверки отказа/отмены разрешения, запрета
незаметного перехода из браузера к ПК, устаревших отметок, восстановления без
разрешений, паузы и общей блокировки исполнителей.

Headless Chromium проверяет реальный браузерный движок и отображение плана, включая
неинтерпретируемый HTML в заголовках. Windows CI дополнен единым циклом поверх
реального Electron-браузера и настоящего скачанного тестового файла. **Компьютерный
адаптер и модель в этом CI-сценарии тестовые, ОС и приложения владельца не управляются.**
Факт успеха CI подтверждается checks/артефактом PR, не наличием тестового кода.

Контрольная задача владельца — поиск информации, Word-отчёт с источниками и сохранение
на рабочем столе — остаётся живой приёмкой после восстановления VPS и допуска к
установленному клиенту. Word, Telegram и реальные файлы владельца в этом проходе
не открывались. Платные AI-запросы и выкладка на VPS не выполнялись. Новые аккаунты,
API-ключи и миграции не нужны; для живой работы требуется обновлённый API/клиент,
а для новой кнопки в Work — соответствующая версия web.
