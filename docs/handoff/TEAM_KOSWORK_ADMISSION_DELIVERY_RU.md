# Koswork: регистрация занятого слота до старта Work

Дата: 9 ноября 2026, Москва. Ветка: `developer/koswork-admission-reliability`.
Фактическая база main: `08f865f6362d3045438d6ca7f93be8e9e56e1e6c`.
Объём: проверка ограничений и lifecycle существующего исполнителя в рамках
[согласованного плана Ruflo](../product/RUFLO_ADOPTION_SCOPE_RU.md).

## Действующий путь и исправление

Пользователь создаёт Work через `POST /api/v1/projects/:projectId/work`.
Существующий store сохраняет queued-задачу; timer `ManagerWorkCoordinator.start()`
вызывает `execute()`, затем существующие plan/draft/review/publish и ledger.
Содержимое читается по прежнему owner-scoped download API. Нового исполнителя,
хранилища, API, маршрутов, миграций, capabilities и зависимостей нет.

Раньше `execute()` вызывал `run()` до добавления записи в `active`. Async-функция
может синхронно вызвать зависимость до первого await. Подключённый graph adapter
при первом `read()` мог повторно вызвать `execute()` другого проекта, пока слот
ещё считался свободным. SQL по-прежнему исключал второй running в одном проекте,
но два разных проекта проходили эту проверку: измеренный peak context reads = 2.

В том же окне `stop()` и `quiesceOwner()` не видели начавшуюся работу, поэтому
возвращали завершённое ожидание раньше неё. Теперь настоящий settlement promise
и AbortController помещаются в **существующий** `active` перед вызовом `run()`.
Повторный запуск видит занятый слот; lifecycle видит контроллер, отменяет работу и
ожидает её завершения. После settlement снимаются прежние timeout/active записи.
Обычный синхронный порядок claim/начала работы сохранён; отложенного второго
исполнителя нет. Лимит остаётся 1 Work на процесс, права/квоты/провайдер не менялись.

Общий исходник изменён отдельным интеграционным коммитом
`5a2e04863682eec031fd1f6e61b2fdc97d61e86f` — 9 добавленных строк и 1 заменённая.
Тестовые сценарии: `740fed7836b89dcdc0ab0a34ce189056f38652f1`.
Деревья публикуемых Git-объектов сверяются с локальными коммитами.

- `apps/api/test/fixtures/manager-admission.json`: синтетический бриф с `19 700 ₽`,
  `00123` и «кроме доставки».

  вызов чтения контекста и считает одновременно начавшиеся чтения. Его callback
  воспроизводит повторный вход/остановку, не создавая реальных модельных запросов.
- В существующем `manager-work.test.ts` добавлены три регрессии: повторный вход
  другого проекта, startup privacy drain и startup shutdown.
- Успешный сценарий обрабатывает два Work через настоящий Manager pipeline,
  записывает артефакты в временную SQLite, скачивает их через Fastify API и сверяет
  текст/версию/SHA256 с canonical artifact metadata.
- `fixtures/koswork-admission/result.json`: настоящий снимок этого успешного
  сценария. Peak = 1, четыре вызова **локального provider fixture**, два скачанных
  файла версии 1 с SHA256
  `38533a99faf701682c8ae981f545f0cec13e719ae5d10413fe661b95e87be0d6`.
  Реальный HY4/другая внешняя модель не вызывались. Файл создаётся с `wx`, без

## Команды и фактические результаты

Из корня репозитория с установленными frozen-lockfile зависимостями:

```sh
KOSWORK_ADMISSION_REPORT_DIR=/tmp/koswork-admission-new \
  pnpm --filter @cosmora/api exec vitest run test/manager-work.test.ts \
  -t 'Work admission startup'
pnpm --filter @cosmora/api lint
pnpm --filter @cosmora/api typecheck
pnpm check:core
```

Каталог отчёта выбирается отдельно от пользовательских данных; `result.json` в нём
должен отсутствовать. Без переменной окружения тест проверяет тот же путь, но не
пишет отдельный отчёт. Локальный Linux-стенд: Node v24.22.1, pnpm 11.25.0;
install scripts отключены. CI использует закреплённый workflow toolchain.

До исправления все три корректно подготовленные регрессии упали: peak 2 вместо 1,
преждевременно settled privacy drain, преждевременно завершённый shutdown.
В самой первой privacy-фикстуре отсутствовал обязательный global privacy fence;
это было ошибкой теста. Добавлена существующая lifecycle-запись quiescing до
`quiesceOwner`, затем повторный baseline подтвердил настоящий дефект. Проверки
истинного lifecycle и существующие глобальные fences не обходились.

После исправления: **3/3 PASS**, остальные 67 тестов файла в целевом запуске
пропущены фильтром и не называются прошедшими этим запуском. Первый общий gate
остановился на `no-unnecessary-type-assertion` в новой фикстуре. Вместо подавления
правила пары project/work сделаны tuples `as const`; лишние `!` удалены. Отдельные
API lint/typecheck после этого завершились с exit 0. Исходные неуспешные логи
сохранены, ошибки не выдаются за успешные проверки.

Итоговый повторный `pnpm check:core`: **PASS, exit 0**. API: 920 PASS,
в том числе все 70 Manager Work и 40 DAG; web: 263; contracts: 206; core: 386;
db: 160; model-gateway: 151; policy-engine: 43; config: 17. Tool-runtime:
63 PASS / 4 OCI skipped (локально они не исполнялись). Пройдены format, secrets,
lint/typecheck, все package tests, корневые deploy/connection/live-acceptance/secrets/
media guards, production builds, privacy и compatible-profile fixture smoke.
Сохранённый readback отдельно перепроверен по обоим UTF-8 телам, версиям и SHA256.
Внешние CI checks точного опубликованного head фиксируются в PR; живой модельной
приёмкой эти fixture/guard-проверки не являются.

Read-only merge-tree с Office/composer head

## Границы, интеграция и откат

Это исправление повторного входа, а не включение параллельных платных задач.
Предел process-local; распределённый глобальный semaphore не добавлялся. SQL CAS,
owner/project budgets и durable fences остаются действующими границами.
Graph adapter должен соблюдать прежний контракт/signal; исправление не обещает
принудительное завершение произвольного стороннего I/O после его таймаута.

Существующие клиенты и UI продолжают работать по тем же маршрутам. Для интеграции
нужен общий коммит coordinator и тесты/fixtures; точный финальный SHA и внешние
checks зафиксированы в PR. Native desktop/browser/installer, дизайн, тарифы и HY4
не менялись; установка на ПК владельца и production не выполнялись.

Откат production-логики: `git revert 5a2e04863682eec031fd1f6e61b2fdc97d61e86f`.
Это возвращает старое окно повторного входа, поэтому три регрессии снова должны
падать; для полного отката пакета затем убрать соответствующие tests/fixtures.
Схема данных не менялась, принятые Work и их артефакты удалять не требуется.
