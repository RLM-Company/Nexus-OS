# Kosmora: надёжность черновиков и вложений

Дата: 8 ноября 2026. Ветка: `developer/kosmora-composer-reliability`.
База отдельного checkout: `304d5170a7e7381b1885fb12201ba7df31e80dbc` (main, PR #471).
Объём согласован владельцем: сохранение черновика/вложений после закрытия вкладки,
изоляция чатов и исправление потери данных без изменения дизайна.
Office остаётся отдельной поставкой PR #466.

## Что было и что изменено

Существующий путь: textarea/вставка продолжения → `page.tsx` →
`composer-draft-storage.ts` → browser localStorage; в Windows используется
`desktop-draft-bridge` с отдельным уже существующим текстовым хранилищем.
Вложения декодирует существующий `useChatAttachments`; сервер принимает существующий
POST сообщения. Новых баз, API, прав доступа, зависимостей и миграций нет.

Ранее сохранение читало состояние последнего React render. Закрытие вкладки в том же
задании браузера после удаления файла возвращало старое вложение. При отклонении POST
восстанавливался обрезанный `.trim()` текст. Некоторые уведомления `input`, при которых
React value tracker уже видел значение, не попадали в `onChange`: прикрепление файла
сбрасывало такой текст. Поздние ACK и ошибки стирали продолжение, подготовленное пока
POST ожидал ответа; ACK также безусловно очищал более новую запись другой вкладки.

Теперь актуальный текст и набор вложений доступны синхронно до следующего render.
Обработчики `input`/`change` используют один путь с устранением повторной записи.
`pagehide` сохраняет актуальный снимок; неизменённая вкладка повторно не записывает
свой старый снимок поверх чужого. Изоляция по ключу чата/проекта и epoch сохранена;
запоздавшее чтение файла отменяется при смене области.

POST использует отдельный снимок отправленных данных. Ошибка сохраняет точный текст
с пробелами и переводами строк либо уже подготовленный более новый текст.
После ACK очистка возможна только для неизменённых канонических записей текста и
материалов. Продолжение, добавленное во время отправки, сохраняется. В Windows
pagehide/таймер используют актуальный текст; поступающий контекст ожидает окончания
отправки. IPC и формат Windows не изменены, вложения туда не сохраняются.

## Воспроизведение

После установки закреплённых зависимостей из lockfile:

```sh
pnpm --filter @cosmora/web typecheck
pnpm --filter @cosmora/web lint
pnpm --filter @cosmora/web test
KOSMORA_E2E_PRODUCTION=1 pnpm --filter @cosmora/web test:e2e:composer
node --test desktop/windows/test/draft-*.test.cjs
pnpm check:core
```

Для уже установленного отдельного Chromium в Linux добавьте
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium`. Стандартный Playwright browser
также поддерживается. Конфигурация сама поднимает изолированный API с временной SQLite
и `MODEL_PROVIDER=mock`, собирает и запускает production web. Порты 3000/3100 должны
быть свободны; существующий сервер не переиспользуется. Реальный HY4 не вызывается.

`input.json` содержит точные пробелы, перенос, `19 700`, `00123`, `кроме доставки` и
байты `brief.txt`. Тест прикрепляет файл через настоящий input, получает отказ POST,
перезагружает страницу и считывает localStorage/восстановленный интерфейс. В
`test-results/**/browser-draft-readback.json` сохраняются реальные записи, текст и
SHA-256. Копия проверенного результата приложена рядом с входом. Это сохранение
настоящего browser storage; отказ POST синтетический, модель не вызывается.

Исходный ранее нестабильный сценарий можно нагрузить отдельно:

```sh
DRAFT_STRESS_CPU=1 PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium \
  KOSMORA_E2E_PRODUCTION=1 pnpm --filter @cosmora/web exec playwright test \
  -c playwright.composer.config.ts --grep 'restores text and files after closing' \
  --repeat-each=24 --workers=2
```

## Фактические проверки

До исправления исходный нестабильный CI-сценарий локально прошёл 12 повторов и затем
24 повтора при CPU×6/двух workers. Точная причина старого падения CI этим не доказана.
Отдельные управляемые тесты выявили реальные ошибки: удаление + немедленный pagehide,
обрезание пробелов при отказе, tracked input + прикрепление файла, поздние ACK/ошибка
и запись из другой вкладки. Эти тесты падали до соответствующих исправлений.

Промежуточный прогон выявил ошибку самого теста: счётчик «нет отправки» учитывал
служебный POST импорта pins после reload. Проверен trace, счётчик ограничен
маршрутами отправки сообщений; дальнейший production-прогон дал 22/22 без retries.
После первых исправлений исходный сценарий отдельно прошёл 24/24 при CPU×6.
Первоначальная конфигурация E2E не проходила exactOptionalPropertyTypes для
`executablePath: undefined`; исправлена условная передача launchOptions.

Последний модульный прогон: 266 web-тестов + 10 Studio regression PASS; native
текстовый storage/session/isolation — 7/7 PASS. Typecheck (включая E2E), web lint,
формат изменённых файлов, secret scan и `git diff --check` прошли.
Production-набор после исправления поздних ответов: **25/25 PASS**, retries=0,
1 worker, 1,9 минуты, отдельный Chromium. Все 13 исходных chat-reliability сценариев
и 12 сценариев гонок прошли, включая сохранение в другой вкладке до ACK.
Приложенный readback дополнительно проверен по точному UTF-8 содержимому входа и
обоим SHA-256: PASS.

Общий `pnpm check:core` после синхронизации main: **PASS**, exit status 0.
Прошли format, secrets, lint, typecheck, тесты всех пакетов (в API — 917/917),
deploy/connection/live-acceptance-guards/secrets/media-acceptance guards,
production build, privacy E2E smoke и compatible-profile fixture smoke.
В tool-runtime штатно пропущены 4 OCI-теста; они не заявляются прошедшими.
Реальная live acceptance модели этими guard/fixture-тестами не подтверждается.
После переподключения среды handle исходной команды был недоступен;
её завершение и нулевой exit status проверены по завершённому shell-процессу,
весь исходный лог сохранён. Quality gate не перезапускался для скрытия результата.

## Границы и откат

Browser localStorage остаётся локальным незашифрованным хранилищем этой функции.
Квоты прежние: 20 черновиков, 4 000 000 символов записей, 128 000 символов текста,
срок материалов 30 дней. Недоступность/quota и повреждённые материалы обрабатываются
существующими уведомлениями. Снимок не обещает сохранение ещё не прочитанного файла
при завершении процесса; завершённое чтение и его отмена проверяются отдельно.

Сравнение записей защищает от уже сохранённой новой версии и повторной записи
неизменённой вкладки. Это не полноценная распределённая транзакция или слияние
одновременных правок: localStorage не предоставляет CAS между процессами, а активные
правки двух вкладок всё ещё подчиняются порядку записей. Live-синхронизация интерфейса
между вкладками в этот объём не входит.

Native bridge проверен фикстурой браузера и реальными Node-тестами backend storage.
Полный Windows GUI/DPAPI/закрытие процесса на отдельном стенде владельца не проверялись.
Реальная модель и production не использовались; stage-one live acceptance не заявляется.

Для отката отменить интеграционный коммит, затем коммит вспомогательных модулей и
тестов. Схема хранения не менялась: прежний клиент продолжит читать те же ключи.
Не удалять пользовательские записи при откате. Merge PR и deploy выполняет владелец.
