# Koswork: активное истечение разрешения

Ранее локальное разрешение на управление истекало через 30 минут, но проверялось
только между асинхронными операциями. Уже ожидающий запрос планировщику или
нативному исполнителю не получал AbortSignal в момент истечения.

Теперь после выдачи session grant ставится локальный таймер на оставшийся срок.
При истечении используется штатный `stop`: отзывается gate, прерывается signal,
предпринимаются отмена workspace и остановка нативного драйвера. Таймер очищается
при ручной остановке и любом завершении; старый таймер не переносится в новый
запуск. Максимальный срок и первичное согласование не изменены.

Это сигнал отмены, а не гарантия отката внешнего эффекта. Если действие уже
отправлено, журнал сохраняет `dispatching` и `requiresReview: true`. Поздний ответ
отклоняется существующей проверкой. Пока старый исполнитель не вернул управление,
локальный слот остаётся занят: новый запуск не пересекается с неопределённым старым.
После завершения прежнего вызова новый запуск возможен с новым подтверждением.

## Проверки

- До исправления регрессионный сценарий подтверждал, что signal не прерывается
  при истечении срока во время ожидания планировщика.
- Управляемые часы и 20-миллисекундный grant проверяют ту же выдачу/истечение,
  без реального ожидания 30 минут. После истечения выполняются обе очистки,
  отклоняется позднее действие и временно запрещается конкурирующий запуск.
- Отдельный сценарий с ожидающим нативным вводом проверяет AbortSignal,
  `cancelled`/`dispatching`, сохранение зашифрованной истории и review при recovery.
- Следующий запуск снова проходит подтверждение; grant и права не восстанавливаются
  из истории.
- `npm run check --prefix desktop/windows`: **307 tests, 306 passed, 0 failed,
  1 штатный Windows-only skip**. Prettier, проверка секретов и `git diff --check`.

Исполнитель и планировщик в fault-сценариях сценарные. Устройство владельца,
платные модели, серверная выкладка и дизайн не затронуты.
