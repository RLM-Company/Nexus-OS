# Сквозной сценарий Koscode

База `4fb73e33142fbb13180138cb3052c73aa17b6b23`, ветка
`team/koscode-live-workflow`. В базе уже есть восстановление выбранной задачи
из #609 и привязка публикации к хешу проверенного diff из #625.

## Что изменилось

- При потере ответа браузер перечитывает ту же задачу. Если сервер сохранил
  состояние «исход неизвестен», Koscode один раз вызывает сверку с GitHub
  для этой попытки. Сверка читает состояние созданной ветки и PR.
- Если GitHub подтвердил PR, открывается исходная ссылка и снимается
  устаревшее сообщение об ошибке. Если подтвердить результат пока нельзя,
  доступна кнопка повторной сверки. Исходный запрос публикации не повторяется.
- Регрессия проходит предложение модели, отказ проверки, разрешение на
  исправление, сохранение нового diff, обновление страницы, новую проверку
  и двойной клик после одобрения. Ответ публикации теряется. Интерфейс
  показывает одну подтверждённую ссылку. Отдельные сценарии проверяют
  переключение задач и потерю запроса до принятия сервером.

## Проверки на фикстурах

```sh
pnpm --filter @cosmora/api exec vitest run test/code-agent.test.ts test/code-agent-github-tree.test.ts test/github-integration.test.ts
pnpm --filter @cosmora/web exec playwright test --config playwright.code-agent.config.ts
CODE_AGENT_TEST_IMAGE="$(docker image inspect node:24-bookworm-slim --format '{{.Id}}')" \
CODE_AGENT_REPAIR_REPORT_DIR=/tmp/koscode-fixture-proof \
pnpm --filter @cosmora/api exec vitest run test/code-agent.test.ts -t 'real OCI API repair'
```

Браузерные сценарии используют фикстуру API. Сценарий OCI применяет точный diff
в новом локальном Git-репозитории, выполняет проверку через настоящий
изолированный раннер и сверяет один запрос создания Draft PR с фикстурой GitHub.
В этом сценарии модель также заменена фикстурой.

## Живой прогон

Нужны согласованные тестовый репозиторий, базовая ветка и стенд с доступной
моделью и изолированным исполнителем. На этом этапе внешние модельные запросы
и публикация в тестовом репозитории не выполнялись.

1. В `/code-agent` выбрать тестовый проект, проверить подключённый репозиторий
   и выбрать согласованную ветку. Зафиксировать исходный SHA. Дать небольшое
   задание по одному тестовому файлу с проверяемым результатом.
2. Запустить модель через «Предложить исправление», сохранить выбранный diff
   и запустить разрешённую проверку. Зафиксировать команду, вывод и код выхода.
   При отказе отдельно разрешить попытку исправления и выполнить свежую
   проверку после сохранения нового diff.
3. Обновить страницу и убедиться, что открылась та же задача. Записать URL и хеш
   актуального проверенного предложения. Явно подтвердить один Draft PR.
4. При симуляции потери ответа обрывать ответ только после приёма сервером.
   Дождаться сверки и сравнить ссылку из Koscode с результатом чтения GitHub.
   Проверить статус черновика, базовую и исходящую ветки, точный diff и число
   PR. Команды чтения после получения номера и имени исходящей ветки:

```sh
gh pr view "$TEST_PR" --repo "$TEST_REPO" --json url,isDraft,headRefName,baseRefName,headRefOid
gh pr diff "$TEST_PR" --repo "$TEST_REPO"
gh pr list --repo "$TEST_REPO" --head "$TEST_HEAD" --state all --json number,url,isDraft
```

Сохранить только обезличенные результаты без токенов и личных
данных. Схема БД и зависимости прежние. Откат через revert коммита.
