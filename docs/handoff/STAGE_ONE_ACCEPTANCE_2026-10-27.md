# Приёмка первой версии Kosmora — 27 октября 2026

Первый этап закрепляет существующие возможности и их совместную работу. Дизайн,
обучение/персонализация и дальнейшее расширение относятся к следующему этапу.
Визуал, сайдбар, чат и логотип в этом изменении не редактируются.

## Закрытый разрыв запуска проекта

Пустой проект по-прежнему создаётся как `DRAFT`, без запроса модели. Первое принятое
сообщение или первая принятая задача Work переводят его в `ACTIVE` в той же
транзакции, что и создание задания. Раньше фоновый Manager не выбирал сообщение
такого проекта, а Work отклонялся с `PROJECT_INACTIVE`.

При ошибке вставки/снимка транзакция возвращает проект в исходное состояние.
Чужие, архивные, завершившиеся с ошибкой, отменённые и ограждённые privacy-fence
проекты Work не активирует. Повтор запроса сохраняет прежнее задание и его контекст.
Статусы `ARCHIVED`/`FAILED` не переводятся в `ACTIVE` этим исправлением.

При создании пустого проекта API подготавливает обычные настройки политики и учёта.
У старой задачи без политики исполнитель до первого запроса создаёт стандартный
профиль A0. Существующая политика владельца сохраняется. Подтверждение плана и
публикации файлов не обходится.

## Воспроизводимая локальная приёмка

`pnpm test:release:api` запускает ограниченный двумя процессами набор критичных API.
В него входят чат проекта, Work/планы, таблицы/контекст/знания, авторизация, изображения
в чате и Code. Это локальные проверки; они не заменяют приёмку на рабочем сервере.

Новый `stage-one-workflow.test.ts` проверяет один связный сценарий:

1. Создать пустой проект через API с настоящей bearer-сессией.
2. Сохранить таблицу, проиндексировать тестовый документ, найти точную цитату.
3. Подготовить сводку таблицы и цитату, явно сохранить их в материалах.
4. Принять сообщение и Work, затем изменить таблицу, удалить документ и материалы.
5. Закрыть API/SQLite и открыть тот же файл базы заново.
6. Проверить доступность задания фоновому исполнителю и неизменность принятых снимков.
7. Выполнить чат и Work через настоящие API/координаторы с синтетическим провайдером.
8. Подтвердить план и явно задать тестовую политику публикации; скачать результат.
9. После второго открытия проверить результат, учёт без повторного списания и SQLite integrity.

Синтетический провайдер позволяет проверить передачу контекста и жизненный цикл,
но не доказывает качество ответа внешней модели. Рабочие данные, ключи и платный
провайдер в сценарии не используются.
