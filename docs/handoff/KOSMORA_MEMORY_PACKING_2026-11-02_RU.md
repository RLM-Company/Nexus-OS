# Подготовка контекста: производительность и точный размер

Изменён действующий код `packages/core/src/context-memory.ts` и
`packages/core/src/conversation-window.ts`. Новый параллельный packer не добавлен.
Внешний вид, модель, DB-схема и правила доступа/выбора источников не менялись.

## Что исправлено

`fitContextMemory` раньше на каждом кандидате копировала весь выбранный массив,
четырежды сериализовала растущий bundle и кодировала его UTF-8. Теперь сериализация
каждой записи выполняется один раз, длина выбранного массива накапливается числом,
а стабильное разделение обязательных/обычных записей заменяет сортировку.

Размер вычисляется без маркеров и зависимости от порядка свойств:

1. Сериализовать заголовок с `items: []`, `omitted: 0`, `bytes: 0`.
2. Вычесть четыре байта заменяемых значений: `[]`, `0`, `0`.
3. Прибавить длину настоящего массива: скобки, сериализованные записи, запятые;
   затем число десятичных разрядов настоящего `omitted`.
4. Найти неподвижную точку `bytes = fixed + digits(bytes)`. Число разрядов
   ограничено безопасными целыми JS. Небезопасные счётчики отвергаются.

Экранирование, Unicode, emoji и непарные суррогаты учитывает настоящий JSON serializer
и TextEncoder. Размер поля `bytes` включён в сам размер. Результат проверен повторной
полной сериализацией в независимых тестах. Подбор линейный по общему объёму входного
текста/числу записей; пользовательское содержимое не кэшируется между запросами.
`mergeContextMemory` сохраняет прежнюю дедупликацию и provenance.

Отрицательный остаток после резервирования рамки памяти остаётся поддержанным:
обычная память не включается, обязательная вызывает прежнюю явную ошибку.
Последнее сообщение и его файлы не обрезаются.

В `conversationWindow` выбранные группы собираются в обратном порядке и один раз
разворачиваются. Старые группы после первого непоместившегося хода не кодируются.
Группы user/assistant/tool остаются целыми. Закрыт реальный пропуск проверки:
слишком большой обязательный prefix при пустой conversation теперь вызывает
ContextTooLargeError вместо возврата контекста сверх бюджета.

Проверка показала, что действующее русское предупреждение уже помещается в старый
резерв 256 байт. Утверждение о существующем переполнении именно предупреждением
не подтвердилось. Его стоимость не вычитается второй раз; добавлена проверка
итогового размера на случай будущего увеличения текста.

## Измерения

Синтетические одинаковые данные, медиана трёх измерений, Node 26.13.0 на ноутбуке.
Перед отчётом результаты нового/старого алгоритмов сравниваются deep equality.
Это подготовка контекста, не скорость модели, сети или всей переписки.

| Операция      |            Объём | Было, мс | Стало, мс |
| ------------- | ---------------: | -------: | --------: |
| Подбор памяти |      100 записей |   16,538 |     0,287 |
| Подбор памяти |      500 записей |  448,840 |     1,028 |
| Окно истории  |  2 000 сообщений |    2,275 |     1,528 |
| Окно истории  | 10 000 сообщений |   13,416 |     5,012 |

Данные оператора: `2026-11-02/koswork-memory-performance/benchmark-final.json`.
Числа зависят от входа и нагрузки компьютера; порог скорости в CI не закреплён.

Повторить на checkout с Node 24+:

```sh
pnpm --filter @cosmora/core build
node scripts/bench-context-memory.mjs --sizes=100,500
```

Benchmark использует тестовый baseline старых функций из f106571e. Он не подключён
к production-экспортам. Вызовов модели/сети и чтения пользовательской БД в нём нет.

## Проверки и активация

- 29 тестов ядра: исходные сценарии, точные границы, порядок свойств, строки-маркеры,
  frozen-входы, переполнение счётчиков, негативный остаток, источники и ограничения.
- Детерминированное сравнение со старым алгоритмом: 360 вариантов памяти и
  200 вариантов истории. Отдельно проверен линейный объём UTF-8-кодирования.
- 17 API и 23 DB-теста памяти/маршрута/учёта; типы, сборка core, lint, форматирование,
  secret scan и diff checks.

Обновлён только локальный API Kosmora после проверки нулевого числа активных
запросов/Work. Health, web-прокси, маршрут Fable и сохранённая история проверены
после перезапуска. Новых платных модельных запросов для этих проверок не было.
VPS не обновлялся; его HTTPS и приёмка остаются отдельной работой.

Кандидат Koswork не был применён: первый получил Critic FAIL и имел дополнительные
дефекты кода; второй прервался на ошибке провайдера. Финальную реализацию исправил
и проверил основной исполнитель. Нельзя выдавать этот блок за автономную успешную
разработку модели или скрывать оставшуюся нестабильность провайдера.
