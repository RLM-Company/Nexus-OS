приёмки текстовый файл; личные документы не использовались.

Тайминги Work накопительные и включают подтверждения, выполненные скриптом в
рамках заранее разрешённой приёмки. Ожидание ручного решения пользователя может
быть значительно дольше. Это один короткий сценарий, не нагрузочный тест и не SLA.

Использовались `cheapvibecode` / `gpt-6.1-sol`; повторное чтение сохранённых SSE
обоих чатов подтвердило внешний provider/model, правильный run_id и завершение.
В каждом сохранённом потоке один кадр с текстом. Время до первого токена в этом
прогоне не измерено достоверно; низкую задержку потоковой выдачи не заявляем.

Баланс провайдера изменился с 30 845 319 до 30 843 282 его внутренних единиц.
Это не денежная цена и не тот же счётчик, что сумма input/output токенов.
У всех пяти записей `currency` и `calculated_cost_amount` равны null. Пять
соответствующих резервов остались uncertain согласно существующей консервативной
политике учёта; ручного удаления или фиктивной нулевой стоимости не было.
Для финансовой приёмки остаётся подключить подтверждённые тарифы/сверку. В
рублях стоимость этого испытания неизвестна.

## Воспроизводимость и поправки инструмента приёмки

`scripts/live-ai-work-acceptance.mjs` принимает только loopback HTTP API, сессию
через окружение и новый абсолютный каталог отчёта. Запуск требует явного значения
`COSMORA_LIVE_ACCEPTANCE=RUN_FIVE_BOUNDED_MODEL_REQUESTS`. Без него генерация не
начинается. `COSMORA_OWNER_SESSION_TOKEN` должен поступать из существующего
закрытого файла окружения владельца, а не из команды или репозитория.

Скрипт ограничивает Work тремя стадиями, требует одну попытку маршрута и чатовый
output cap не выше 2 000. Повторный запуск с тем же каталогом блокируется до
сетевого вызова. Новое имя каталога означает новый оплачиваемый сценарий;
создавать его автоматически для обхода отказа нельзя.

Первый запуск инструмента ошибочно ожидал HTTP 202 при создании чата, хотя API
правильно вернул 201 и выполнил запрос. Этот запрос найден по сохранённому
синтетическому сообщению и принят через ручной режим восстановления
`COSMORA_ACCEPTANCE_ADOPT_CHAT`; вторая генерация первого ответа не запускалась.
Идентификатор первого client_message_id первоначального запроса:
`b1db5a1a-e5e9-449e-9ce6-17fd99d66039`. При восстановлении окончательный скрипт
оставляет это поле null, вместо нового неиспользованного случайного ID.

Также исправлено чтение вложенного SSE-конверта `{ type, data }` и проверка
принадлежности run_id/provider. Исправленный разбор проверен на сохранённых
потоках через GET, без новых обращений к модели. Это исправления инструмента,
не рабочего приложения. В первоначальном отчёте `first_delta_ms=null`; время
чтения сохранённого потока не считается задержкой первого ответа.

Семь локальных Node-проверок admission/replay/SSE не вызывают внешнюю модель и
включены в `pnpm check:core` через `pnpm test:live-acceptance-guards`.
