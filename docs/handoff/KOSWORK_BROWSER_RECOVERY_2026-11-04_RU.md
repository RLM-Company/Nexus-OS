# Koswork: восстановление после потери элемента браузера

## Назначение и согласованный объём

Продолжение разрешённого владельцем плана Ruflo/Gemini для Kosmora/Koswork.
После перерисовки страницы прежний DOM-ref может исчезнуть. Раньше агент получал
только BROWSER_ELEMENT_UNAVAILABLE и новое наблюдение. Теперь новое наблюдение
содержит причину отказа и ограниченный набор свежих кандидатов для перепланирования.
Изменений UI, новых разрешений устройства и новых платных маршрутов нет.

## Использованная основа

Проверен закреплённый Ruflo 3.71.0 / commit
5f3dacc54b7279e39b172d6027d7989791448e2e,
[causal-recovery-service.ts](https://github.com/ruvnet/ruflo/blob/5f3dacc54b7279e39b172d6027d7989791448e2e/v3/@claude-flow/browser/src/application/causal-recovery-service.ts).
Полезны объяснение поломки и аннотирование свежего snapshot. Наш браузер уже
использует изолированный CDP, opaque refs, контроль поколения и отдельный native
approval; эта база сохраняется. Второй browser service/selector engine не добавлен.
Код upstream не копировался, новых зависимостей нет. Вместо межсессионного selector
store и risk scores используется одна краткоживущая запись конкретного отказа.

## Поведение

1. Отсутствующий, перекрытый или изменённый элемент отклоняется до ввода.
2. Только подтверждённый локальный отказ до ввода может создать recovery record.
   Любая ошибка после начала input остаётся BROWSER_INPUT_UNCERTAIN и останавливает
   текущий сценарий; повтор/retarget не запускается.
3. Следующий штатный observe добавляет recovery в description. Запись одноразовая,
   допускается до 30 секунд, только на той же вкладке, URL и поколении документа.
   После навигации, переключения, отмены и смены контекста старые кандидаты не выходят.
4. Для исчезнувшего элемента выбираются максимум 3 ref с точным прежним signature
   и тем же scope. Signature учитывает тип/роль/имя, id/name, адрес ссылки, действия
   формы, методы/target и контекст фреймов; координаты и догадки по похожим словам
   не используются. Совпадение атрибутов не доказывает прежнее назначение/effect.
5. Дубли не превращаются в автоматически выбранный target. more_candidates и
   partial_snapshot обозначают неполный обзор. Изменённые/перекрытые цели получают
   объяснение без предложения повторить ввод.
6. Кандидаты вычисляются по окончательному, ограниченному snapshot. После обрезки
   description не содержит ref, которого больше нет в текущем nodes. Обрезка теперь
   явно устанавливает truncated; прежний предел description 14500 UTF-16 сохранён.
7. Агент должен явно выбрать новое действие по свежим данным. Обычная проверка
   актуальности, подтверждение владельца и отдельное серверное authorize остаются.
   Никакой автоматической отправки формы или повторного клика нет.

Запись живёт только внутри owner/server-scoped engine. Текст ввода, содержимое
файла и новые screenshots не сохраняются; secret targets не аннотируются.
Кандидаты не включают raw signature, исходный URL или внутренний filesystem path.
Диагностика не добавляет CDP/network/model вызовов: она использует существующее
следующее наблюдение и прежний цикл перепланирования. Это не обещание отсутствия
любого CPU/размера сообщения и не гарантия очистки native RAM.

## Приёмка

- Unit: точные атрибуты, другой frame/URL/generation, TTL и обратный ход часов,
  дубли, ограничения количества, чувствительные поля, отсутствие введённого текста.
- Реальный session loop: отказ до input, новое наблюдение, новый ref, повторная
  native confirmation и server authorization, один insertText и завершение.
- Отдельно: ошибка после input не становится not_executed; отмена очищает hint;
  trimming не выдаёт недоступные ref и показывает partial_snapshot.
- Настоящий headless Chromium/CDP: замена кнопки внутри Shadow DOM отвергает старый
  ref без клика, выдаёт текущий ref, затем выполняет явно выбранный клик ровно раз.
  Продолжают проверяться вложенные frames, focus theft, form action mutation,
  occlusion/transform fences, реальные байты ввода и одна отправка формы.

Planner в сценариях — fixture, не живая платная модель. Эти проверки не являются
Windows-приёмкой ноутбука владельца или измерением качества произвольных сайтов.

Локальная проверка: 246 desktop tests, 61 computer-control API tests, API typecheck
и lint, root format/secrets, unsigned packaging policy и реальный Chromium/CDP
прошли. Общая сборка/приёмка CI проверяется на том же commit в PR.

## Совместимость и выпуск

Клиент 0.18.0 включает browser/recovery.cjs в NSIS inputs и проверку упаковки.
Новый инструмент, endpoint и capability не нужны: report находится в существующей
строке observation.description. API-инструкция объясняет границы этих подсказок;
старые API сохраняют прежние правила fresh refs/confirmation. Старый клиент просто
не возвращает report. Без установки нового клиента функция на ПК не появляется.

Установка на основной ноутбук и изменение веб-интерфейса не выполняются этим пакетом.
VPS с предыдущим индексом памяти этим пакетом не перезапускается. Фактическая
приёмка и ссылки на CI фиксируются отдельно после успешной проверки ветки.
