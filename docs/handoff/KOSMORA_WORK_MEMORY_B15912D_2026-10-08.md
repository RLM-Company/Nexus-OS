## Что работает

- Существующий `ManagerWorkCoordinator` сохранён. Он исполняет зависимые этапы: план → создание файлов → Критик (по риску) → сохранение. План, задачи, зависимости и состояния сохраняются в `manager_work.state_json`; coordinator проверяет зависимости перед исполнением каждого этапа. Это ограниченный рабочий DAG из четырёх этапов, а не произвольный автономный исполнитель.
- SQLite compare-and-swap позволяет забрать только queued-задачу актуальной версии; одновременно выполняется максимум одна задача проекта. Очередь хранится на сервере. Другие проекты могут исполняться независимо, существующий глобальный предел — две задачи.
- Каждый переход состояния и запись checkpoint фиксируются одной транзакцией. Pause происходит после текущего модельного запроса, resume использует уже сохранённый план/черновик, cancel отменяет активный запрос. Закрытие вкладки не владеет исполнением.
- После перезапуска безопасный running-checkpoint переводится в paused и продолжает со следующего этапа после явного resume. Неопределённый provider/tool operation останавливается с `RECOVERY_REQUIRED`. Он не повторяется и не объявляется успешным. Новые полномочия из checkpoint не восстанавливаются.
- CRUD проектной памяти: источник, версия, поиск (Unicode/NFKC), pin/unpin, forget. Owner/project проверяются в каждом запросе. Ограничения: 200 активных записей проекта, 4000 символов содержания, снимок максимум 12 записей / 8000 символов сериализованных записей. Нет тихого усечения записи; количество исключённых записей видно в Work.
- Память принимает только явные действия владельца, без автоматической записи моделью. Снимок делается при принятии задачи, поэтому редактирование записи влияет на новые задачи. Forget удаляет текст из активной памяти и исключает запись из всех последующих dispatch существующих задач. Уже отправленный запрос отозвать нельзя. Принятые исторические снимки и файлы сохраняются; это не обещание удаления истории проекта.
- Источник `artifact` проверяется по ID опубликованного артефакта текущего проекта. `owner` и `reference` — ссылки, заявленные владельцем; их достоверность не выдается за результат внешней проверки. URL не загружаются.
- Неизменяемые версии файлов привязаны к проекту, имени и Work; сохранены UTF-8 размер, SHA-256, происхождение (work ID), признак публикации. Неуспешные черновики видны как черновики и не скачиваются через version-download. Результаты разных задач не перезаписывают друг друга.
- Для complex-плана Критик обязателен даже при `needs_critic=false` модели. FAIL запрещает публикацию. Пустые/дублированные/опасные имена отклоняются, JSON дополнительно проходит синтаксическую проверку. Критик оценивает содержание, не делает вид, что запускал код.
- Сохранение файлов использует прежний GuardedToolRuntime / Policy Engine: A0–A2, подтверждения, profile version, текущие permissions и emergency stop не обходятся. Нет нового shell, произвольной сети, внешней публикации, отправки сообщений или расходов.
- При первом `route.failed` Work закрывает iterator Gateway до retry loop. Даже Gateway с пятью attempts делает для этого Work только один запрос. Fallback отключён. Все token reservations сохраняются консервативно; неизвестные расходы не объявляются нулевыми.
- Если обязательные draft + Critic не помещаются в max_model_requests, остановка происходит после плана, до draft. Общие проектные лимиты Usage Ledger продолжают действовать.
- Панель внутри существующего Work (`/?project=<id>&view=plan`): задачи, зависимости, прогресс, ожидающее решение, состояние, checkpoint, версии результата и память. Можно поставить несколько задач в очередь. Русский текст, чёрный/белый/серый, без изменений глобальной навигации.

## Опциональный граф интеллекта

`WorkIntelligenceGraphAdapter` (контракт `kosmora-work-v1`) можно передать как `graph` в существующий конструктор `ManagerWorkCoordinator`. По умолчанию он отсутствует: дополнительных вызовов и сетевого подключения нет.

`read` получает owner/project, максимум 500 символов запроса, limit=12 и AbortSignal. При включении adapter вызывается перед каждым модельным этапом, результат ограничивается 8000 символами, проверяется project scope и версия контракта. Внешний adapter должен обеспечивать owner-bound чтение; это явная обязанность реализации другой ветки. Здесь нет реализации графа, его обучения, записи или подключения к произвольному endpoint.

Результат хранится как проектный контекст-данные. Он не содержит и не восстанавливает grants, роли или полномочия. Неправильный scope, ошибка или превышение 1 секунды прекращают Work до следующего модельного запроса с `GRAPH_UNAVAILABLE`. Нет автоматического повтора или подстановки успешного контекста.

## API

Общая авторизация прежнего API обязательна. Новые маршруты подключаются через существующий `registerManagerWorkRoutes`, поэтому изменений `app.ts` / `server.ts` не требуется.

| Метод     | Маршрут относительно `/api/v1/projects/:projectId` | Результат                                                                    |
| --------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| GET       | `/memory?q=...`                                    | Поиск текущих записей                                                        |
| POST      | `/memory`                                          | Создать запись                                                               |
| GET / PUT | `/memory/:id`                                      | Прочитать / обновить с version                                               |
| POST      | `/memory/:id/control`                              | pin / unpin / forget с version                                               |
| GET       | `/work/:id/runtime`                                | Задачи, checkpoint, версии, размер снимка памяти                             |
| GET       | `/work-artifacts`                                  | Метаданные последних 100 версий                                              |
| GET       | `/work-artifacts/:id/download`                     | Только опубликованный completed-результат, attachment + text/plain + nosniff |

Существующие `/work`, `/work/:id/control`, `/work/:id/files/:name` сохраняются. Новые записи памяти и controls не вызывают модель.

## Интеграция

Пакет содержит реальные изменённые/новые файлы под `files/` и два непересекающихся unified diff:

1. `kosmora-work-memory-b15912d-main.patch` — собственные модули, изменения существующего Manager, контракты, панель и проверки.
2. `kosmora-work-memory-b15912d-integration.patch` — только четыре barrel exports, новая SQL-миграция и одна запись migration journal.

В отдельном checkout сначала проверьте базу и оба патча, затем примените их. Команды из корня репозитория, где файлы патчей находятся в текущем каталоге:

```bash
git apply --check kosmora-work-memory-b15912d-integration.patch
git apply --check kosmora-work-memory-b15912d-main.patch
git apply kosmora-work-memory-b15912d-integration.patch
git apply kosmora-work-memory-b15912d-main.patch
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm format:check
pnpm check:secrets
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:profile
pnpm --filter @cosmora/web exec playwright test e2e/work-manager.spec.ts e2e/manager-work.spec.ts e2e/manager-work-stops.spec.ts --workers=1
```

Проверка `git apply --check` не меняет файлов. Эти патчи рассчитаны на указанную базу; новые изменения основной ветки требуют обычного ручного разрешения конфликтов. Общие package.json / lockfile / schema.ts / app.ts / navigation не изменялись. Нет новых зависимостей.

Миграция `0025_work_runtime.sql` создаёт только `project_memory`, `work_checkpoints`, `work_artifact_versions` и их индексы. Если другая ветка заняла номер 0025, интегратор переименовывает SQL и корректирует только её tag/idx/when в журнале по актуальному порядку, не переписывая уже применённые миграции. Применять миграцию необходимо **до** запуска обновлённого API.

Исторические completed-Work сохраняют прежние скачивания. Новые версии/checkpoint создаются для новых Work и последующих сохранений; старые завершённые файлы автоматически не пересчитываются и не получают выдуманную provenance.

## Проверки и границы приёмки

Точный список выполненных проверок приложен в `VALIDATION.md` пакета. Проверки используют настоящий coordinator, SQLite, Policy Engine и Gateway с локальным детерминированным провайдером. Они не подтверждают качество ответа или стоимость живой модели.

Браузерный новый сценарий сохранён в `apps/web/e2e/work-manager.spec.ts`. В этой среде Chromium отсутствовал, его установщик не дал пригодный ZIP; выбранные browser tests не смогли запустить браузер. Сценарии остаются **UNVERIFIED**, визуальная приёмка не заявляется. Production web build не заменяет проверку браузера.

Другие ограничения:

- Один API execution process. CAS проверен через две SQLite connections, но автоматическая recovery при старте не рассчитана на параллельные production replicas; lease/distributed scheduler не реализован.
- Произвольные пользовательские DAG, отдельный worker на каждый подпункт, длительные внешние инструменты и Code-agent интеграция — расширения, а не реализация этого базового file-work цикла. Разделы памяти/артефактов и adapter сохраняют точки расширения.
- Критик не security perimeter. Он выдаёт краткий verdict/reason, без скрытой chain-of-thought; не выполняет код и не доказывает факты из внешних источников.
- Неопределённые операции после restart требуют reconciliation. Нет опасной кнопки «повторить платный запрос», продолжить их автоматически нельзя.
- Проверка живого оплачиваемого Manager, графа другой ветки, VPS, GitHub merge/PR и Windows lifecycle здесь не выполнялась. Главный чат интегрирует и выкатывает изменения.
