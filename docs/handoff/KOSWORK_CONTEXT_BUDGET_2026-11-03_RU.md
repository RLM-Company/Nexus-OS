# Koswork: общий бюджет рабочего запроса

3 ноября 2026, Europe/Moscow. Продолжение согласованного блока экономии контекста
и подбора источников; база `80c45e231ce4fe9594e46773f06e158fc412ef2c` (PR #430).

## Исправленная проблема

Manager Work и локальный исполнитель сначала получали базовый запрос ManagerService,
затем заменяли его сообщения данными своего этапа. При этом память подгонялась под
собственный лимит, без общего остатка после материалов, навыков, проектной памяти,
плана, черновика и наблюдения. Финальные проверки маршрута и бюджета оставались,
но необязательные воспоминания могли зря блокировать выполнимую задачу, а большой
черновик критика не проходил единый предварительный контроль окна менеджера.

## Поведение

- `fitContextMessages` учитывает всю сериализованную оболочку, условные правила
  памяти, служебную оценку сообщений и резерв изображений. Используется та же
  консервативная оценка входа, что в существующем сборщике; это не точная
  токенизация провайдера и не оценка цены.
- Goal, принятые материалы/Skills, проектный снимок, план и полный черновик
  не обрезаются. Сначала проверяется обязательная часть без recalled-memory.
- Только факультативные воспоминания уступают место обязательным данным.
  Закреплённые записи и ограничения должны поместиться целиком либо запрос
  этого этапа останавливается до gateway dispatch.
- Manager Work учитывает одновременно окно настроенной модели и остаток
  принятого суммарного входного бюджета задачи. Проверки владельца, маршрута
  и фактического расхода после преобразований сохраняются.
- Локальный Work учитывает наблюдение, историю и резерв фотографии до создания
  строки запуска. Ошибка упаковки не оставляет новый незавершённый run.
- Квитанция памяти формируется по фактически переданному пакету. Если вся
  необязательная память снята, квитанция честно содержит `representation=none`
  и пустой список источников; два успешных этапа остаются двумя квитанциями.
- Снимки Skills и проектной памяти читаются один раз на сборку запроса.
- В журнале Work есть понятные сообщения для нехватки полного контекста или
  обязательной памяти. Сохраняются машинные коды `WORK_CONTEXT_TOO_LARGE`,
  `WORK_MEMORY_CONTEXT_INCOMPLETE`; суммарный бюджет задачи по-прежнему имеет
  `EXECUTION_BUDGET_EXCEEDED`. В native API — `COMPUTER_CONTEXT_TOO_LARGE`.

Нового ограничения 32К нет: allowance берётся из настроенной модели с прежним
резервом под ответ и служебные данные. Проверка с окном 1 000 000 и выходом
100 000 допускает 895 904 единицы консервативного входа; запрос с материалами
больше 100К проходит. Резерв модели не заменяет финальную проверку выбранного
маршрута. Если окно не задано, сохраняется прежнее legacy-поведение ManagerService.

## Проверка

- **50 core-тестов**: общий пакет, память, compaction, история и ManagerService.
- **126 API-тестов**: Manager Work, native Work, контекст и учёт Relay.
- Новые случаи проверяют точную границу JSON с кавычками/Unicode, изображения,
  сохранение замороженных данных, неверный renderer, большой контекст и ошибки.
- Реальные SQLite/API-фикстуры подтверждают: задача с бюджетом 3000 завершается
  за два scripted-вызова без факультативной памяти; обязательное не теряется;
  слишком большие материалы не вызывают адаптер и не списывают квоту; большой
  полный черновик сохраняется при отказе перед вызовом критика; фото учитывается
  до вставки native run. Это проверки с контролируемым провайдером, не live AI.
- Сборка API со всеми зависимостями, typecheck core/API, ESLint изменённых файлов,
  Prettier и secret scan.

## Границы выпуска

Чат, сайдбар, логотип, CSS, новые пользовательские настройки и разрешения не менялись.
Миграций, новых зависимостей и платных модельных тестов этого блока нет. Приложение
на ноутбуке и VPS не перезапускались. Серверная и Windows-приёмка первого этапа
остаются отдельными отложенными работами.

Fable-пакет не подменяет эту реализацию: его кандидаты ещё требуют отдельного
ревью. В частности, нельзя принять замену тестового файла, удаляющую прежние
регрессии. Полный CI базы #430 проверен и успешно завершён; CI новой ветки
проверяется отдельно после публикации.
