- **Ветка:** `deepseek/kosmora-limit-feedback`
- **База:** `9a7ffec` (актуальный `origin/main` на момент начала)

- **Решение владельца:** период обновления лимита **не вводить**; реализовать

## Что было

K07 (поиск, правка, повтор, ветвление, экспорт) и K08 (управляемая память,
PR #464) уже реализованы. В K09 в личных настройках были «Всего учтено»,
«Персональный лимит» с progress и детализация по запросам, но при отказе
прогона `USAGE_LIMIT_EXCEEDED` пользователь видел только
«Лимит токенов достигнут. Измените квоту в персональных настройках.» — без
фактических чисел и без указания, где смотреть разбивку. «Осталось» и время
обновления отсутствовали; период лимита владельцем ранее определён не был.

Важный факт, установленный тестом: `accountStore.reserve()` вызывается
**внутри** цикла `for await` после события `route.selected`, поэтому
провайдер может уже получить запрос до отказа. Любая формулировка «запрос не
отправлен» была бы неверной — в UI используется «прогон остановлен».

## Что работает теперь

1. **Понятный отказ.** При `USAGE_LIMIT_EXCEEDED` в обычном чате показывается
   сообщение с реальными числами из уже существующего
   `GET /api/v1/personal-settings/usage`:
   - «Учтено X из Y токенов» (или «Учтено X токенов», если предел не задан);
   - «Разбивка по запросам — в личных настройках, раздел «Использование»»;
   - «Период обновления лимита не задан» — честная формулировка вместо
     выдуманной даты;
   - «текст сохранён в поле ввода».
     Если `usage` недоступен, остаётся короткий честный fallback без чисел.
2. **Остаток в настройках.** В `UsageMetrics` рядом с progress добавлено
   «Осталось N токенов · период обновления не задан». Показывается только при
   заданном `max_total_tokens`, считается как
   `max(0, max_total_tokens - total_counted_tokens)`, не противоречит
   накопительному учёту.
3. **Регрессионный тест** `apps/api/test/kosmora-limit-feedback.test.ts`:
   настоящий `buildApp` с `max_total_tokens = 1` проверяет, что прогон
   завершается `run.failed` с `USAGE_LIMIT_EXCEEDED`, канонический текст
   пользователя сохраняется целиком, а `usage().summary` отдаёт конечные
   числа и **не содержит** выдуманных `resets_at` / `remaining`.

## Чего не делали

- Не вводили период, дату сброса, размер бесплатной квоты, тарифы, квоты,
  провайдера HY4 и модель прав доступа.
- Не меняли контракт SSE `run.failed` (`additionalProperties: false`): числа
  берутся ленивым запросом к существующему эндпоинту, без расширения события.
- Не меняли схему БД и не добавляли миграций.
- Не трогали сайдбар, основной экран чата, логотип, палитру, типографику и
  глобальные стили — только текст ошибки и одну строку в существующем блоке
  настроек.
- Не обещали «запрос не отправлен»: это опровергнуто тестом.

## Ограничения

- Период обновления лимита не задан по решению владельца; пункт «время
  обновления» из целевого поведения K09 закрывается честным текстом, а не
  реализацией сброса.
- Числа в сообщении об ошибке приходят из `usage()` в момент показа; если
  эндпоинт недоступен, показывается fallback без чисел (без выдумывания).
- Живой провайдер не вызывался: тесты используют mock-шлюз. Проверен конвейер
  и форма сообщения, не качество ответа модели.
- При отказе по квоте провайдер мог уже получить запрос (см. выше); это
  существующее поведение резервирования, данный блок его не менял.

## Откат

`git revert <commit>` убирает текст ошибки, строку «Осталось» и тест.
Миграций и изменений формата данных нет, поэтому откат не требует действий с
БД; прежнее короткое сообщение «Измените квоту в персональных настройках»
будет восстановлено вместе с кодом.
