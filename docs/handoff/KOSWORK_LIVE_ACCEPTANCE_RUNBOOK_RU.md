# Живая приёмка Koswork: контрольная задача владельца — чек-лист

Статус: подготовка к живому сеансу. Код и локальные сценарии проверены;
реальная модель, приложения владельца и рабочий стол в этой проверке не
задействованы и не выдаются за проверенные. Дата подготовки: 8 ноября 2026.

## Что именно подтверждается (и что нет)

Контрольная задача владельца: **поиск информации → Word-отчёт с источниками →
сохранение на рабочем столе**.

Подтверждает:

- один агент, одна цель, план до восьми этапов с наблюдаемыми критериями;
- переходы между браузером, выбранной папкой и приложениями после отдельных
  разрешений, без повторного объяснения цели;
- проверка каждого критерия на свежем наблюдении и завершение задачи;
- создание настоящего DOCX через приложение Word с разрешённым управлением ПК
  (не переименованный Markdown);
- отдельное принятие результата владельцем (кнопка «Принять результат»,
  PR #468) и его отражение в истории.

Не подтверждает:

- семантическую правильность отчёта (это проверка моделью, не аттестация);
- гарантии, что модель распознает любое опасное действие (классификация
  модель-зависима);
- совместимость с произвольными приложениями (живой сеанс — один сценарий).

## Предусловия

1. **API доступен.** Обновлённый сервер с миграциями и последним `main`
   (включая PR #464 и #468, когда они объединены). Проверка: главная страница
   Kosmora открывается, `/api/v1/health` отвечает.
2. **Windows-клиент 0.23.0** (`desktop/windows/package.json`, версия 0.23.0)
   собран как unsigned-кандидат, updater OFF, и запущен на ноутбуке владельца.
3. **Провайдер.** Выбранная модель с vision-маршрутом для управления ПК
   (текстовый маршрут клиент не подменяет). Тарифы/квоты и модель HY4
   не меняются.
4. **Согласие владельца** на: снимки основного монитора и управление
   приложениями **для этой задачи и сеанса**; отдельная рабочая папка для
   файловых инструментов; открытие приложения Word для создания отчёта.

## Шаги живого сеанса

1. Запустить API (VPS) и клиент Kosmora на ноутбуке.
2. В меню клиента: **Koswork → Рабочая задача…** — открывается отдельное
   нативное окно. В web-панели Work кнопка «Выполнить в Koswork» только
   передаёт цель/проект в то же окно и сама ничего не запускает.
3. Выбрать проект, при необходимости подключить рабочую папку, ввести одну
   цель: «Найди в сети актуальную информацию по <теме владельца>, подготовь
   Word-отчёт с источниками и сохрани его на рабочем столе».
4. Проверить план: до 8 этапов, у каждого наблюдаемый критерий. Если план
   нерелевантен — отменить, поправить цель, начать заново (планирование не
   даёт доступа к экрану или сайтам).
5. По запросу разрешить **первый переход в браузер** (отдельное нативное
   разрешение) и **первый переход к ПК** (снимки монитора и управление
   приложениями). Разрешения действуют на одну цель и текущий сеанс.
6. Следить за окном: план, выполняемый этап, текущая среда, краткие отметки
   проверки. При `ask_user` — выполнить локальное действие и нажать
   «Продолжить после моего действия».
7. После создания отчёта проверить: файл .docx на рабочем столе, внутри —
   настоящий Word-документ (не текст с переименованием), источники приведены.
8. Завершение задачи — только после отметки каждого критерия на свежем
   наблюдении. В панели проекта нажать **«Принять результат»**; убедиться, что
   появилась строка «Результат принят владельцем <дата>».
9. Зафиксировать использование памяти/расхода: в панели видно число запросов;
   в настройках памяти — квитанции использованных источников.

## Остановка и границы (не нарушать)

- Остановка: нативная «Остановить», **Ctrl+Alt+Shift+K**, закрытие окна
  управления или выход из клиента.
- Лимиты: 90 действий и 30 минут на задачу; один task gate — параллельные
  браузерные/компьютерные агенты не запускаются.
- `ask_user` останавливает наблюдения и вызовы модели до Resume.
- Логин, MFA, CAPTCHA, UAC и заблокированные экраны выполняет только владелец.
- Снимки до разрешения не снимаются; refs/координаты через переключение сред
  не переносятся.

## Свидетельства для протокола

1. Скриншот плана с этапами и критериями.
2. Скриншот окна после завершения (все критерии отмечены).
3. Файл отчёта .docx с рабочего стола (имя, размер, дата).
4. Строка «Результат принят владельцем …» в панели проекта.
5. Журнал/квитанции usage по задаче (число запросов, канал work).

После сеанса сверяем с серверными записями: `manager_work` (статус
`completed`, `stage=done`, поля принятия), квитанции использования и, для
Windows-цикла, записи `work-tasks-v1` (только цель/план/статусы, без снимков
и токенов).

## Критерии успеха

- [ ] Одна цель → план → браузер (поиск) → файл .docx через Word → рабочий стол.
- [ ] Каждый критерий этапа подтверждён свежим наблюдением.
- [ ] Результат принят владельцем отдельным действием, виден в истории.
- [ ] Нет автоматического повторного запуска, лишних платных запросов и
      восстановленных разрешений после перезапуска.
- [ ] Файл открывается в Word как настоящий документ, источники на месте.

## Что остаётся за рамками

Установка клиента владельцу, выкладка на VPS и публикация релиза — отдельные
действия владельца. Multi-Agent и облачные компьютеры не включаются. Эта
проверка не заменяет общую приёмку первого этапа.
