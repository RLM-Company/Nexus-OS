# Журнал дополнительной памяти в запросах

Продолжение согласованного блока памяти Kosmora/Koswork. Функция показывает,
какой дополнительный пакет памяти был подготовлен для конкретного запроса.
Это не доказательство понимания источника моделью и не журнал всей переписки.

## Поведение

- Доверенные сборщики помечают исходный пакет, а квитанция проверяется для
  окончательного запроса после преобразований профиля / Relay.
- `exact`: исходный пакет присутствует в запросе. `unverified`: пакет мог быть
  преобразован, например переведён Relay. `none`: дополнительного пакета нет.
- Граница отправки и завершение провайдера — разные фазы. Ошибка / отмена после
  границы отправки не превращается в подтверждённое завершение.
- Каналы: обычный чат (включая фоновое исполнение), Manager Work и агент Koswork.
- Журнал содержит ссылки, версии и SHA-256; исходный текст в него не копируется.
  Переписка, вложения и результаты локальных файловых инструментов отдельно не
  включены в эту квитанцию.
- Не более 500 последних записей аккаунта, со страницами по 20. Удаление запуска,
  источника или записи памяти очищает связанные квитанции. Экспорт / удаление
  данных аккаунта учитывает новую таблицу; чужой аккаунт изолирован.
- Позднее завершение провайдера не восстанавливает вытесненную или удалённую
  квитанцию и не превращает успешно оплаченный ответ в ошибку журнала.
- Очистка журнала не удаляет исходные воспоминания. Во время активной работы или
  privacy fence очистка блокируется существующими ограничениями.
- В существующие настройки памяти добавлена свёрнутая функциональная секция.
  Главный экран, сайдбар, логотип и CSS не меняются.

## Миграция и выкладка

Новая миграция: `0059_memory_usage.sql`. Перед обновлением существующей базы
нужны проверенный online-backup и репетиция из общего offline release runbook.
Номер файла не означает число уже применённых миграций: проверять журнал и хэши.
Этот блок отдельно не активирует провайдера, не снимает остановки и не делает
платных запросов. Пакет замены VPS от 1 ноября собран с другого зафиксированного
коммита; наличие этой функции в рабочем дереве не означает её выкладку на VPS.

## Проверки

До возобновления серверной задачи целевые проверки API, DB и core проходили
локально (см. внешний checkpoint от 31 октября). Добавлены проверки фаз квитанций
Manager Work, отсутствия квитанции при отказе бюджета и браузерный сценарий
чтения/очистки без удаления источников.

Повторная локальная проверка 1 ноября выявила тайм-ауты подготовки SQLite-фикстур
(hook 10 секунд) и старта production webServer (180 секунд). Проверки и тайм-ауты
не ослаблялись; эти результаты не считаются успешной приёмкой. Полный результат
нужно подтвердить CI. CI сохраняет синтетический снимок панели квитанций для
визуальной проверки; отсутствие снимка не заменяет результат browser acceptance.

Точечный повтор двух новых Manager Work проверок прошёл после исправления
подготовки фикстуры: до настройки памяти завершаются как пустое Work, так и
начальный проектный чат. При активной очереди память по-прежнему изменять нельзя;
защитное условие не обходится и не ослабляется.

Браузерные сценарии памяти вынесены в отдельную последовательную фикстуру
HTTP/SQLite на 3226, аналогично существующим Issues/compaction-наборам.
Полная команда `test:e2e` по-прежнему запускает все сценарии. Общие параллельные
Work-тесты используют другую базу и больше не вызывают ожидаемый
`MEMORY_RUN_ACTIVE` внутри проверок редактирования памяти. Боевое условие
простоя владельца не менялось; повторные мутации и увеличенные тайм-ауты
не добавлены.
