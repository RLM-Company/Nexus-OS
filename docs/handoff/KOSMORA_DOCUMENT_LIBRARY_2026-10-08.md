# Kosmora — document library (blocks 11–13)

Base: tracked source snapshot `b15912d23ab15a99e38370e22e472faf28c99961` (8 Oct 2026). This handoff is for the main integrator, NOT proof that this feature has been deployed.

## What is implemented

- Durable, project/owner-scoped original **PDF/DOCX/TXT/CSV** files as SQLite BLOBs (20 MB/file, 100 MB and 100 files/project). Statuses `processing`, `ready`, `failed`; deletion and download; persisted across application restarts. Status `processing` can be resumed from the stored original in Studio after interrupted browser extraction.
- Source extraction **in the authenticated browser**: `pdfjs-dist` per-page PDF text, existing DOCX/TXT/CSV decoder for other formats. Up to 500 PDF pages/2M extracted characters. Server persists index and original, uses FTS5 for bounded lexical search and deterministic Russian-aware reranking, without paid embeddings or automatic model calls.
- Authoritative project/owner scope checks before all reads and writes. Filenames constrained and downloads returned as `application/octet-stream` with `nosniff`/attachment disposition. API avoids returning full source documents as part of normal list/search.
- Citation format: `file.pdf, стр. 12, строки 1–13`, or `file.csv, строки 40–52`. PDF lines are from the text extraction order, DOCX lines are extracted paragraphs, not Word's visual line wraps.
- Studio → «Крупные файлы»: upload multiple, see status, retry, download original, delete, search one or multiple documents, select fragments, preview report, generate actual DOCX / PDF / CSV downloads. «Прикрепить к чату» transfers up to 7400 text characters of selected fragments through the existing safe paperclip path; the model never receives the whole 20 MB file. No changes to Manager, Code-agent, Studio media editors, existing paperclip, autonomous privileges, provider, or paid requests.
- Reports are **source-excerpt reports**, not disguised model answers. After «Прикрепить к чату», the answer with sources is generated by the configured real chat model (when permitted). Report preview/download can be performed without a paid model call. Browser PDF export uses A4 raster pages with embedded JPEG: valid PDF, but not selectable/searchable text. DOCX has editable text. CSV has UTF-8 BOM and quoted fields; spreadsheet-formula prefixes are escaped.
- Scanned/encrypted PDFs have **no OCR** here. Existing PDF text layer is required. DOCX uses the existing bounded parser (up to 8 MB XML), so complex office package features and non-text elements are outside the indexed source.

### Manual end-to-end acceptance in integrated checkout

1. Open/create a project. Studio → «Крупные файлы» → upload a large text-layer PDF with a known fact on page N plus another TXT/CSV/DOCX.
2. See `processing` → `ready`. Refresh; files and status persist. Confirm source download matches uploaded binary.
3. Ask a factual question, with and without restricting the search to selected documents. Check citations' file/page/line against extracted text. Search for an absent fact: no invented hit.
4. Select evidence, send to chat, execute the live **approved** model route, verify a cited reply and model usage with no full-document injection.
5. Preview source report and download DOCX/PDF/CSV. Open each exported file in real viewers (PDF is intentionally raster). Delete a file; it must disappear from list, download and search, and from FTS. Check another owner's project cannot see/download it.
6. Interrupt indexing and refresh: file remains `processing` and offers a resume action. Test scanned PDF: `failed`, OCR not claimed. Test 20 MB and 100 MB quota boundaries and malicious filenames.

## Limitations and security notes

## Root integration verification — 9 October 2026

The original source-only checks above describe the producer's environment. In the actual Windows integration checkout on base `7e12e12`, the integrator ran the core/db/api/web typechecks successfully, the added core (3), database (2), API (3) and DOCX export (1) tests successfully, and ESLint on the changed source/test files successfully. The browser E2E is outside the existing ESLint TypeScript project scope and was verified by Playwright directly.

`apps/web/e2e/document-library.spec.ts` passed in real Chromium with the actual local API and SQLite fixture: project creation, original TXT upload, ready index, persistence after reload, byte-identical original download, exact source lines, an actual editable DOCX archive containing the fact and citation, preparation of an attachment without dispatching a model request, and document removal. No external model calls or production data were used. This check does not prove PDF/DOCX extraction in all viewers, production migration, or live deployment.

Integration repairs include strict control-character filename rejection without an ESLint-invalid regex, XML-safe DOCX text, preservation of empty PDF page positions, and clearer library heading text. Production deployment remains pending.

The browser provides the extracted text/page mapping, while the server stores its original binary. This implementation does not independently cryptographically verify PDF/DOCX text against the original on the server; provenance relies on the authenticated client extraction, and users should verify critical citations against originals. A client with owner privileges can deliberately submit arbitrary index text. Future optional server extraction can strengthen this without changing the route contracts.

Search is lexical FTS5 + a local ranker, not semantic embedding retrieval. At most 1200 matching rows per search are rescored and eight returned; broad queries on very large libraries may miss relevant evidence. This is deterministic, explicit, and does not claim exhaustive semantic ranking. Projects are backed up along with binary content; quota management and DB backup size should be monitored.
