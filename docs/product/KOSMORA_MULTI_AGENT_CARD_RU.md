# Карточка раздела Multi-Agent

Материал для совместного обсуждения по [workflow этапа](STAGE_TWO_WORKFLOW_RU.md),
подготовка одобрена владельцем 12 ноября 2026. Это карточка, не реализация:
runtime, UI и сервер этим документом не меняются. Multi-Agent остаётся
последним разделом; решение об объёме — за владельцем.

## 1. Пользовательская задача и полезный результат

Задача владельца, ради которой вообще стоит делать раздел: поручить крупную
работу так, чтобы части исполнялись **одновременно и под явными полномочиями**,
а результат собирался в проверяемый итог — без того, чтобы владелец вручную
нарезал задачу и без потери контроля за тем, кто что может делать.

Полезный результат формулируем честно: не «команда агентов» как зрелище, а

- разбиение задачи на независимые части там, где это реально сокращает
  время или улучшает качество;
- каждая часть — с собственными полномочиями, бюджетом и границей данных
  (никакой агент не наследует молча права владельца);
- собирание результатов с внешней проверкой, а не взаимным доверием агентов;
- полная наблюдаемость: владелец видит, какой агент что делал, что потратил
  и что проверено.

## 2. Текущее фактическое поведение Kosmora (проверено по коду 12.11.2026)

Существующее разделено на четыре слоя, и это ключ к пониманию, что уже
построено и чего не хватает.

### Что уже построено — governance-слой (реальный код)

- **Agent Studio (UI + API)**: страница `apps/web/src/app/agent-studio`,
  API `apps/api/src/app.ts` — полная CRUD-поверхность на проект:
  `functions`, `patterns` (с `test_status`: untested/verified/restricted/
  rejected), `blueprints` (с версиями), `proposals` (включая
  делегированные, с `parent_instance_id`), `decision-events`. Идемпотентность
  создания (conflict на повторный ключ), owner/project scoping на каждом
  маршруте, mutation-журнал с версионированием результата.
- **Контракты**: `packages/contracts/src/agent-studio.ts` — blueprint содержит
  grant (capability_ids/tool_ids/data_scope_ids/object_ids, бюджет в
  деньгах/токенах/операциях, `delegation_depth`, `valid_until`), memory_scope
  (read_mode: none/task/project_segments/handoff; write_back:
  none/result_only/result_and_evidence), task_contract, start/close условия.
- **База**: таблицы `agent_function_definitions`, `agent_blueprints`,
  `agent_studio_mutations`, `agent_studio_decision_events`,
  `agent_instances` + pattern library (`packages/db/src/schema.ts`), сторы
  с конфликтами/валидацией/делегированием.

Вывод: **слой конфигурации команды и полномочий уже построен** — роли,
права, бюджеты, делегирование, журнал решений. Это значительное преимущество:
не нужно проектировать governance с нуля.

### Что отсутствует — runtime-слой (проверено по коду)

- Ни один исполнительный код не потребляет `agent_instances`: единственные
  упоминания — в API-сторах и маршрутах. Work-исполнитель командной строки
  прямо фиксирует «одна задача — один план, не multi-agent team»
  (`apps/api/src/computer-control/service.ts`).
- Нет: планировщика, порождающего экземпляры из blueprint'ов; межагентной
  коммуникации; сборки результата из частей; общего бюджета команды поверх
  owner-бюджета; перезапуска/восстановления упавшего экземпляра.

### Поверхности UI (макеты, не поведение)

- Режим «Multi-Agent» в оболочке — статическая презентация: роли Manager /
  Исполнитель / Критик, текст «правила проектируемого интерфейса»
  (`apps/web/src/app/workspace-sections.tsx`, `Team`), FutureHint про
  отдельные права видимости коллективных чатов. Аудит K10 уже отмечал:
  панель упоминает «мультиагентная команда» — формулировку можно уточнить
  только по решению владельца (`KOSMORA_K10_TRANSITION_AUDIT_RU.md`).
- Desktop-клиент: `multi-agent` входит в восстанавливаемые поверхности
  (`desktop/windows/desktop-recovery.cjs`) — маршрут открывается,
  содержимого за ним нет.

### Сопутствующие основания, уже работающие

- Work DAG, пределы активных запусков, admission, общий owner budget и
  ledger с расходом (`RUFLO_ADOPTION_SCOPE_RU.md`).
- Skills/специализации: срезы 06_CLAUDE в main (#538) — явный scope,
  precedence, детерминированное разрешение конфликтов, цикл подтверждённых
  исправлений владельцем, model-free оценка результата по явным критериям.
  Это естественные «поведенческие паттерны» для ролей.
- Память с привязкой к владельцу/origin, изоляция владельцев A/B в
  настольном клиенте, черновики с DPAPI.

### Дублирование и чего не хватает (кратко)

Дублирования нет — governance-слой один. Не хватает именно **исполнения**:
планировщика команды, межагентной передачи, сборки и проверки результата,
бюджета команды, наблюдаемости прогона.

## 4. Причина делать именно этот раздел (и когда он оправдан)

Раздел оправдан только там, где одиночный агент — реальное ограничение:

1. **Время на независимых частях**: проверка фактов, сбор источников и
   черновик — параллельно, если части не зависят друг от друга.
2. **Разные полномочия по необходимости**: исполнитель с правом записи в
   рабочую папку и проверяющий с правом только чтения — безопаснее, чем
   один агент с максимальными правами на всё.
3. **Внешняя проверка результата**: второй агент с иным контекстом не
   «убеждает» первый, а проверяет по явным критериям (у нас уже есть
   model-free оценка по критериям из #538).

Где он **не** оправдан (и потому не входит в предложение): разбиение
последовательных процедур — там дешевле один агент; повторная проверка
«критиком» ради вида; любые сценарии, где выигрыш только в формулировке
«команда» (`KOSWORK_FUNCTIONAL_BLUEPRINT_RU.md`, строки 232-237, уже
фиксируют это ограничение).

## 5. Предложение

Сохраняем и переиспользуем (уже построено, не переделывать):

- governance-слой Agent Studio целиком: blueprint'ы, grants, бюджеты,
  delegation_depth, memory_scope, decision events — как единственный
  источник полномочий;
- Work DAG, admission, owner budget и ledger — бюджет команды добавляется
  поверх, вторым журналом не становится;
- skills/специализации с scope/precedence как поведение ролей;
- Work-исполнителя как **единственного** типа runtime-агента первого
  выпуска: те же проверки, те же честные отказы, те же лимиты.

Доделываем (ядро среза — runtime):

1. **Планировщик команды**: из blueprint'ов проекта порождать экземпляры
   (`agent_instances`) с родителем, глубиной делегирования и
   индивидуальными бюджетами; без blueprint'а — одного агента (сегодняшнее
   поведение сохраняется по умолчанию).
2. **Сборка результата**: arbiter-шаг, собирающий части в итог с явным
   указанием, какая часть кем сделана; конфликты частей не разрешаются
   «голосованием» — возвращаются владельцу.
3. **Наблюдаемость прогона**: панель хода с экземплярами и их расходом,
   decision events при делегировании и завершении.

Убираем из планов (и это важно):

- «Коллективные чаты с агентами» из FutureHint — отдельный будущий раздел,
  не часть первого выпуска;
- любые автоконфигурации «команды» без явного blueprint'а и подтверждения
  владельцем.

Отдельные собственные идеи Kosmora (польза объяснена):

- **Blueprint как видимый продукт**: в отличие от конкурентов (Claude
  скрывает суб-агентов, Google их не даёт), Kosmora может показать
  пользователю, кто с какими полномочиями и бюджетом работает — это
  превращает уже построенный governance-слой в конкурентное отличие, а не
  в мёртвый код. Польза: контроль и доверие без чтения логов.
- **Проверяющий без права записи** как дефолтный Критик: внешняя проверка
  результата по явным критериям (механизм из #538), а не «второе мнение»
  другой модели.

## 6. Необходимые внутренние механизмы и связь с результатом

| Механизм                                                                                                                  | Связь с пользовательским результатом                                      |
| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Планировщик команды поверх Work DAG (spawn из blueprint'ов, CAS-слот как сегодня)                                         | Одновременные части задачи без второго управляющего движка                |
| Runtime-исполнитель экземпляра (тот же Work executor, публичный контракт)                                                 | Части исполняются той же проверенной машиной, без нового класса рисков    |
| Бюджет команды поверх owner budget (ledger остаётся один)                                                                 | Расход виден и ограничен; никакого второго учёта денег                    |
| Межагентная передача результата (файлы/текст с версиями, без чата)                                                        | Сборка без утечки полномочий: передача — данные, не права                 |
| Arbiter-сборка + проверка по критериям (#538)                                                                             | Итог проверяем, а не «согласован между агентами»                          |
| Decision events на делегирование/завершение/остановку                                                                     | Владелец видит, кто что решил и что потратил                              |
| Отмена/восстановление: отмена владельцем останавливает поддерево; восстановление экземпляра по контрольной точке Work DAG | Прерывание не теряет завершённые части; чужие владельцы не подхватываются |

## 7. Нормальный сценарий, ошибки, отмена, повтор, восстановление, ограничения

Нормальный сценарий: владелец даёт задачу проекту → Work-агент строит план →
если части независимы и есть blueprint'ы, планировщик предлагает состав
(владелец подтверждает при первом запуске состава) → части исполняются
параллельно с индивидуальными бюджетами → arbiter собирает итог, проверка
по критериям → владелец видит: план, экземпляры, расход, что проверено.

Ошибки: недоступность модели у части — честный статус части и повтор по
существующим retry guard'ам; конфликт частей — возвращается владельцу;
исчерпание бюджета экземпляра — остановка только этого экземпляра, итог
отмечается неполным, ничего не молчит.

Отмена: остановка поддерева экземпляров, завершённые части сохраняются как
артефакты с версиями; повторное делегирование создаёт новые экземпляры со
своими ключами идемпотентности (защита от двойного внешнего эффекта уже есть
в #430/#432 механике).

Восстановление: перезапуск сервера восстанавливает поддерево по контрольным
точкам Work DAG; экземпляр не «оживает» с чужими полномочиями (grant'ы
валидны по времени и версии blueprint'а).

Понятные ограничения первого выпуска: один тип исполнителя; состав команды
задаётся blueprint'ами и подтверждается владельцем; нет коллективных чатов;
нет межагентных приватных диалогов; глубина делегирования ограничена
`delegation_depth`; всё в границах current device/data grants — новые
OS-полномочия не вводятся.

## 8. Проверяемые критерии готовности

- Время на параллелизуемой задаче сокращается против одиночного агента на
  одном и том же наборе задач (включая русский язык), при сопоставимом
  качестве по тем же критериям проверки результата.
- Расход не превышает owner budget; ledger показывает раздельные расходы
  экземпляров; счётчик «предотвращённых бесполезных вызовов» не деградирует.
- Ни один экземпляр не действует вне grant'а blueprint'а (проверка:
  попытки выхода фиксируются в decision events и отклоняются).
- Отмена и восстановление не теряют завершённые части и не повторяют
  внешние эффекты (проверка на синтетических задачах без платных моделей).
- Live-приёмка — отдельно, после VM-прогонов, по правилу пакета.

## 9. Открытые вопросы владельца

1. **Формат раздела**: нужен ли пользовательский конструктор команд (видимый
   Agent Studio как продукт) или coordination остаётся внутренним механизмом
   Work, как у конкурентов? Наш governance-слой позволяет первое; второе
   быстрее до результата.
2. **Первый выпуск**: параллельные части + проверяющий без записи +
   бюджет команды — согласуете такой минимальный объём?
3. **Формулировки панели**: уточнить текст «мультиагентная команда» в
   существующем макете (только формулировка, без редизайна — по
   `apps/web/UI_RULES.md` требуется точечный запрос)?
4. **Интеграция с уже отложенным**: live-приёмка Windows и первый live-прогон
   ждут секрета `KOSMORA_LIVE_ORIGIN` — держать их впереди или параллельно?

### Решения владельца (13.11.2026, question-tool)

1. Формат раздела — **blueprint-ориентированный**: состав команды задаётся
   blueprint'ами проекта (построенный governance-слой) и подтверждается
   владельцем при первом запуске состава; без blueprint'ов — один агент
   (сегодняшнее поведение по умолчанию).
2. Объём первого выпуска — **минимальный объём + файловые артефакты**:
   завершённые части сохраняются как файловые артефакты с версиями в
   рабочей области (прерывание и повторное делегирование не теряют
   сделанное).
3. Формулировка — **уточнена** (точечный запрос владельца по UI_RULES):
   надпись шапки чата проекта заменена на «Менеджер · проект», e2e-утверждение
   обновлено с rationale.
4. Приоритет — **Multi-Agent впереди**; live-приёмка остаётся отложенной до
   готовности владельца (секрет `KOSMORA_LIVE_ORIGIN`; задание включится
   само).

## Границы (не нарушать)

Никакой реализации в этой карточке; Multi-Agent остаётся последним разделом —
реализация только после согласования объёма владельцем. Jarvis, облачный ПК,
обучение весов, VPS, выкладка и платные вызовы не затрагиваются. Существующие
границы устройства и данных не расширяются. Решения о конкурентных сравнениях —
только по фактически проверенным строкам раздела 3 с датами проверки.
