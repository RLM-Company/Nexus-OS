# Срез Multi-Agent: arbiter-сборка + проверка по критериям (#538)

**Статус: объём согласован владельцем 13.11.2026 (§7), реализация —
отдельный следующий шаг; код на этом шаге не менялся.** Материал подготовлен
по поручению владельца «Согласовать объём arbiter/#538» (13.11.2026). Опора: [карточка раздела](KOSMORA_MULTI_AGENT_CARD_RU.md) (п. 5–8, решения
владельца 13.11.2026) и [workflow этапа](STAGE_TWO_WORKFLOW_RU.md).

## 1. Задача и полезный результат именно этого среза

Срезы 1 и 2 уже дали: состав из blueprint'ов (1 blueprint = 1 узел, плоский
DAG без зависимостей между частями), bounded concurrency `cap=2`, каждая часть
— обычный Work с иммутабельными версионированными опубликованными артефактами
(`sha256`), статус части и `artifact_count` читаются из DAG. Чего нет:
**единого собранного результата команды** и **проверки целого по явным
критериям**. Сегодня владелец открывает файлы каждой части вручную, а
проверка — либо платный модельный Critic на отдельный узел, либо проверка
имён файлов в workflow.

Полезный результат среза (честно): когда все части завершены, владелец
получает **один инертный проверяемый итог** — детерминированную сборку
опубликованных артефактов частей с происхождением (какая часть, какой
экземпляр, версия, sha256) плюс **model-free отчёт по явным критериям**.
Конфликты частей не разрешаются «голосованием» и не переписываются — они
возвращаются владельцу. Никаких новых платных модельных вызовов, никакого
«второго мнения» модели, никакого второго журнала расхода.

## 3. Чего genuinely не хватает (новое, подлежит согласованию)

1. Объект «собранный результат команды», привязанный к составу/графу, с
   происхождением каждой части (сейчас есть только generic `results`/ZIP,
   не связанные с team-activation/parts).
2. Проверка **целого** по явным критериям: сегодня проверка либо платный
   per-node Critic, либо проверка имён файлов — детерминированной проверки
   собранного результата по критериям нет.
3. Явные критерии с **замороженным снимком**, владельцем/blueprint'ом
   заданные (не придуманные агентом, не «взаимное доверие агентов»).
4. Обработка конфликтов частей → владельцу (не голосование, не перезапись).
5. Decision event на сборку/проверку (новые литералы операции).

**Уже есть и НЕ переделывается:** Work DAG, admission/`cap=2`, owner budget и
единый ledger, versioned artifacts, `recover()`, двухфазный `dag_binding.bound`,
per-node платный `require_critic`, гранты blueprint'ов.

## 4. Отличие (diff) и честные границы

- От текущего поведения: «владелец вручную открывает N файлов» → один
  инертный бандл с provenance + отчёт `passed/checks/not_checked`.
- От платного Критика: «Критик без права записи как дефолтный проверяющий»
  (карточка п. 5, строка 172–174) = **model-free `evaluateSkillResult()`**,
  а не второй модельный вызов. Платный `require_critic` остаётся per-node и
  этим срезом не включается/не расширяется.
- Конкурентные сравнения — только по проверенным строкам карточки §3 с датами;
  новых заявлений о превосходстве не делаем.
- Никаких новых прав устройства/данных, коллективных чатов, второго ledger,
  нового типа runtime-агента, автоконфигурации команды без blueprint'а.

## 5. Сценарии

- **Норма:** все части `completed` → детерминированная сборка (байт-проверенные
  published-артефакты) → проверка по замороженным явным критериям → владелец
  видит бандл + отчёт (какой критерий прошёл/не прошёл, factual `detail`) и
  может скачать архив. Arbiter не тратит модельных запросов.
- **Часть failed / неполный состав:** итог помечается неполным (`incomplete`),
  завершённые части сохраняются, ничего не молчит и не «дотягивается» до успеха.
- **Конфликт частей** (противоречивые required facts / перекрытие): возвращается
  владельцу механически, без голосования и без переписывания содержимого.
- **Отмена / восстановление:** части уже сохраняются версионированными
  артефактами (срезы 1–2); arbiter — read-only поверх published-артефактов,
  replay детерминированно пересчитывает итог, двойного внешнего эффекта нет.
- **Ошибка критерия:** отсутствующий `required_fact` → `passed:false` с
  фактическим `detail`, без балла/уверенности/процента; `not_checked` явно
  указывает, что истинность и качество не проверялись.

## 6. Границы реализации первого выпуска (если объём согласован)

- **Без редизайна UI** (`apps/web/UI_RULES.md`): чат, sidebar, логотип,
  стили, типографика не меняются. Доставка — через существующие DAG-results
  маршруты + team-scoped путь чтения, без новой панели.
- **Без платных вызовов** на arbiter, без новых OS/data grants, без коллективных
  чатов, без второго ledger, без нового исполнителя.
- **Бюджет команды поверх owner budget** и **панель хода** — отдельные
  следующие срезы, в этот не входят (карточка §5, CHECKPOINT «следующий шаг»).
- Проверка — проектные сценарии на синтетических данных без платных моделей;
  live-приёмка остаётся отложенной (`KOSMORA_LIVE_ORIGIN` не создан).
- Потолок статуса среза — «готово к интеграции»; merge PR только после
  явного одобрения владельца.

## 7. Открытые решения владельца

1. **Источник явных критериев** (`required_facts`/`forbidden`/`format`):
   задаёт владелец при подтверждении состава/запуске плана и они
   замораживаются снимком (как `expected_results`); либо берутся
   детерминированно из `task_contract` blueprint'а; либо ограничиваемся
   только проверкой целостности/имён публикаций без содержательных фактов.
2. **Природа сборки**: инертный детерминированный бандл/ZIP с provenance без
   переписывания (как `buildWorkResultsArchive`) — или смысловое слияние
   частей в единый документ (потребует платного модельного вызова и потери
   byte-верифицируемости).
3. **Граница среза**: только arbiter-сборка + проверка по критериям +
   assembly decision event — или включить сразу бюджет команды / панель хода.

Конфликты → владельцу (без голосования) и model-free природа проверяющего
зафиксированы карточкой раздела и отдельному голосованию не выносятся.

### Решения владельца (13.11.2026, question-tool)

1. **Источник критериев — владелец + замороженный снимок**: владелец задаёт
   `required_facts`/`forbidden`/`format` при подтверждении состава/запуске
   плана; критерии замораживаются immutable-снимком по образцу
   `expected_results`/`definition_version`. Механизм #538 критерии не
   придумывает, модель их не генерирует.
2. **Природа сборки — инертный бандл + provenance**: детерминированная сборка
   опубликованных артефактов с происхождением каждой части, без переписывания
   содержимого, без платных модельных вызовов, byte-верифицируемо. Смысловое
   слияние в документ исключено.
3. **Граница среза — только arbiter**: сборка + проверка по критериям +
   decision event на сборку. Бюджет команды поверх owner budget и панель хода —
   отдельные следующие срезы (панель хода потребует точечного запроса по
   `apps/web/UI_RULES.md`).

Итог согласованного объёма: model-free arbiter read-only поверх
published-артефактов, проверка целого по явно заданным и замороженным
критериям, конфликты → владельцу, без UI-изменений/платных вызовов/новых
прав/второго ledger. **Реализация — отдельный следующий шаг; в этом файле и
на этом шаге код не менялся.**
