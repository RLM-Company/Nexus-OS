## 1. Задача пользователя и результат

Дать материалы и цель, получить план с зависимостями, выполнить шаги, получить
проверенные файлы и скачать их. При остановке плана — скачать честный частичный
результат.

## 2. Текущее поведение Kosmora

Источник: чтение кода, тестов и локальные запуски. Живой прогон не выполнялся.

Работает на уровне fixture-тестов API:

- план из шагов с `depends_on`; содержимое файла первого шага попадает в запрос зависимого (`work-dag.test.ts`, проверка `source_artifact_ids` и текста файла);
- пауза и возобновление одиночной задачи, дисковый чекпоинт;
- после перезапуска автозапуск не возобновляется сам: статус `RESTART_REQUIRES_RESUME`, завершённые шаги не повторяются;
- отмена шага до старта, в очереди, в полёте и при паузе плана; отправленный запрос остаётся неопределённым расходом;
- повтор шага только с `acknowledge_cost`; без него `EXPLICIT_RETRY_REQUIRED`, модель не вызывается;
- ZIP результатов: только опубликованные файлы завершённых шагов, SHA-256 и байты сверяются, `complete: false` для частичного результата;
- повреждённый файл даёт 409 `ARTIFACT_INTEGRITY_MISMATCH` без вызова модели;
- бюджет владельца, ограждение владельца, контекстная память, превышение окна контекста.

В интерфейсе (`work-manager-dag.tsx`) по чтению кода есть: «Повторить этот шаг…» с чекбоксом расхода, подтверждение отмены шага, ссылки «Скачать отчёт и файлы (ZIP)» и «Скачать все результаты плана». Ссылка на ZIP не зависит от завершённости плана.

Покрыто веб-тестами (`work-manager-dag-controls.test.ts`, 14 проверок): повтор с
подтверждением расхода, блокировка платных действий, условия кнопок и текста
подтверждения отмены шага, условия ссылок на ZIP и JSON, пометка частичного
результата. DOM-тестов на сам компонент нет: в проекте применяется
`renderToStaticMarkup` для display-частей, а этот компонент — клиентский, с хуками.

Не покрыто:

- живой прогон с моделью, опрос прогресса в браузере, реальное скачивание ZIP, пауза через кнопки — не проверялись;
- живая приёмка этапа 1 не выполнена (`live_model_accepted:false`, `owner_windows_accepted:false`).

Неизвестно: состояние снимка материалов плана и восстановления очереди (PR #592, #593) — зависит от sync.

## 4. Предложение (решает владелец)

Сохранить: модель плана с зависимостями, явный повтор с подтверждением расхода, честный частичный ZIP, проверку целостности при выдаче.

Доделать:

1. **Снято после sync 15 ноября.** Локально выносились чистые правила
   управления планом в `work-manager-dag-controls.ts` (14 тестов, без изменения
   видимого поведения). После `git fetch` + fast-forward main `80481bb1`

## 5. Внутренние механизмы

DAG-координатор, пошаговый конвейер с проверкой Критика, версионированные артефакты, CAS по версии плана, закрепление Skills на план, бюджет владельца с учётом неопределённых удержаний.

## 6. Ошибки, отмена, повтор, восстановление

Уже определены в коде (см. раздел 2). Ограничения для пользователя: отменённый шаг продолжить нельзя, нужна копия плана; перезапуск требует явного продолжения; повтор может тратить токены.
