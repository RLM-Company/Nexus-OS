# Koswork: требования к скетч-формату reference для кросс-пакетной договорённости

Статус: подготовлено пакетом 03_OPENCODE 2026-11-12 по выбору владельца после
merge #540. Это материал для решения владельца и — при его указании — задание
пакету 01_CODEX. Код не пишется до договорённости. Базовый план:
[EXPERIENCE_DISTILL_PLAN_RU.md](EXPERIENCE_DISTILL_PLAN_RU.md) (вариант B).
Реализованный первый шаг — вариант A (#537, #540): скраб внутри текущего
формата `koswork.accepted-example.v1`.

**Решение по вилке (2026-11-12)**: владелец делегировал выбор пакету
03_OPENCODE («выбери сам»); решение пакета — **остаться на A**. Основание:
gate-замер раздела 1 (медиана скетч/A 0,943; с метками потерь 1,0348 —
байтового выигрыша нет); маркеры потерь дублируют рамку
`WORK_REFERENCE_RULES`, которая уже называет те же классы
наследуемо-запрещённого, а упоминание дропнутых шагов само приглашает модель
достраивать пробелы; хранимый компактный след — ценность только при
реальном запросе память/история-функций (план предусматривает вернуться
тогда). Документ остаётся материалом на будущее; в пакет 01_CODEX ничего
не передаётся.

## 1. Gate-замер после A — обязательное условие плана

План требовал: вариант B — только если после A остаточная ценность
скетч-формата подтверждена замером. Замер выполнен 2026-11-12 на замороженной
панели v1 (13 кейсов, read-only): скетч-конструктор bench-кандидата
(`extractive-drop-candidate-v1`: цель-префикс с лимитом 480 байт, kinds без
counts, бюджет скетча 5 000) работает на тех же фиксированных паттернах, что
продукт после #540; сравнение с уже скрабленным reference варианта A

компромисс, который план требовал проверить до договорённости.

## 2. Что остаётся ценного в B (честно)

1. **Маркер частичности**: A дропает шаги молча (семантика «пример без
   молчаливых шагов» принята владельцем в #537); B несёт маркированные
   потери в самом артефакте. Ценность — честность формата, а не байты
   (и она стоит байтов, см. раздел 1).
2. **Компактный хранимый след**: скетч как формат хранения принятого опыта —
   фундамент будущих память/история-функций; ценность вне текущего потока
   запросов, проявляется только при реальном запросе этих функций.
3. **Единые лимиты** (цель 480 байт, бюджет 5 000): выравнивание лимитов,
   а не выигрыш — бюджет 5 000 на больших примерах режет
   переиспользуемый хвост (кейс large-with-clipping), тогда как лимит API
   14 000 A-выпуск не исчерпывает.

## 3. Вилка для решения владельца

- **B-полный** (новый формат `koswork.example-sketch.v1`): максимум формата,
  весь объём раздела 4; байтовый выигрыш ~0% в медиане (раздел 1); изменения
  в `packages/contracts` и `apps/api/computer-control` (сфера 01_CODEX) +
  conformance в desktop.
- **B-lite** (минимальное расширение существующего формата): опциональные
  поля в `accepted-example.v1` (например `plan_partial: true` +
  `lost_steps`) — закрывает пункт «маркер частичности» без нового формата;
  объём изменений contracts+API+desktop на порядок меньше; маркеры в любом
  варианте не бесплатны (+3.5% медианы байтов по замеру раздела 1).
- **Остаться на A**: замер говорит, что острота байтов низкая; маркер
  частичности уже принят как семантика; хранимый след можно вернуть при
  реальном запросе память/история (данные и bench в main ничего не теряют).

Рекомендация пакета 03_OPENCODE: **B-lite**, если нужен маркер частичности;
**B-полный** — только если владелец считает хранимый компактный след
приоритетом, оправдывающим кросс-пакетный объём. Решение владельца.

## 4. Если B-полный: требования к договорённости

### 4.1 packages/contracts (сфера 01_CODEX)

- Новый член union `WorkReferenceSchema`:
  `ExampleSketchReferenceSchema` с `format: Literal("koswork.example-sketch.v1")`,
  strict (`additionalProperties: false`, как у соседей).
- Поля (bench-кандидат + маркировка потерь): `prototype`
  (`^[a-z0-9-]{1,64}$`), `source_task_id` (тот же uuid v4-паттерн),
  `source_project_id` text(160), `accepted_at ≥ 0`,
  `outcome: Literal("owner_accepted")`, `goal_excerpt` (граница — открытый
  вопрос 5.1), `goal_prefix_only` const true, `goal_cut` Boolean,
  `plan` 0..8 × {title ≤180, criteria ≤240} (minItems 0 валиден только
  вместе с непустым `lost_steps`), `tool_kinds` ≤16 × `^[a-z_]{1,64}$`
  (sorted unique — фиксировать валидатором/конформансом, не паттерном),
  `tool_counts_included` const false, `weights_trained` const false,
  `lost_steps` ≤8 × {index 0..7, rule `^[a-z_]{1,64}$`}, `clipped_steps` 0..8.
- **revision — хэш ИСХОДНОЙ записи, не скетча** (desktop уже считает его от
  id/project/goal/plan/steps/acceptedAt): совместимость с защитой от
  наследования грязных данных и desktop-историей.
- Бюджет 14 000 остаётся; скетч ≤ 5 000 по определению — ниже лимита.

### 4.2 apps/api/src/computer-control (сфера 01_CODEX)

- `Value.Check` по union — механика без изменений, двухформатность
  прозрачна для валидации, хэша и конфликта ревизий
  (`COMPUTER_REFERENCE_CONFLICT` — формат-агностичен).
- `WORK_REFERENCE_RULES` дополнить предложением о скетче: `tool_kinds` —
  только kinds без counts; `lost_steps`/`clipped_steps` — заявленные
  потери, план может быть неполным; не достраивать молча.

### 4.3 desktop/windows (сфера 03_OPENCODE)

- Ядро то же (`work-reference-scrub.cjs`); скетч-конструктор переносится из
  bench-кандидата в продукт с единственным источником паттернов (модуль
  после #540). Bench-скрипт и панель не редактируются.
- Правило выбора формата — решение владельца (открытый вопрос 5.4).
- Тесты: паритет свойств с bench (0 запрещённых фрагментов, свойство цели
  по решению 5.2, детерминизм бит-в-бит, бюджет, маркировка).

### 4.4 Conformance (оба пакета)

- Замороженная панель v1 остаётся эталоном (read-only): оба пакета прогоняют
  её через свою реализацию; критерии: REPRODUCED true бит-в-бит, 0
  запрещённых фрагментов, шаги плана — целое подмножество исходных,
  `tool_kinds` ⊆ исходных kinds, `lost_steps` = дропы по паттернам.
- Расхождение реализации — блокер интеграции, а не «особенность».

## 5. Открытые вопросы до кода (решение владельца / договорённость)

1. **Пустая `goal_excerpt`**: bench допускает пустую цель (goal_empty),
   `text(500)` в accepted-example пустоту запрещает. Варианты: пустая цель
   → честный отказ скетча (паритет с A) или пустая + явный флаг.
2. **Точный префикс против нормализации**: bench re-join предложений
   пробелом не всегда даёт точный префикс исходника; A — точный префикс.
   Панель на точных префиксах разницу не ловит — выбрать семантику до кода
   (точный префикс или явный флаг нормализации).
3. **Маркированные потери в скетче**: включать (честность, +байты) или нет;
   в bench-скелете их не было — план обещает их формату B.
4. **Правило выбора формата при двух форматах** (всегда B / по размеру /
   флаг владельца) и судьба `accepted-example.v1` (не удалять: история и
   corrections остаются).
5. **Достаточность хранимого следа**: counts остаются в desktop-записи;
   скетч их не переносит — хватает ли этого для будущих память/история.

## 6. Что не меняется при любом исходе

Веса, fine-tuning и сеть исключены; новые журналы денег и управляющие
движки не создаются; автоматическая выдача remedialResolution исключена;
bench/фикстуры не редактируются и вне CI; права устройств и гранты не
расширяются; UI приёмки не меняется (видимые изменения — только через
VISUAL_WAITLIST и решение владельца); Multi-Agent — последний раздел;
live-приёмка — прежняя отложенная граница. Задание пакету 01_CODEX выдаёт
владелец — этот пакет требования не навязывает и в чужую сферу не входит.
