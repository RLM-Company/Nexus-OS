### Что именно отсутствует в K09

По тексту целевого поведения («остаток, время обновления и объяснение
расхода; незавершённый текст пользователя сохраняется при исчерпании»):

1. **Нет остатка и времени обновления.** `max_total_tokens` — это накопительный
   персональный предел без периода: в `kosmora_account_preferences` хранится
   только число и `updated_at` (время правки настройки), нет поля периода или
   даты сброса. `Summary` содержит `total_counted_tokens` и `max_total_tokens`,
   но не `remaining` / `resets_at`. UI показывает прогресс «потрачено/лимит»,
   а не «осталось» и «когда обновится».
   В брифе отдельно сказано: «Конкретные значения и период лимита не
   определены» — то есть период требует решения владельца, это не баг кода.
2. **Объяснение расхода есть**, но только в личных настройках: детализация по
   запросам (провайдер, модель, статус, input/output/reserved). В момент отказа
   по лимиту пользователь видит код ошибки `USAGE_LIMIT_EXCEEDED` без указания,
   сколько израсходовано и где посмотреть разбивку. Важный нюанс, найденный
   тестом: `accountStore.reserve()` вызывается **внутри** цикла
   `for await` после события `route.selected`, поэтому провайдер может уже
   получить запрос до отказа. Нельзя обещать «запрос не отправлен» — честная
   формулировка: «прогон остановлен, текст сохранён».
3. **Сохранение незавершённого текста при исчерпании.** Черновик композитора
   уже сохраняется в localStorage/Windows draft bridge и восстанавливается
   после reload; при отказе запроса по квоте `submit` не очищает `draft`
   (очистка идёт только после успешного accepted). Это поведение существует,
   но не закреплено отдельным тестом именно для `USAGE_LIMIT_EXCEEDED`.

## Вывод

K07 и K08 закрыты. Реальный пробел — только K09, и он **продуктовый**:
период и размер бесплатной квоты владелец ранее не определял. Без этого
решения «время обновления» и «остаток» невозможно реализовать честно —
пришлось бы выдумать период.

Поэтому предлагаю не изобретать тариф, а закрыть ту часть K09, которая не
требует нового продуктового решения, и отдельно вынести вопрос о периоде
на согласование.

## Предлагаемый объём (на согласование)

1. **Честный отказ при исчерпании лимита.** В сообщении об ошибке прогона
   `USAGE_LIMIT_EXCEEDED` добавить понятный текст с двумя фактами из уже
   существующего `usage()`:
   - сколько учтено и каков предел;
   - где смотреть разбивку (ссылка на личные настройки Usage).
     Без новых чисел, без «осталось», без периода.
2. **Явный признак остатка там, где он корректен.** `remaining =
max(0, max_total_tokens - total_counted_tokens)` — только когда
   `max_total_tokens` задан. Показывать рядом с прогрессом как «Осталось N
   токенов», не называя это «бесплатным лимитом на день/месяц».
3. **Регрессионный тест «текст не теряется при отказе по квоте»**: HTTP-путь
   с `QuotaExceededError`, проверка что черновик/поле ввода сохраняется и
   пользователь может повторить. Без изменения модели прав и тарифов.
4. **Ничего не меняем** в провайдере HY4, квотах, тарифах, модели доступа,
   правилах резервирования и в значениях лимита по умолчанию.

## Вопрос владельцу (продуктовое решение, без него не начинаем)

Нужен ли период обновления личного лимита? Варианты:

- **Оставить без периода** (текущее поведение): накопительный предел, который
  владелец меняет в настройках вручную. Тогда пункт «время обновления» из
  целевого поведения закрывается честной формулировкой «период не задан»,
  а не выдуманной датой.
- **Ввести период** (например, сутки/месяц по московскому времени) — тогда
  это новый объём: миграция, поле `resets_at`, сброс счётчика, отдельное
  решение по размеру квоты. Требует отдельного согласования и не входит в
  этот срез.

## Критерии приёмки (для выбранного объёма)

- Отказ по лимиту содержит фактические числа из существующего `usage()` и
  ссылку на разбивку; новых/выдуманных чисел нет.
- «Осталось» показывается только при заданном `max_total_tokens` и не
  противоречит накопительному учёту.
- Текст запроса сохраняется после отказа по квоте; тест это фиксирует.
- Существующие 900+ api-тестов и e2e не меняют поведения.
- Провайдер, тарифы, квоты и модель прав не изменены.

## Что не входит

- K06 (голос/изображения) — отдельное решение по квотам.
- K10 (переход в Koswork) и скрытые механизмы I01–I07 — следующий разбор.
- Живая приёмка первого этапа, VPS и Windows-клиент — как предписано
  `AGENTS.md`, остаются отложенными.
- Сайдбар, основной экран чата, логотип, палитра, типографика — без
  изменений; допустим только функциональный текст в существующем экране
  настроек и в сообщении об ошибке прогона.
