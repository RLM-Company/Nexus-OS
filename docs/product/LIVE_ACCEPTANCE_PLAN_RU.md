# Kosmora Windows: план живой приёмки (cookie gateway, DPAPI, reconnect)

Статус: отложение снято владельцем 2026-11-12. Это план проверяемого сценария —
материал для согласования объёма и среды до прогона; реальные прогоны после
одобрения. Записанный отложенный объём: BACKLOG пакета («реальная живая
приёмка — отдельно согласованные live-проверки»), `INTEGRATION_0.11.2.md`,
`ACCEPTANCE_0.11.2.md`, README desktop/windows.

## 1. Что принимаем

Три механизма из записанного отложенного объёма — на **реальном
Electron-клиенте против живого сервера** (сегодня их логика покрыта
node-тестами, а CI-приёмки живут на локальных фикстурах; NSIS fresh /
upgrade+uninstall / SHA-256 и sandbox уже покрыты отдельными заданиями CI и
не дублируются):

- **A. Cookie gateway** — настоящая сессия Chromium против живого сервера:
  вход через auth gateway; cookie-авторизованный identity fetch
  (`/api/v1/identity/sessions`, `ownerCache` строго привязан к origin,
  поведение 30-дневного сеанса); hosted `/logout` — полная очистка сеанса
  (`session-cleanup.cjs`: did-navigate / did-navigate-in-page, никогда из
  will-navigate); смена origin — commit-phase с полной очисткой предыдущего
  сервера.
- **B. DPAPI** — настоящие шифрование/расшифровка Windows в реальном профиле:
  сохранение черновика при живом сеансе; перезапуск EXE — черновик
  восстанавливается; выход — локальные черновики исчезают из UI; изоляция
  владельцев A/B (второй не читает черновики первого); недоступность DPAPI —
  честный отказ, не тихая деградация.
- **C. Reconnect при живом сервере** — обрыв сети: честный статус, черновик
  не теряется; возврат сети / перезапуск сервера — reconnect без повторного
  ввода, не подключается к чужому владельцу; потеря доступности API —
  понятные статусы вместо зависших кнопок; отмена/новый адрес побеждают
  запоздалые ответы.

## 2. Среда и сборка

- **Disposable VM/CI (GitHub-hosted Windows runner)** — все
  автоматизируемые сценарии; guard `ci/nsis-lifecycle.ps1` уже требует
  disposable-среду программно.
- **Ноутбук владельца** — только финальный настоящий пользовательский цикл:
  правило пакета «автоматические проверки не заменяют первую пользовательскую
  приёмку»; owner-PC отмечается отдельно, не по фикстурам.
- Сборка: `npm run pack:unsigned:win` — unsigned, updater OFF,
  `update-trust.json` c `publicKeyPem:null`, никаких signing-секретов.
  Повышение версии `package.json` — только отдельный интеграционный commit,
  согласованный с Codex (граница пакета).
- **Известное ограничение**: `gui-acceptance.cjs` жёстко требует
  loopback-фикстуру (`http://127.0.0.1:<port>`) — сценарии против живого
  сервера требуют параметризации origin или отдельного live-харнесса. Это
  код — отдельный срез после одобрения плана.

## 4. Что требует владельца (честно)

1. **Живой сервер** с развёрнутым API — выкладка сервера отдельно и не входит
   в этот срез; нужен origin для сценариев.
2. **Лицензия/учётные данные** для сценариев A1–A3, B3–B4 и финального цикла
   (реальные cookies владельца; никаких настоящих секретов в CI).
3. **Решение о секретах CI**: для VM-сценариев против живого сервера origin
   (и тестовая учётная запись, если решите её завести) добавляются как
   GitHub-секреты — создаёт владелец.
4. **Финальная приёмка на ноутбуке** — по чек-листу из этого плана, с
   изолированным тестовым профилем; предшествующие данные v0.11.x —
   по сценарию upgrade из `ACCEPTANCE_0.11.1.md`.

## 5. Порядок исполнения после одобрения

1. Срез «live-харнесс»: параметризация origin в `gui-acceptance.cjs` или
   отдельный сценарий живой приёмки (код + тесты, стандартный цикл PR).
2. VM-прогоны сценариев C1–C5/B1/B2/B5/A4 (без учётных данных владельца).
3. VM-прогоны с участием владельца (A1–A3, B3–B4) — по договорённости о
   времени/учётной записи.
4. Финальный пользовательский цикл владельцем; отчёт
   `desktop/windows/ACCEPTANCE_<версия>.md` с фактическими наблюдениями —
   только реальный результат, ничего не отмечается пройденным без прогона.

## 6. Границы (не нарушать)

Не переключать unsigned+updater OFF на компьютере владельца; никакие
signing-секреты; серверная выкладка, реальная модель и owner-PC отмечаются
отдельно; платные вызовы — только по явному решению владельца; видимые
изменения — через VISUAL_WAITLIST; Multi-Agent — последний раздел; Jarvis,
облачный ПК и обучение весов не запускаются.

## 7. Критерии готовности приёмки

Все строки матрицы раздела 3 с фактическим результатом (пройдено/отказ/наблюдение),
известные дефекты перечислены, отчёт версии подписан фактическими числами
(время/стоимость — только фактические), и первая пользовательская приёмка
владельца выполнена.
