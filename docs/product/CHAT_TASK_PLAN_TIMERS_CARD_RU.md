# Карточка раздела: задачи, план и таймеры в чатах

Подготовлено 15 ноября 2026 по
[правилам второго этапа](../product/STAGE_TWO_WORKFLOW_RU.md) («Карточка раздела»,
9 пунктов). **Статус функции: DEFERRED снят владельцем 15 ноября 2026 («все по порядку»)** —
точечное разрешение на реализацию панели над полем ввода получено. Исходный
статус и референсы сохранены ниже для истории решения.

## 1. Пользовательская задача и полезный результат

В многошаговой работе в чате владелец видит текущую цель, активный шаг и
сворачиваемый план со статусами; после завершения шага берётся следующий
доступный; перезагрузка восстанавливает прогресс без повторного запуска
завершённых шагов; время считается по событиям с разделением «модель /
инструменты / очередь / пауза / ожидание решения». Ожидаемый результат —
понятный прогресс и честное время без выдуманных метрик.

## 2. Текущее фактическое поведение Kosmora

| Есть                                                                                 | Где                                                                                                                                                                      |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| План с зависимостями, статусы шагов, прогресс, пауза/отмена/повтор, частичная выдача | `apps/web/src/app/work-manager-dag.tsx`, `workflow-panel.tsx`, `apps/api/src/work-dag-coordinator.ts` (проверено: 47 API-тестов + единый сквозной сценарий, 10 e2e)      |
| Восстановление состояния после перезагрузки                                          | durable Work DAG, черновики composer, `restored-run-state`                                                                                                               |
| События выполнения с отметками времени                                               | `run.started` (`timestamp`), `message.started`, `message.delta`, `message.completed`, `run.completed` в `general-chat-routes.ts` / `app.ts`; `tool.call` в Model Gateway |
| Идемпотентность и устойчивость к потере ответа                                       | `client_message_id`, `client_request_id`, CAS по версиям                                                                                                                 |
| Карточка уточняющего вопроса над полем ввода Koswork (смежный, уже закрытый пункт)   | `apps/web/src/app/clarification-card.tsx`                                                                                                                                |

**Чего нет:** панели «текущая цель / активный шаг / свёрнутый план» над полем
ввода **обычного чата**; таймеров по событиям; раздельного учёта времени модели,
инструментов, очереди и пауз. Существующий план относится к Koswork/проекту, а
не к произвольному чату. Дублировать его под вторым названием нельзя — правило
«не размножать одинаковый чат/план».

## 3. Решения конкурентов (проверено по источникам владельца)

В [записи идеи](../ideas/2026-11-14-chat-task-plan-and-timers.md) референс —
два скриншота DeepSeek Harness со свёрнутой/раскрытой панелью «Дела» и строкой
«Текущая цель». В [разборе демки от 14 ноября](../product/2026-11-14-owner-review.md)
отмечены: ChatGPT Work показывает прогресс и поддерживает корректировку задачи,
Claude Cowork описывает параллельную работу, Claude Code группирует сессии по
проектам. Это **наблюдения/референсы владельца**, а не проверенные нами текущие
характеристики конкурентов; самостоятельного исследования поведения сервисов в
этом проходе не проводилось. Не заявляем превосходство без сопоставимой проверки.

## 4. Зачем отдельный раздел вместо обычного чата или Koswork

Обычный чат даёт ответ, но не показывает промежуточные шаги и их время. Koswork
уже даёт план и файлы, но привязан к проекту/Work DAG и требует отдельного
входа. Смысл раздела — **лёгкий прогресс в самом чате** без переключения в Work.
Если владелец сочтёт это дублированием Koswork, раздел лучше не делать: правило
этапа прямо запрещает размножать одинаковый чат под разными названиями.

## 5. Предложение (не утверждено)

1. Использовать текущие события `run.started` / `message.delta` / `tool.call` /
   `run.completed` как единственный источник времени. Не показывать «время
   рассуждений», если провайдер его не отдаёт: показывать измеренное время
   запроса к модели и отдельно помечать неизмеряемое.
2. Не создавать второй планировщик и второй журнал состояний: переиспользовать
   существующие durable-состояния run/Work DAG и идемпотентность по
   `client_message_id`. Параллельная ветка `stage3/scheduling` уже вводит
   `scheduled_dispatches` (explicit tick, без фонового таймера) — её границы
   («без правок composer/поля ввода») нужно сохранить.
3. Панель — компактная, сворачиваемая, над полем ввода; в свёрнутом виде только
   счётчики по статусам. Без изменений сайдбара, логотипа, типографики и
   размеров иконок (`UI_RULES.md`).
4. Не вводить автоматический переход к следующему шагу в обычном чате без
   отдельного решения: сейчас «после завершения брать следующий доступный шаг»
   уже реализовано в Work DAG с явным подтверждением расхода; перенос этого в
   чат меняет поведение отправки и требует явного владельческого решения.

## 6. Необходимые внутренние механизмы и их связь с результатом

- Событийные отметки времени → честные таймеры без выдуманных чисел.
- Дurable-состояние run + CAS → восстановление после перезагрузки без повторного
  запуска завершённых шагов.
- Разделение `model` / `tool` / `queue` / `pause` / `await_owner` по реальным
  событиям → понятные паузы и ожидание решения.
- Существующий механизм подтверждений/step-up → никаких новых прав.

## 7. Нормальный сценарий, ошибки, отмена, повтор, восстановление

Сценарий из записи идеи: две зависимые задачи → первая завершается → вторая
стартует автоматически → после перезагрузки видны обе и их фактическое время.
Ошибки: таймаут/отказ провайдера, потеря ответа, отмена владельцем, пауза,
неизвестный исход отправленного запроса (повтор остаётся явным), недоступное
время рассуждения. Ограничения: показывать только измеренное; не считать время
закрытой вкладки; не запускать модель скрытно.

## 8. Проверяемые критерии готовности

- После перезагрузки цель, план и статусы восстановлены, завершённые шаги не
  повторяются; нет лишних запросов модели.
- Таймеры совпадают с разницей отметок событий; пауза/очередь/ожидание решения
  не сливаются с «работой модели».
- На одинаковых задачах время до первого токена и полного ответа измеряется
  фактически, качество не ухудшается.
- Никаких выдуманных метрик, прогресса, расходов или прав (правило 24 референсов).

## 9. Решение владельца и реализованный объём

**Решение владельца 15 ноября 2026:** «все по порядку» — DEFERRED снят,
реализовать все открытые пункты по очереди. По этому разделу принято:

1. Панель над полем ввода чата разрешена (точечный запрос на изменение
   оболочки).
2. Раздел сделан как лёгкий прогресс в чате, а не второй Work DAG: состояние
   хранится в scoped `localStorage`, план приходит через событие текущей задачи.
3. Автопереход к следующему доступному шагу реализован в чистом состоянии плана
   (`completeStep`), без скрытого запуска модели: переходы видимы владельцу и
   восстанавливаются после перезагрузки.
4. Таймеры раздельные (`model/tool/queue/pause/await_owner`), но показывают
   только **измеренные** интервалы между реальными событиями; неизмеренное
   время обозначено «—», «время рассуждений» не выдумывается.

Реализация: `apps/web/src/app/chat-task-plan.ts` (чистое состояние),
`chat-task-plan-panel.tsx` + модуль CSS, `use-chat-task-plan.ts` (durable
состояние + подписка на события), `page.tsx` (рендер панели и emit из
существующих SSE-обработчиков `run.started/message.delta/run.completed/
run.failed/run.cancelled`), 6 unit-тестов и 5 e2e-сценариев. Второго scheduler
и фонового таймера нет; границы ветки `stage3/scheduling-clean` соблюдены —
composer и поле ввода не переписывались, только добавлена панель над ними.

## Границы прохода

Живая модель, VPS, ноутбук владельца, платные вызовы и внешние публикации не
участвовали; прогоны локальные (production webServer, фикстуры событий).
PR/merge/deploy от исполнителя нет. Оставшийся продуктовый шаг — подключить
источник плана к конкретному ответу модели (формат события); панель, прогресс,
восстановление и честные таймеры готовы.
