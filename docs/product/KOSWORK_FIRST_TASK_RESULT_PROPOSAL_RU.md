## Фактическая развилка

В продукте две разные поверхности результата:

| Поверхность                                     | Принятие результата владельцем                                              |
| ----------------------------------------------- | --------------------------------------------------------------------------- |
| Windows-цикл Koswork (`work-experience.cjs`)    | **есть**: `acceptedAt`, `outcome: "owner_accepted"`, ссылка с ревизией      |
| API/Web Manager Work (`manager-work-routes.ts`) | **нет**: только `approve` плана, затем `publish`/`done` и скачивание файлов |

`ManagerWork` (`packages/contracts/src/manager-work.ts`) не содержит полей
принятия результата. `control` принимает только `pause | resume | approve | cancel`,
где `approve` относится к плану сложной задачи, а не к готовому результату.

То есть на API-пути «первая полная задача» завершается статусом `completed`,
но отдельного действия «владелец принял результат» в истории нет. Это расхождение
с формулировкой раздела («принятие результата — отдельное действие»), а не
отсутствие самой задачи.

## Предлагаемый объём (на согласование)

Добавить принятие результата в существующий Manager Work, без нового хранилища:

1. `POST /api/v1/projects/:projectId/work/:id/result/accept`
   тело `{ expected_version }`.
2. Поля в `ManagerWork`: `result_accepted_at: string | null`,
   `result_accepted_by: string | null`. Миграция — одна, аддитивная, на
   существующей таблице работ (номер согласует Codex при объединении).
3. Правила:
   - принимать можно только `status = completed` и неизменяемый результат уже
     опубликован; иначе `409 WORK_RESULT_NOT_READY`;
   - запись принимается один раз: повтор возвращает текущее состояние
     идемпотентно, но не переписывает автора и время;
   - `expected_version` обязателен: устаревшая версия → `409 STALE_WORK`;
   - активный privacy fence владельца → `409 OWNER_DATA_FENCED`;
   - принятие не меняет файлы, не публикует заново и не отправляет ничего наружу.
4. Принятие попадает в существующий журнал `events` и экспорт/удаление владельца
   через уже зарегистрированный privacy-адаптер (отдельный адаптер не нужен).
5. В интерфейсе — только строка состояния «Результат принят владельцем <время>»
   и кнопка принятия в существующем экране работы; чат, сайдбар, логотип и
   палитра не меняются.

### Критерии готовности

- принять можно только завершённый результат; отказ доходит как явный код, а не
  молчаливое «ок»;
- повторное принятие не создаёт вторую запись и не меняет время;
- принятие видно в `GET .../work/:id`, в истории событий и в экспорте владельца;
- удаление владельцем уносит и признак принятия (без осиротевших ссылок);
- существующие 30+ сценариев `manager-work` не меняют поведения, кроме нового поля.

### Что не входит

- Не трогаем Windows-цикл и его `acceptedAt` — там принятие уже есть.
- Не добавляем «отклонить с замечаниями», повторную доработку по замечаниям и
  версионирование принятия: это отдельный объём.
- Не меняем тарифы, квоты, провайдера HY4 и модель прав.
- Не выполняем живую приёмку на устройстве владельца: она требует
  восстановленного VPS и установленного клиента.

## Что остаётся заблокированным

Контрольная задача владельца (поиск → Word-отчёт с источниками → сохранение на
рабочем столе) — это живая приёмка, а не код. Для неё нужны:

1. восстановленный VPS с обновлённым API;
2. установленный кандидат 0.16.0 на вашем ноутбуке;
3. ваше разрешение на управление приложением Word и рабочей папкой в этом сеансе.

Без этого я могу проверить только локальный сценарий с тестовыми адаптерами и
не имею права выдавать его за живую приёмку.
