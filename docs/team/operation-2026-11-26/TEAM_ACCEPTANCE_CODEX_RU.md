## Блокирующие находки

### R1 — пропуск миграций после Stars

Воспроизведено реальным Drizzle migrator и Node SQLite на синтетической базе.

1. Применить журнал текущего main, включая 0075_stars_missions.
2. Применить полный журнал #684 с 0072_project_correction_rules,
   0073_project_sources и 0074_project_members.
3. migrate возвращает успех, но три новые таблицы отсутствуют.

Последняя временная метка до и после — 1795608000003.
Drizzle выбирает миграции новее максимального created_at, поэтому добавление
старых записей в журнал не создаёт таблицы на уже обновлённой базе.

Результат локального воспроизведения

| project_correction_rules | отсутствует      |
| project_source_settings  | отсутствует      |
| project_members          | отсутствует      |

Дополнительное пересечение — #684 и #686 независимо используют номер 0074
для project_members и work_execution_cycles. Простой merge журнала недостаточен.

Владелец исправления — GPT-интегратор.
Нужен безопасный переход как с уже применённого main/Stars, так и с ранее
развёрнутого кандидата. Не менять задним числом применённые миграции и не
полагаться только на пустую базу. Проверить сохранность старых данных и
повторный запуск. Сначала сверить, развёртывалась ли версия 0075 на живом стенде.

### R2 — участник проекта принят, но данные источников недоступны

Воспроизведено на реальных классах и контрактах #684 с минимальной SQLite-схемой.

1. Owner A создаёт проект и приглашает B как editor.
2. B принимает приглашение.
3. membership.canAccess(project, B) возвращает true.
4. ProjectSourceStore.exclusions(project, B) бросает
   PROJECT_NOT_FOUND со статусом 404.

Route gate разрешает участника, но вложенное хранилище по-прежнему требует
projects.owner_id = identity.owner_id. Тест поставки проверяет canAccess,
но не проверяет успешный GET материалов после вступления.

Владелец — OpenCode 1.
Нужны actor-aware чтения с отдельной идентичностью владельца данных,
реальный API-тест чтения B, запрет C, отказ B после revoke и сохранение
разделения личной памяти. Не подменять глобально identity.owner_id.
Чаты, поиск, скачивания и действия с ролями ещё не подключены к membership,
что автор поставки также явно указал в описании PR.

### R3 — Gemini заменяет результат имитацией редактирования

В editJob(image) вне зависимости от исходного изображения создаётся новый
SVG с текстовым журналом правок. Изменение объекта, фона и композиции в
исходном изображении не выполняется. Ветка voice/audio/music/sfx создаёт
синусоидальный WAV. Это не озвучивание текста и не полноценная генерация музыки.
regenerateVideoScene сохраняет SVG-раскадровку вместо нового видеоклипа.

Самостоятельные заглушки пригодны для фикстур и явно обозначенного storyboard.
Считать их завершёнными генераторами или правками исходных медиа нельзя.

Патч также не применяется к main — отсутствуют
apps/api/src/studio/index.ts, studio-media-service.ts и studio-routes.ts.
Нужно переносить полезные части в текущие media-routes/runtime,
а не подключать параллельный неподтверждённый стек.

Владелец — Gemini.
Нужны фактические provider operations и capability flags, раздельные статусы
mock/storyboard/generated, сохранение исходных байтов и проверка реального
изменённого результата. Если провайдер не подключён, функция остаётся
непроверенной, а не объявляется готовой.

### R4 — Gemini передаёт provider key на произвольный URL результата

Локальное воспроизведение использует только внедрённый mock fetch и
DUMMY_REVIEW_KEY. Реальный ключ и сеть не использовались.

ExternalImageProviderAdapter.downloadArtifact принимает абсолютный artifactUrl
и всегда добавляет authorization Bearer с ключом провайдера.
Для https://untrusted-cdn.example/artifact.png mock получил тот же Bearer.

Владелец — Gemini.
Нужны явные правила для provider origin и подписанных CDN URL.
Не передавать provider authorization на посторонний origin. Ограничить
разрешённые адреса, переходы перенаправлений, размер и формат результата
через действующие сетевые средства проекта.

## Остальные незакрытые части

### GPT и Harness 1

#664 уже применяет поддерживаемое правило поставщиков в обычном пути Work.
#681 добавляет отдельный POST work-apply после выполнения DAG. Этот маршрут
выбирает DAG только по владельцу и ID, а правила — по проекту из URL, без связи
между ними. Возвращаемый отчёт не сохраняется как новый фактический Work-файл.
Тест real-work-rule-lifecycle выполняет один Work и затем вручную вызывает
work-apply три раза.

Сохранить полезные core/lifecycle дополнения. Для общего использования нужны
проверка project↔DAG и тест нового обычного запуска после подтверждения,
отключения и конфликта правил с сохранённым результатом и версией правил.
Карточки специализаций пока инертные. Их наличие не доказывает улучшение модели.

### OpenCode 2

Восемь тестов двух новых desktop-модулей независимо повторены, 8/8 прошли.
Recovery events включены в computer-session.
createTabOwnership встречается только в новом модуле, тестах и package.json.
Browser engine/shell его не вызывают, поэтому реальное владение вкладками и

Автор отдельно оставил голосовой ассистент на уровне исследования лицензий,
ссылаясь на локально согласованный с владельцем объём. Не считать голос закрытым
и не отменять более позднюю договорённость без уточнения у владельца.

Следующий срез — подключить ownership в реальные browser entrypoints и проверить
передачу человеку, разных агентов, освобождение/закрытие вкладки и очередь
реальных экранных действий. Граница ПК владельца и fixture остаётся явной.

### Harness 2

В ResearchCoordinator добавлено сохранение receipts вместе с ответом.
Новый тест вручную записывает answer/receipts через ResearchStore.update,
а не проходит через координатор и HTTP. Существующий workflow тестирует
координатор, но новый regression не гарантирует вызов receipts-ветки.

Нужен тест обычного Research run с проверкой receipts через GET после
перезапуска, неверной цитатой и исключением источника для следующей задачи.
Пользовательская видимость и память не приравниваются к наличию helper-функции.

### Harness 3 и Stars

Принятые #677/#683/#685 дают persistent state machine, API и карту.
bindStarsTeam вычисляет идентичность состава и читает instance IDs, но не
создаёт настоящие blueprints/composition и не запускает исполнителей.
Готовый режим команды должен пройти manager+2workers с реальными задачами,
зависимостями, проверкой и единым скачиваемым результатом.

#686 добавляет вторую таблицу cycle и восстановление с parts=[],
extraction=null, history=[], пустым result при result_ref.
result_ref сохраняет ID Work вместо ссылки на проверенный артефакт.
Этот дефект уже зафиксирован для #673 и не исправлен rebase.

Не вводить второй источник истины. Согласовать канонический путь с GPT,
использовать сохранённые входы/версию/историю и настоящий результат.
Не переносить статусы из клиентских событий как доказательство выполненной работы.
