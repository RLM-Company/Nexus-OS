## Реальное состояние пакета

Патч затрагивает шесть файлов. В текущем main отсутствуют три его базовых файла:

- apps/api/src/studio/index.ts
- apps/api/src/studio/studio-media-service.ts
- apps/api/src/studio/studio-routes.ts

Поэтому слепой git apply не является интеграцией. Новая поставка предполагает
другой исходный Studio-стек. Если контекст отдельного hunk отсутствует, восстанови
назначение изменения и реализуй его через действующие сервисы проекта.

В текущем кандидате уже есть media API, политика разрешений, состояние заданий,
проверка результатов и запрет URL-only артефактов. Сохрани более сильные проверки.

## Главные дефекты, которые нельзя перенести

1. editJob(image) создаёт SVG с текстом журнала правок вместо редактирования
   исходного изображения. Исходный результат пользователя подменяется.
2. voice/audio/music/sfx создают синусоидальный WAV. Это не озвучивание текста
   и не полноценная генерация музыки.
3. regenerateVideoScene создаёт SVG-раскадровку вместо нового видеоклипа.
4. downloadArtifact принимает абсолютный URL и отправляет на него Bearer
   с ключом провайдера. Codex воспроизвёл передачу dummy key стороннему origin.
5. Тест пакета использует собственный HTTP-стенд createStudioHttp. Его успех
   не доказывает работу текущего production API, интерфейса и авторизации.

SVG-схемы, тестовые сигналы и storyboard допустимы как явно обозначенные
отдельные результаты/фикстуры. Они не должны подменять настоящую генерацию.

## Что надо реализовать и связать

### 1. Инвентаризация и контракт возможностей

Сопоставь каждое изменение патча с текущим кодом. Зафиксируй disposition —
взять, адаптировать, уже есть, отклонить с причиной.

Для изображений, видео, речи, звуковых эффектов и Music проверь:

- фактический провайдер и реально доступные операции;
- входные параметры и поддержку референсов;
- генерацию, редактирование и отмену;
- получение результата;
- историю и восстановление;
- недоступные операции и честное сообщение пользователю.

Разделяй поддержку адаптером, корректность на фикстуре и живую проверку.
Наличие API-ключа само по себе не означает готовность провайдера.

### 2. Изображения и последовательное редактирование

Адаптируй историю версий, параметры и референсы к действующим заданиям.

Нужен путь — создание изображения → просмотр → правка → новый результат →
сравнение/возврат к предыдущему → скачивание → восстановление после перезапуска.

Операция редактирования должна использовать поддерживаемый provider flow
и исходное изображение. Сохраняй его исходные байты. Если доступна только
генерация нового изображения, называй операцию соответственно.

Не обещай сохранение остальных областей изображения без подтверждённой
поддержки и проверки. Отключай неподдерживаемую точечную правку.

### 3. Видео и сцены

Сохрани полезную модель сцен, принятие сцены, версии и историю.

Разделяй storyboard и настоящий видеорезультат. Замена сцены должна обращаться
к поддерживаемой операции и сохранять реальные артефакты. Принятые сцены
не должны исчезать при правке другой.

Если сервис поддерживает только генерацию целого клипа, реализуй этот путь
честно. Не выдавай обновление JSON или SVG за перегенерацию видео.

Проверь параметры, длительность, референсы, отмену, ошибку провайдера,
восстановление и воспроизводимый экспорт результата.

### 4. Речь, SFX и Music

Сделай явные назначения — озвучивание текста, звуковой эффект, музыка.

Текст для речи должен становиться речью. Параметры голоса/скорости и музыки
должны передаваться в реально поддерживаемые операции. Тестовый синусоидальный
сигнал оставь только фикстурой.

Свяжи результат с просмотром/прослушиванием, историей, скачиванием и отменой.
Для потоковой выдачи проверь реальную поддержку Range, если она заявлена.
Одного заголовка Accept-Ranges недостаточно для поддержки диапазонов.

Не расширяй этот пункт до отдельного голосового ассистента управления ПК —
это другой блок и его согласованные границы сохраняются.

### 5. Презентации и повторное использование

В пакете есть сценарий редактирования слайда и повторного экспорта.
Сверь его с действующим разделом презентаций.

Сохрани существующий генератор и формат. Если полезные проверки отсутствуют,
адаптируй сценарий — генерация → изменение выбранного слайда → экспорт →
проверка структуры PPTX и сохранности неизменённых слайдов.

Не добавляй параллельный Studio backend. Пользователь должен работать
в существующем разделе.

### 6. Общий lifecycle

Используй действующий механизм заданий:

- идентификатор операции и защита от повторного запуска;
- queued/running/completed/failed/cancelled;
- подтверждение и полномочия пользователя;
- восстановление после потери ответа и перезапуска;
- неизменяемые исходные версии;
- недопущение поздней перезаписи отменённого результата;
- разграничение владельцев и проектов.

Не вводи второй источник истины, собственную авторизацию по произвольному
заголовку или отдельную очередь без подтверждённой необходимости.

## Скачивание и безопасность

Сохрани текущий безопасный путь получения медиа. Пока URL-only ответы
отклоняются, не снимай эту защиту ради совместимости с пакетом.

Если выбранному провайдеру действительно требуется скачивание по URL,
адаптируй действующие сетевые средства проекта:

- provider authorization передаётся только разрешённому origin;
- подписанные CDN URL не получают чужой Bearer;
- redirects проверяются либо запрещаются;
- внутренние адреса и неожиданные схемы отклоняются;
- размер и время загрузки ограничены;
- MIME и фактический формат проверяются;
- секреты не попадают в историю, ошибки и логи;
- чужой пользователь не может скачать артефакт.

Добавь regression для стороннего URL и перенаправления. Используй фиктивный
ключ и внедрённый fetch, без настоящей утечки и внешнего запроса.

## Проверки и доказательства

После каждого среза выполняй целевые проверки. На финальном SHA нужен
полный CI общего кандидата. Старый зелёный CI 9b84317b после новых изменений
не доказывает готовность обновлённой версии.

Проверяй через production routes и текущий UI:

1. Создать результат.
2. Проверить содержимое/формат.
3. Изменить поддерживаемым способом.
4. Проверить фактическое изменение.
5. Сохранить исходную версию.
6. Скачать и повторно открыть.
7. Перезапустить процесс и восстановить историю.
8. Проверить отмену и потерю ответа.
9. Проверить другого владельца.
10. Проверить отказ при неподдерживаемой операции.

Тест существования файла, хеша или новой версии не доказывает, что картинка
изменена по заданию, WAV содержит речь, а файл является настоящим видео.

Для живых прогонов используй существующие разрешённые credentials из
окружения. Не отправляй секреты в чат. При отсутствии провайдера заверши
независимые части и явно перечисли оставшуюся живую проверку.

## Петля

Изучить hunk → сопоставить с production кодом → сохранить сильные проверки →
адаптировать функцию → проверить пользовательский путь → устранить дефект →
включить в общий кандидат → взять следующий срез.

Не заканчивай на inventory, документации или новом тестовом стенде.
Работай над действующими функциями. Не меняй глобальный дизайн, sidebar и logo.
