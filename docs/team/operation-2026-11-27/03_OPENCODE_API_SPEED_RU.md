## Продуктовая цель

Внешнее приложение подключается к Kosmora своим ключом, получает ответы,
потоки и результаты задач в пределах разрешённых возможностей.
Быстрый режим снижает измеренную задержку при контроле качества.

Это отдельный клиентский продукт поверх существующего runtime. Внутренний
owner API и подключение чужого provider key не равны готовому API Kosmora.

## Твоя зона

Новый apps/api/src/developer-api/ и профильные контракты/SDK/examples.
packages/model-gateway — текстовый routing, streaming, error handling,
профили скорости и измерения. Media adapters принадлежат Gemini.
Минимальная страница управления developer keys и панель экспериментов.
Тарифы/оплата/размер подписных квот не назначаются.

## Циклы API

1. Опиши устойчивую внешнюю границу. Не открывай напрямую все внутренние
   owner endpoints. Клиентский ключ связан с аккаунтом, scopes и отзывом;
   хранится проверяемое представление секрета, секрет показывается при выпуске.
2. Реализуй минимально полный chat API с потоковой выдачей, cancellation,
   корректными errors и usage. Совместимость с OpenAI объявляй только
   для реально поддержанного контракта/полей, с conformance-проверками.
3. Добавь асинхронные задачи и файлы с владельцем, idempotency, status polling
   и отменой. Stars/Koswork вызываются через интерфейсы их владельцев.
   Реальный повтор после потери ответа не создаёт вторую задачу.
4. Добавь события/webhooks: подписка, проверяемая подпись, retries,
   дедупликация и отзыв. Не допускай произвольного доступа к внутренней сети.
5. Подключи учёт использования к существующему ledger и корреляции запросов.
   Не выставляй пользовательские счета и новые бюджеты. Секреты и содержимое
   личных чатов не должны попадать в технические логи.
6. Подготовь настоящие примеры внешнего клиента и документацию API.
   Опиши версионирование, ошибки, поддержанные операции и ограничения.

## Циклы скорости

1. Измерь baseline на согласованных задачах: TTFT, полное время, ошибка,
   качество и usage. Разделяй очередь, подготовку, провайдера и инструменты.
2. Найди реальные накладные расходы: соединения, буферизацию SSE, дублирование
   контекста, ненужную последовательность, повторный lookup и serialization.
   Исправляй измеренный bottleneck без потери отмены и изоляции.
3. Реализуй маршрут fast/strong/parallel как опциональную функцию.
   Быстрые исполнители получают независимые части, сильный проверяет итог;
   повторяется проблемная часть. Маленькая задача не должна автоматически
   получать дорогой fan-out. Сложные запросы не должны незаметно ухудшаться.
4. Сделай панель сравнения режимов на одинаковом входе с сохранёнными
   параметрами, версией, временами и итогом качества. Синтетические замеры
   отделяй от живого provider run.
5. Кешируй только допустимые данные. Изоляция владельцев и версий обязательна.
   Изменение инструкции/инструментов/разрешений должно учитываться.
   Не кешируй результат внешнего действия как разрешение повторить его.

Изучи существующие router/gateway/SSE и английский relay. Не включай перевод
молча и не обещай увеличение скорости декодирования чужой модели. Публикуй
реальное улучшение end-to-end вместе с условиями и качеством.

## Приёмка

Внешний пример получает ключ, запускает stream, отменяет его, создаёт async
задачу, восстанавливается после обрыва, скачивает результат, получает webhook,
отзывает ключ. Чужой ключ и отозванный ключ получают отказ.
Рабочий публичный endpoint не должен давать административные полномочия.

Панель скорости воспроизводит baseline и оптимизированный маршрут.
Если live provider недоступен, заверши продукт/метрики/фикстуры и явно
оставь неподтверждённый эффект. Числа ускорения без замера не допускаются.

Не изменяй базовое поведение всех режимов без отдельного решения:
экспериментальный router включается явно. Продолжай до полного SDK→API→runtime
сценария и честного отчёта измерений.
