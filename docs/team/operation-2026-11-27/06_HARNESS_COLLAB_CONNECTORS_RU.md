## Продуктовая цель

Несколько людей работают в одном проекте/чате, видят разрешённые материалы,
авторство и задачи. Каждый может работать со своим агентом. Подключённые
сервисы дают реальные данные и разрешённые действия с отзывом доступа.

В #688 уже есть membership, проектные материалы и ограничения ролей.
Общий проект доступен по ссылке, но отсутствует в основном списке участника.
Начинай с этих реальных разрывов, а не со второго RBAC.

## Твоя зона

Project membership/access, shared-project presentation и history/search/download.
Connector runtime, каталог интеграций, OAuth/HTTP/MCP adapters и Drive.
Минимальные controls участников в проекте/чате. Не перестраивай весь sidebar.
Native browser/devices — OpenCode 1, agent hierarchy — Harness 1,
memory contents/selection — Harness 2, public API keys — OpenCode 3.

## Циклы совместной работы

1. Сделай полный путь invite → accept → увидеть проект в списке →
   открыть чаты/материалы → выполнить разрешённую операцию → leave/revoke.
   Приглашение не должно автоматически раскрывать данные до принятия.
2. Проверь доступы через каждый путь: list, GET, search, download, mutation,
   run, event stream и повторное использование ранее полученного ID.
   Viewer/editor/owner отличаются реальными возможностями.
3. Добавь авторство сообщений, поручений и изменений, ответственного
   и приёмку результата. Чужое действие не должно приписываться владельцу.
   Одновременные изменения имеют версию/конфликт, без тихой потери правок.
4. Подготовь совместный чат/проект с персональными агентами участников
   через интерфейс Harness 1. Реши границу личных и общих материалов
   совместно с Harness 2; не подменяй identity.owner_id глобально.
5. Отзыв доступа должен останавливать новые действия и обновления.
   Старый открытый экран не даёт продолжать скачивания/запись.
   Поведение уже запущенной общей задачи явно проверяется.

## Циклы интеграций

1. Приведи сервисы к общему lifecycle: connect → capabilities → источники →
   разрешённая операция → журнал → disconnect/revoke.
   Секреты принадлежат своему аккаунту, доступ команды выдаётся отдельно.
2. Доведи минимум четыре приоритетных сервиса целиком. Начни с Drive,
   GitHub и ещё двух из Calendar, почты, Docs/Sheets, Telegram или Slack,
   выбрав по фактическим существующим адаптерам и пользовательской пользе.
   Дальше продолжай каталог по готовым самостоятельным срезам.
3. GitHub-коннектор не должен ломать подтверждение Draft PR в Koscode.
   Drive использует существующий OAuth/хранилище. Для сообщений и календаря
   различай подготовку и отправку/изменение, сохраняя полномочия пользователя.
4. Доведи пользовательский HTTP/MCP-коннектор: проверка совместимости,
   аутентификация, обнаружение возможностей, тестовое чтение, типизированные
   ошибки, журнал и отзыв. Не обещай подключение любого приложения без API.
5. Свяжи capabilities с выбором инструмента в рабочих режимах. Один каталог
   названий не является готовой интеграцией. Права и необходимость подтверждения
   проверяются при выполнении, а не только при установке соединения.

## Приёмка

A приглашает B-editor и C-viewer, они видят общий проект в интерфейсе.
B добавляет сообщение/материал, C читает, но не меняет.
Агент B выполняет разрешённую задачу с общим источником; личные данные A
не раскрываются. Конкурирующая правка даёт понятный конфликт.
Отзыв B во время работы блокирует новые действия.

Для каждого сервиса пройди хотя бы одно чтение, поддерживаемое изменение
в тестовом контуре, восстановление после обрыва и отзыв доступа.
Проверяй второй аккаунт, stale token, scope mismatch и ошибку провайдера.
Живые OAuth/отправки отделяй от контролируемого transport.

Продолжай до целого совместного сценария и четырёх реально подключённых
production adapters. Недоступные внешние аккаунты фиксируй отдельно.
