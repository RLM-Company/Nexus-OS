## Цель

Во всех рабочих режимах видны текущая цель, шаги, ожидание, уточнение,
проверяемый прогресс и прошедшее время. Пользователь меняет поручение,
останавливает или продолжает работу без потери состояния.

## Владение

Существующие chat-task-plan, use-chat-task-plan, clarification-card
и work-manager-progress. Новый тематический слой task-observability допустим
как адаптер к текущим событиям. Scheduler — OC6; Stars state — Harness 1;
provider timings — OC3; media job state — Gemini; identity — Harness 3.
Не создавай второй универсальный task engine и не переписывай их состояния.

## Полная петля

1. Сверь уже подключённые планы/таймеры/карточки. Работай с реальными
   источниками событий и точными IDs/версиями, а не текстовыми эвристиками.
2. Доведи отображение текущей цели, готовых/активных/ожидающих шагов.
   Следующий разрешённый шаг выполняет runtime по зависимостям.
   Интерфейс не должен самостоятельно придумывать completed.
3. Различай очередь, модельный вызов, инструменты, проверку и паузу.
   При неизвестной фазе показывай неизвестность. Не отображай внутренние
   скрытые рассуждения модели — только наблюдаемые состояния и время.
4. Состояние восстанавливается с сервера после reload/reconnect.
   Не полагайся только на sessionStorage для общего долгого поручения.
5. Уточнение относится к конкретному шагу/версии: варианты, свой ответ,
   пропуск только необязательного вопроса, одно принятие после повтора.
6. Подключи stop/resume/retry и разрешённое изменение задачи с правильным
   отображением конфликтов, потери связи и позднего события.
7. Пройди обычную длинную беседу и рабочие режимы, где план реально есть:
   Koswork, Koscode, Stars и media jobs. Не рисуй фиктивный план для
   мгновенного ответа без задач.

Сдай действующие controls в существующей оболочке без общего редизайна.
Приёмка — длинное поручение, вопрос, пауза, reload, ответ, продолжение,
потеря сети, отмена и отсутствие позднего «успеха».
