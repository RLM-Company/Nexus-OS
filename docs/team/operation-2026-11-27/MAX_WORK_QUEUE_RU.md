# Усиленная очередь шести исполнителей — максимум полезной работы

Дополнение владельца от 27 ноября 2026 к SPRINT_48H. Применяется к OpenCode 1–3
и DeepSeek Harness 1–3. Gemini/Grok сохраняют свои зоны. Это очередь работы,
а не запуск чатов и не автоматическая настройка внешних приложений.

Прочитай свою личную инструкцию, 00_COMMON_RULES_RU.md и SPRINT_48H_RU.md.
Интегратор — второй разработчик GPT; Codex проверяет поставки.

## Не начинать отсчёт заново

Общий ориентир основного финиша остаётся 29 ноября около 15:57 МСК,
акционного резерва — около 18:57 МСК, с проверкой фактического срока провайдера.
Новое сообщение не добавляет ещё 48 часов каждому чату.
Никакого автоматического stop в приложениях этот документ не устанавливает.

## Режим непрерывного исполнения

1. Сначала исправления, возвращённые интегратором, и совместимость контрактов.
2. Затем незавершённый пользовательский путь приоритета A.
3. После его приёмки переходи к B, затем к C своей зоны.
4. Сдал PR — сохрани SHA/checkpoint и начинай следующий независимый срез.
   Не заканчивай на вопросе «что делать дальше».
5. Заблокирован одним провайдером/устройством/стыком — изолируй блокер,
   сохрани весь код и продолжай другой пункт своей зоны.
6. Отчёты, схемы и тесты сопровождают реализацию. Инертные карточки,
   пустые handlers и fixture-only сценарии не закрывают функцию.
7. Отдельно отмечай реализацию, контролируемую проверку и настоящий live.
8. Не добавляй новые функции за пределами своей зоны ради занятости.
   Когда все пункты реально пройдены, бери воспроизводимый дефект или
   интеграционную доработку своего блока, сохраняющую назначение продукта.
9. Последние восемь часов основного окна — завершение и регрессия.
   В резерве только исправления блокеров в пределах действия акции.

### Параллельная работа

Шесть главных исполнителей сохраняют ответственность за свои зоны.
Если конкретное приложение поддерживает дочерних исполнителей, используй
их для независимых модулей/сценариев с разными файлами и проверкой владельцем.

Параллелизм увеличивай по наблюдаемой пропускной способности провайдера
и устройства. Общий native input, файл, миграция и изменяемый ресурс имеют
одного владельца. Не создавай конкурирующие сессии, дублирующие одну задачу.
429/очередь не лечится бесконечным повтором такого же запроса.
Полные тестовые прогоны не запускай одновременно без необходимости.

Локальные проверки и исправление кода выполняются без модельного запроса,
когда это достаточно. Не генерируй токены ради заполнения акционного окна.

## OpenCode 1 — ПК, браузер, native runtime

### A — закончить основной исполнитель

- Рабочий путь: приложение → документ → сохранение → проверенный результат.
- Браузер: поиск/страница → разрешённая форма → файл → возврат в Koswork.
- Action lease, очередь native input, человеческий takeover и stop.
- Recovery по реальному наблюдению, отсутствие позднего ввода.
- Повторное подключение и продолжение сохранённой задачи без дублей.

### B — расширить реальную управляемость

- Несколько окон/приложений, смена фокуса, системный диалог, закрытый процесс.
- Разрешённые upload/download с проверкой конечного файла и путей.
- Устойчивые ссылки на элементы, свежие наблюдения и readback после действия.
- Работа с профилями браузера без утечек между аккаунтами/средами.
- Согласованный мост для Grok и Games: typed actions, events, cancel и capabilities.
- Проверка нескольких агентов на одном устройстве с очередью ресурсов.

### C — довести desktop продукт

- Вход, сохранение сессии, reconnect и понятные причины отказа.
- Восстановление после перезапуска приложения/исполнителя.
- Подготовка рабочего каталога, центр результатов/скачиваний и разрешения.
- Переносимый executor-target контракт с Harness 1.
- Установочный пакет и runnable native acceptance для владельца.
- Исправления UX внутри native поверхностей, без глобального редизайна.

Итог — управляемый компьютер с проверяемыми действиями, доступный рабочим
режимам через общий runtime. Новый браузерный движок с нуля не писать.

## OpenCode 2 — Games, 3D и Sites

### A — полный рабочий проект

- Поддерживаемая 3D-сцена, реальные игровые состояния и изменение механики.
- Исходники, ресурсы, версия и предпросмотр соответствуют друг другу.
- Игра и сайт к ней создаются/редактируются в существующей Kosmora.
- Экспорт → распаковка → повторное открытие без потери ресурсов.

### B — развить редактор и итерации

- Объекты/иерархия сцены, трансформации, камера, свет и материалы.
- Поддержанный импорт/замена модели с честными границами формата.
- Выбор объекта и адресная правка, история/undo и восстановление.
- Ошибка → точный файл/версия → правка → повторный запуск.
- Согласованный агентный интерфейс редактирования структуры проекта.
- Проверка stop, повреждённого ресурса, unsaved changes и перезагрузки.

### C — закончить Sites и передачу результата

- Связанные страницы/ресурсы в поддерживаемом объёме проекта.
- Изменение выбранного блока без потери остальных материалов.
- Проверка предпросмотра на нескольких размерах экрана.
- Работоспособный экспорт и понятная граница preview/published.
- При готовом device bridge — открытие проекта в поддержанном нативном инструменте.
- Документированный воспроизводимый пример проекта для приёмки.

Не ограничиваться static viewer. Не объявлять локальный preview настоящей
публикацией, а набор примитивов — генератором произвольных 3D-моделей.

## OpenCode 3 — публичный API и скорость

### A — внешний рабочий клиент

- Scoped ключи, безопасное хранение, отзыв и аудит.
- Настоящий text/stream запрос с отменой, ошибками и usage.
- Один полноценный async job, восстановление, скачиваемый результат.
- Проверка другого владельца и отсутствия доступа к owner API.

### B — продукт для разработчика

- Поддержанные endpoints задач/файлов и versioned contract.
- События/webhooks с подписью, повторами, дедупликацией и отзывом.
- SDK/CLI-пример, который проходит весь путь обычного клиента.
- Страница ключей/использования и документация ошибок/совместимости.
- Подключение готовых Stars/Koswork операций через реальные адаптеры.
- Учёт расхода без самостоятельного назначения тарифов и квот.

### C — ускорение с доказательствами

- Панель baseline/fast, точные TTFT и end-to-end времена.
- Исправление буферизации, ненужной последовательности и подготовки.
- Явный fast/strong/parallel маршрут для подходящих задач.
- Частичный retry и проверка качества на новых входах.
- Изолированный кеш с версией контекста/инструментов/разрешений.
- Подтверждённые улучшения; отрицательный результат эксперимента тоже сохраняется.

Не обещать скорость декодирования чужого сервера и не менять все режимы
на слабую модель без видимого выбора. Медиаадаптеры остаются у Gemini.

## DeepSeek Harness 1 — флагман Stars

### A — настоящая команда нескольких бизнесов

- Постоянная иерархия: главный, два управляющих, по два исполнителя.
- Два раздельных проекта, распределение задач и разрешённых ресурсов.
- WorkDAG-зависимости, проверка старшим и общий скачиваемый результат.
- Замена исполнителя с сохранением незавершённого поручения.
- Перезапуск и восстановление без ручного выставления completed.

### B — управление и самостоятельность

- Назначение/изменение ролей уполномоченным менеджером.
- Уточнение ТЗ, критерии результата, приоритет и арбитраж конфликта поручений.
- Сообщения агентам и между агентами с проверяемой принадлежностью к команде.
- Личный/общий контекст через Harness 2 и права людей через Harness 3.
- Инициативные предложения отдельно от разрешения внешнего действия.
- Фоновые event/time triggers с ожиданием без постоянной генерации.

### C — окружения и рабочая карта

- Изолированный remote runner и выбор local/remote target.
- Lease/heartbeat, cancel, checkpoint и перенос результатов между средами.
- Карта показывает настоящий состав, связи, задачи и состояния.
- Провалы управляющего/исполнителя, отзыв доступа и поздний результат.
- Поддержанные hooks для API и встречи Grok.
- Полный сценарий с trace, историей, проверкой и человеком, принимающим итог.

Не писать второй scheduler; не подменять remote environment тестовой
фикстурой в описании готовности. Живой VPS не менять автоматически.

## DeepSeek Harness 2 — память, Skills, профессиональные функции

### A — реальная долговременная работа

- Продолжение длинной задачи после сжатия и перезапуска.
- Исправление факта/решения, источник и версия.
- Исключение и удаление производных данных без возвращения через кеш/summary.
- Разделение личного, проектного, командного контекста.
- Обычный runtime использует отбор и квитанцию, а не отдельный helper.

### B — работающие навыки и первые 12 сценариев

- Запускаемые версии Skills, выбор, правка, конфликт, отключение и rollback.
- Применение к новым данным с проверенным результатом.
- Поддержанное сохранение пользовательского стиля.
- Минимум 12 законченных бизнес-сценариев минимум в четырёх специализациях.
- Документный анализ, закупки, расчёт/отчёт и текстовые материалы.
- Не выдавать повтор уже готовых BIZ-013/BIZ-040 за новую реализацию.

### C — следующая партия в той же системе

После прохождения качества первой партии расширяй поддержанные сценарии
к 24 из согласованного каталога. Это последовательная очередь, а не обещание
реализовать любые 24 функции к одной дате.

Добавляй совместимые процедуры, доступные реальные инструменты, пользовательские
шаблоны и повторное применение. Сохраняй единый механизм Skills вместо копий
исполнителя для каждой профессии. Сравни качество на новых заданиях.

Не переходить к обучению весов модели и не выдавать систему правил за него.
Точный весь исходник и результаты важнее количества названных специализаций.

## DeepSeek Harness 3 — совместная работа и сервисы

### A — целый совместный проект

- Invite/accept/list/open с реальными данными и принятием приглашения.
- Чаты/материалы/история/поиск/скачивание и операции по роли.
- Авторство и ответственный, конкурентная правка без потери изменений.
- Персональные агенты участников через Stars.
- Отзыв доступа во время работы с проверкой следующих операций.

### B — четыре полных коннектора

- Drive и GitHub через существующие безопасные пути.
- Ещё два приоритетных сервиса по личной инструкции и имеющемуся коду.
- Connect/capabilities/read/action/journal/disconnect/revoke.
- Повтор после потери ответа без дубля и scope mismatch.
- Настоящие adapters в production, отдельные пометки mock/live.

### C — расширение каталога без фиктивных интеграций

После четырёх проверенных lifecycle продолжай к следующей группе,
ориентир — до восьми реально поддержанных сервисов при доступных API.
Кандидаты — Calendar, почта, Docs/Sheets, Telegram, Slack и Notion,
если это соответствует существующему плану и лицензиям/интерфейсам.

Доведи пользовательский HTTP/MCP connector и общие capabilities.
Не заменяй реализацию сервисов карточками каталога.
Не отправляй реальные сообщения третьим лицам без назначенного действия.
Изменение косcode GitHub-пути согласуй с его существующей приёмкой.

## Условия перехода между A, B, C

Следующая партия не должна маскировать поломку предыдущей.
Нужны подключённый путь, наблюдаемый результат, сохранение, права,
отмена/ошибка и воспроизводимая проверка. Отсутствующий внешний аккаунт
не закрывает живой этап, но не мешает реализовывать остальные части.

Завершённый срез сдаётся немедленно; checkpoint не реже интервала спринта.
Интегратор принимает последовательно и возвращает регрессии конкретному
владельцу. Все новые миграции сводятся в одну проверенную последовательность.

## Пакет сдачи

Полный исходник + base/head SHA + PR/доступный raw patch + сценарий пользователя +
команды и результаты + незакрытый live + следующий пункт очереди.

После ответа «готово» без этих материалов интегратор не должен искать
несуществующую ветку или восстанавливать код из рекламного отчёта.
