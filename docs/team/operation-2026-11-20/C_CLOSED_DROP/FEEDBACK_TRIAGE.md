# Схема разбора обратной связи первой группы

Вход: заполненный [шаблон ошибки](ERROR_REPORT_TEMPLATE.md) или простое
сообщение кандидата. Выход: воспроизводимый дефект с владельцем, PR и
результатом повторной проверки — либо честный отказ с причиной.

## Поток

```
Новое → Нужны данные → Воспроизведение → Классификация → Владелец
      → Исправление (PR) → Повторная проверка → Закрыто / Отклонено
```

| Состояние           | Кто ведёт          | Условие перехода                                                                                                                    |
| ------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Новое               | Ведущий дропа      | Есть ID, версия, шаг, ожидалось/фактически                                                                                          |
| Нужны данные        | Ведущий → кандидат | Запрошен недостающий вопрос/лог; время ожидания не фиксируется выдуманным SLA                                                       |
| Воспроизведение     | Ведущий            | Есть минимальные синтетические данные и сценарий из [DEMO_DATA](DEMO_DATA/README.md)                                                |
| Классификация       | Ведущий + владелец | Присвоен приоритет и владелец раздела                                                                                               |
| Владелец            | Владелец раздела   | Подтверждён объём исправления; новый функционал отдельно согласуется по [правилам этапа](../../../product/STAGE_TWO_WORKFLOW_RU.md) |
| Исправление (PR)    | Владелец раздела   | Есть PR с тестом/фикстурой, без merge до проверки совместимости                                                                     |
| Повторная проверка  | Ведущий            | Прогнан тот же сценарий на зафиксированной версии после исправления                                                                 |
| Закрыто / Отклонено | Владелец           | Результат повторной проверки записан; при отказе — причина и ссылка                                                                 |

## Правила

1. **Дубликат.** Сначала ищем совпадение по (шаг сценария + версия +
   ожидалось/фактически). Если найден — связываем с существующим ID, а не
   открываем копию.
2. **Минимум для передачи.** Без воспроизведения дефект не передаётся в
   разработку. Минимальный набор — те же три артефакта, что в потоке E:
   синтетические входные данные, сценарий, ожидаемое поведение.
3. **Приоритет.** Фиксируется владельцем; в таблице не выдумываются сроки.
   Критический — утрата данных, приватности, безопасности или полная
   недоступность основного сценария. Остальное — по влиянию на сценарий.
4. **Границы.** Отказ на неподдерживаемое действие, отсутствие живого
   провайдера и расхождение с конкурентом без проверки — не дефект.
5. **Честность статуса.** «Готово к интеграции» — потолок исполнителя.
   Merge, VPS и живая приёмка остаются за владельцем/Codex и отдельно
   фиксируются.
6. **Обратная связь кандидату.** Каждому ID даётся один из ответов:
   воспроизведён + PR, не воспроизведён + что пробовали, ожидаемое поведение,
   принято решение владельца.

## Куда передавать

Владелец раздела определяется по [карте владельцев](../../operation-2026-11-10/README.md):
чат/Work/контракты — Codex, браузер — Gemini, память/контекст — DeepSeek,
навыки/стиль — Claude, код-агент — разработчик, Windows — OpenCode.
Связка «сообщение → дефект → PR → повторная проверка» ведётся в потоке
[E](../E_DEFECT_REPRO/README.md).
