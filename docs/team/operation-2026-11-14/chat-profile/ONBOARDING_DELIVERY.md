## Проблема (воспроизведено)

PR #600 добавил имя/род в **профиль** (`/personal-settings`) и приветствие, но
**первый вход** оставался без точки ввода: новый владелец видел «Чем могу
помочь?» без имени и без возможности задать род до первого диалога. Сценария
«первый вход → сохранение → перезагрузка → первый диалог» не было.

## Реализация

1. **`profile-onboarding.tsx`** — first-run блок «Давайте познакомимся»
   **внутри hero** (не модальный оверлей, ничего не перекрывает): имя,
   «Обращение к вам» (мужской/женский/нейтральный), «Род ассистента»
   (нейтральный/мужской/женский). «Сохранить и начать» делает
   `PUT /api/v1/personal-settings` с полным CAS-телом; «Пропустить» сохраняет
   серверные defaults (мужской род обращения, нейтральный ассистент) и ставит
   локальную метку `kosmora:profile-onboarding.v1 = done`.
   Блок рендерится только на стартовом экране (нет активного чата/проекта).
2. **`profile-onboarding-core.ts`** — чистая логика: `shouldShowOnboarding()`
   (показывать, пока имя пусто и метка не стоит; **версию настроек не
   проверяем**, т.к. другие настройки могли поднять её раньше) и
   `onboardingPayload()` (все обязательные поля + 3 поля профиля,
   `expected_version`, trim имени).
3. **`page.tsx`** — `<ProfileOnboarding onSaved={setDisplayName} />` в корне;
   имя сразу появляется в приветствии («Анна, рад вас видеть.»), а после
   перезагрузки берётся с сервера существующим запросом `reloadShellData`.
4. **`profile-onboarding.module.css`** — локальные стили модалки, без изменений
   `globals.css`, сайдбара и компоновки чата.
5. **Поле ввода, настройки профиля и диктовка OpenCode не менялись.**

### E2E (в CI на production web build)

`apps/web/e2e/profile-onboarding.spec.ts`:

1. **«Первый вход → сохранение → перезагрузка → первый диалог»**: модалка
   видна → «Анна» + feminine/feminine → сохранение → имя в приветствии →
   `reload` → онбординг не повторяется → настройки на сервере ( version > 0,
   имя и оба рода ) → отправка «Кто ты?» в обычный чат и появление заголовка.
2. **«Пропустить»**: модалка → «Пропустить» → после `reload` не появляется →
   на сервере остались `'' / masculine / neutral`, PUT не было.

Настройки в e2e изолированы через `page.route("**/api/v1/personal-settings")`,
поэтому тесты **не зависят от порядка** и от общей БД фикстурного сервера
(другие спеки тоже пишут в personal-settings и поднимают version).

Локально e2e не запустился: Playwright `webServer` на Windows не поднимается
(`--require ../../scripts/windows-node-user.cjs` внутри `pnpm --dir ../api`),
а порты 3000/3100 в момент прогона были свободны. Это **ограничение среды**,
не пройденный живой прогон; CI на Linux поднимает оба webServer штатно и
покроет оба сценария. Временная правка `playwright.config.ts` для
`reuseExistingServer` была откачена — конфиг в PR не изменён.

## Как обновляются существующие аккаунты

- Изменений схемы и миграций **нет**: используются поля `display_name`,
  `user_gender`, `assistant_gender` из #600, уже в `main`.
- Онбординг появляется только при **пустом имени**. Аккаунты, уже указавшие
  имя, его не увидят. Аккаунты без имени увидят один раз; «Пропустить» больше
  не предложится (метка в localStorage), при этом серверные defaults не меняются.
- Метка локальная: на другом устройстве онбординг предложится снова, пока имя
  не будет сохранено на сервере. Это ожидаемо и не требует миграции данных.

## Найденный сбой и исправление (цикл)

Первый прогон CI (`43710020854`) показал **реальную регрессию**: модальный
`backdrop` (`position: fixed`) перехватывал клики в чужих e2e-спеках —
`artifact-context.spec.ts` и другие падали с
`locator.click: <div class="...backdrop"> intercepts pointer events`.
Job был отменён по 30-минутному лимиту, но причина в логе читается однозначно.

Исправлено содержательно: оверлей заменён на **встроенный блок в hero**
(обычный `section[role="region"]`, без `position: fixed` и без перекрытия),
рендер ограничен стартовым экраном. E2E-селекторы обновлены на `role="region"`.
Это сохраняет сценарий первого входа и не ломает остальные 500+ браузерных
сценариев.
