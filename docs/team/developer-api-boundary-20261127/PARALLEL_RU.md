# Исправление параллельного исполнения API

База: исправление доступа PR #699, SHA
`849457ae64f5250b635fdcc0d104cdb702c91f39` (поставка исходного API —
`48862d7809e306ada8ac40776c53be02cf434a3c`, PR #694).

## Фактические изменения

- В исходной реализации части вызывались последовательно через await внутри for.
  Теперь работает пул с максимум четырьмя одновременными вызовами. Очерёдность
  результата определяется исходными частями, а не временем окончания.
  Четыре — ограничение одновременной нагрузки; количество частей не обрезается.
- Отмена проверяется до первого вызова, перед следующей частью и после выполнения.
  Ошибка одной части отменяет остальных исполнителей; неполный результат не уходит
  на проверку. Слушатель родительского сигнала освобождается.
- HTTP-обвязка передаёт AbortSignal каждому вызову. Разрыв клиентского соединения
  отменяет активные части. Это проверено локальным TCP-запросом, не только inject.
- Системные инструкции и предыдущая переписка сохраняются. На части разбивается
  только последнее сообщение пользователя; инструкции и история не становятся
  отдельными задачами.
- Каждая часть, проверка и повтор получают собственный request/idempotency ID.
  В учёте расхода дочерний вызов связан с исходным клиентским ID через run_id.
- Проверка видит метки частей и исходное задание. При исправлении передаются
  исходное задание части, предыдущий ответ и замечания. После ремонта результат
  проверяется повторно; незнакомый ответ проверяющего не превращается в PASS.

## Доказательства и границы

Локальные API-тесты: 28/28. Включены проверка реальной одновременности через
управляемую блокировку, ограничение числа активных вызовов, отмена соседних задач,
повторная проверка после ремонта, сохранение контекста, разные дочерние ID и
отмена через разрыв HTTP-соединения. Тесты хранилища из предыдущего прогона: 3/3.
API typecheck, целевой ESLint, Prettier и git diff --check прошли.

Все модельные вызовы тестовые. Замеров живого провайдера и доказанного ускорения
его токенов/сек здесь нет. Все вызовы пока используют существующий gateway:
отдельное назначение быстрой модели исполнителям и сильной проверяющему
этот патч не реализует. Поиск независимых подзадач не интеллектуальный:
режим включается явно, а части задаются строками последнего запроса. Для связного
текста следует использовать обычный режим. Полноценный планировщик — отдельная
согласованная функция.

Схему базы, пользовательский интерфейс и VPS этот патч не меняет.
Для сведения нужна цепочка #694 → #699 → эта ветка; итоговый кандидат должен
пройти полный CI и отдельные живые проверки.
