# Цикл исполнения Koswork: поставка 2 (продолжение)

База: main `57820acd3757cee05ef326a8e94dd0381a044b4d` (после merger'а #666).
Ветка: `codex/supplier-cycle-2`.

## Сценарии, доведённые в этой поставке

1. **Промежуточная ошибка** — `error` сохраняет принятые части и извлечение;
   после новых указаний задача возвращается к расчёту.
2. **Новые указания пользователя** — сохраняются в порядке поступления,
   сбрасывают ошибку, не удаляют принятые части.
3. **Пауза/продолжение** — пауза сохраняет вопрос и извлечение, resume
   восстанавливает предыдущую стадию (включая ожидание ответа).
4. **Отмена** — терминальное состояние, но принятый результат остаётся
   доступен для скачивания.
5. **Версионность** — событие с устаревшим `expected_version` отклоняется
   `SupplierCycleConflict`, что защищает от гонки старых команд управления.

## Реализация

`packages/core/src/supplier-cycle-continuation.ts` — чистый state machine:

- не читает файлы, не вызывает модель, сеть или БД;
- не меняет общие контракты `ManagerWork` и не трогает файлы PR #661/#662;
- использует `extractSupplierInput()` из поставки 1 как источник пропусков;
- результат расчёта сохраняется как marker (csv/markdown остаются в file layer).

## Стыковка

Для полного сквозного прогона через обычный Koswork интегратору нужно
подключить state machine к существующей точке входа (PR #661) и реализовать
сохранение вопроса и ответа в `ManagerWork`. Это общий контракт, поэтому не менялось здесь:
запрос на согласование оставлен в PR #661, ответа на момент поставки нет.

## Ограничение

Поставка завершает чистый слой цикла. Живой прогон с реальными файлами и
открытым PR #661 не выполнен: без изменения API/UI нельзя доказать сквозной
результат только через пользовательский вход. Это следующий шаг после
согласования контракта с интегратором.
