Роли распределены по границам модулей, а не по недоказанному превосходству моделей.

## Как запускать команду

1. Передать каждому его MD-файл целиком и адрес репозитория. Для второго разработчика
   сначала дать Write или работу через fork/PR. Пароли, .env и production SQLite не передавать.
2. Каждый фиксирует BASE_SHA, создаёт свою ветку от актуального main, читает действующий
   путь модуля и приступает к коду. База этого плана — main `338536ee5946f96dcd18768143cc41af998c476a`.
   Старые Gemini ZIP, draft/kosmora-blocks и найденные экспериментальные каталоги не
   становятся исходной базой без сравнения с актуальным main.
3. Извлечь первый работающий вертикальный срез своего блока, затем завершить остальные
   пункты. Обзор текущего кода нужен, но не заменяет поставку. В ответе обязательно
   commit/PR либо архив с реальными исходниками и patch.
4. Codex принимает интеграционные commits, регистрирует контракты/маршруты, разрешает
   коллизии миграций и ведёт [BOARD.md](BOARD.md). Остальные не сливают свои ветки
   самостоятельно и не выкатывают их на сервер параллельно.
5. Перед общей приёмкой синхронизировать ветки с main, объединить модульные поставки,
   пройти сквозные сценарии на одном комплекте версий. Живые проверки с аккаунтами/
   устройством — отдельный явно разрешённый этап; фикстуры не выдавать за него.

## Состояние базы и границы

В исходниках уже есть браузер/CDP, native Work cycle, DAG, локальные Office/PDF/OCR
инструменты, E5/индекс/память, Drive bundles и skills/workflows. Присутствие файла,
в том числе большого apex-каталога, не доказывает включённую пользовательскую функцию.
Каждый исполнитель обязан найти entrypoint и сохранить текущую сильную реализацию.

7 ноября установлен Windows 0.23.0 и проверен один настоящий чат HY4. API на сервере
сохраняет более раннюю базу с ограниченными совместимыми изменениями. Это не полная
выкладка всего main и не завершённая приёмка Koswork. Ключи и адреса приватных
операторских файлов этому пакету не требуются. Маршрут HY4 не менять попутно.

Работа остаётся в Kosmora/Koswork, как установил владелец для второго этапа.
Не добавляем автономно новый дизайн, Studio-разделы, голос/Jarvis, облачный ПК и
Multi-Agent. Параллельная команда разработки — не реализация режима Multi-Agent
в самом продукте. Сайдбар/главный чат/логотип/глобальные стили сохраняются.

## Независимость блоков

- Root использует уже существующие файловые/браузерные операции для первой рабочей
  задачи, поэтому ему не нужно ждать всего нового Office-модуля.
- Office, браузер и Windows делаются на отдельных fixtures/дев-профилях.
- Память использует текущие scoped sources; Drive сначала работает с текущими
  canonical bundles; стиль — с существующими skills. Они не ждут друг друга.
- Интеграционные hooks и новые capabilities согласуются через
  [CONTRACTS.md](CONTRACTS.md), не через переписывание общего app.ts всеми сразу.

## Готовность и отчётность

| Статус              | Что он означает                                                        |
| ------------------- | ---------------------------------------------------------------------- |
| Готово к выдаче     | Есть инструкция, исполнение ещё не подтверждено                        |
| В работе            | Есть ветка и конкретный выполняемый срез                               |
| Работает локально   | Модуль запускается и создаёт настоящий результат на fixtures           |
| Готово к интеграции | Исходники/контракты/миграции/сценарий и проверенные команды переданы   |
| Интегрировано       | Общий пользовательский путь работает в совместимом комплекте           |
| Живая приёмка       | Проверен явно разрешённый сценарий с настоящим провайдером/устройством |

Не повышать статус по количеству токенов, файлов или отчётов. Шаблон сдачи —
[DELIVERY_TEMPLATE.md](DELIVERY_TEMPLATE.md). Неизбежные предложения внешнего вида —
[VISUAL_WAITLIST.md](VISUAL_WAITLIST.md). Новые идеи вне блока фиксировать отдельно,
а не расширять задачу бесконечно. Владелец сохраняет микроменеджмент продуктовых решений.
