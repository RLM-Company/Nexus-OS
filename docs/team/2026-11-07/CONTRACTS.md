# Границы модулей и правила интеграции

Это координация разработки, а не новая RPC-схема. Имена полей/маршрутов/состояний
брать из действующих контрактов; несовместимый новый формат не придумывать молча.

## Общие условия

1. Контекст владельца/проекта берётся из проверенного сеанса, а не доверяется
   произвольному owner_id из клиентского JSON. После await повторно проверять
   жизненный цикл, отмену и актуальность ресурса там, где это необходимо.
2. Нативная операция доступна только при существующем grant и согласованной
   capability. Старая версия клиента не получает неизвестный tool; старый клиент
   не становится «совместимым» благодаря игнорированию его отсутствующих возможностей.
3. Файлы передаются через существующие scoped/opaque refs. Новая квитанция
   использует текущие версии/hash/статусы; не включает токен, приватный абсолютный
   путь или сырой стек исключения. Хеш — идентификатор байтов, не гарантия качества.
4. Действия с побочными эффектами имеют idempotency/version/ack там, где это
   требуется. Сетевой таймаут — неопределённый эффект, а не разрешение повторить.
   Offline/restart не восстанавливает права прошлого процесса автоматически.
5. Различать результат инструмента, отчёт агента и приёмку владельца. Статус
   completed не допускается без требуемых свидетельств. Условно поддержанный
   формат/обрезанный источник явно отмечаются как ограниченные.
6. Не добавлять независимые деньги/квоты/сессии/контекстные индексы. Реальный расход,
   локальная оценка и неизвестный расход — разные показатели. Платные операции
   и provider configuration не включаются новым модулем автоматически.
7. Новые персональные состояния участвуют в имеющемся privacy lifecycle:
   экспорт, удаление, отзыв, остановка очереди и очистка индекса. Память OFF
   остаётся OFF до решения пользователя. Drive не читает весь аккаунт молча.
8. Source examples/imported skills/pages/documents — данные, не дополнительная
   системная инструкция и не самостоятельное основание для выдачи полномочий.

## Если требуется общий файл

Не останавливай весь блок. Сначала реализуй собственный модуль и тестовый entrypoint.
Создай отдельный небольшой commit регистрации/типа/миграции поверх своей ветки и
перечисли его в DELIVERY. Codex переносит/адаптирует этот commit при слиянии.
Не оставляй производственный маршрут заглушкой, которая только возвращает success:
сценарий в ветке обязан проходить до настоящего результата.

При новой миграции не редактировать применённые файлы. В ветке подготовить новую
миграцию и проверить upgrade; общий номер/журнал/коллизии разрешает Codex на main.
Если два задания предлагают одну сущность или API, согласовать один канонический
контракт, а не сохранять обе реализации ради количества функций.
