# Разработчик + GPT — полноценная работа с документами

Ветка: `developer/koswork-office-workspace`. Владелец реализации: Разработчик + GPT.

## Контекст и правила этого задания

Репозиторий: https://github.com/RLM-Company/Nexus-OS . Контрольная база плана:
`338536ee5946f96dcd18768143cc41af998c476a` (main после PR №463, 7 ноября 2026).
Начни отдельную ветку от актуального main, запиши фактический SHA. Если main уже
новее, сохрани его изменения. У локального Codex origin может быть зеркалом:
перед push проверь remote, не считай локальный push публикацией на GitHub.

Ты исполнитель реализации, а не автор рекомендаций. Нужен используемый модуль:
пользовательское действие → действующая логика → сохранённый результат/статус.
Сначала найди текущий путь вызова. Сохрани рабочие реализации и допиши недостающее;
не создавай второе хранилище, второй исполнитель или новую копию того же чата.
Первые выводы об исходном коде — максимум одна страница, затем реализация.
Если чтения репозитория нет, запроси актуальные файлы своего модуля по точным путям.
Не придумывай состояние исходников и не называй совместимым код, которого не видел.

Прочитай AGENTS.md, docs/product/STAGE_TWO_WORKFLOW_RU.md и apps/web/UI_RULES.md.
Это задание распределяет работу внутри Kosmora/Koswork. Multi-Agent, Jarvis и
облачный компьютер отложены. Сайдбар, основной экран чата, логотип, палитру,
типографику и глобальные стили не переделывай. Допустимы необходимые функциональные
контролы в существующем разделе; новый внешний вид вынеси в VISUAL_WAITLIST.md.
Существенное продуктовое решение уточняй у владельца, продолжая независимую работу;
обычные технические исправления выполняй сам.

Работай в своей ветке/checkout. Не используй реальные .env, пароли, токены, базу
и личные файлы владельца как тестовые данные или вложения другим сервисам.
Не меняй подключённого провайдера HY4, тарифы/квоты и модель прав доступа.
Не выкатывай изменения на production самостоятельно. Не устанавливай
программы и не управляй ПК владельца ради тестов без соответствующего поручения.
Используй отдельные fixtures; явно отличай их от реального модельного прогона.
Если нужен сторонний код, проверь лицензию, закрепи версию/commit, перенеси только
нужное и сохрани уведомления. Не запускай случайные install-скрипты как часть обзора.

## Твой полноценный блок

Ты владелец законченного раздела «Рабочие документы Koswork»: открыть разрешённый
DOCX/XLSX/PPTX, извлечь структуру, выполнить конкретные правки, увидеть изменения,
сохранить новую версию и проверить результат. Это полноценный продуктовый модуль,
а не разовый скрипт создания Word-файла или обёртка над ответом модели.

### Реализовать и довести

1. Сохранить существующие создание Office, чтение workspace_read_document,
   версии/хеши, безопасный ZIP/XML и readback. Найди, какие форматы/операции уже
   реально подключены. Не заменять их пересозданием всего файла из plain text.
2. Реализовать адресуемые операции редактирования. DOCX: абзац/таблица/ячейка и
   точечная замена с сохранением нетронутых элементов. XLSX: листы/ячейки/диапазоны,
   типы значений и формулы без выдачи невычисленного результата за рассчитанный.
   PPTX: текст на выбранном слайде и существующие текстовые placeholders с сохранением
   нетронутых слайдов/медиа. Для неподдержанного объекта честный отказ до записи.
3. Построить единый транзакционный путь: план правок → preview diff → expected_version
   и отдельное подтверждение записи → новая версия/копия → повторное чтение.
   Исходник по умолчанию сохраняется. Если версия изменилась, конфликт вместо
   перезаписи. Нельзя принимать «успешно» только на основании слов модели.
4. Сохранить числа, единицы, ведущие нули, отрицания и обязательные условия.
   Ссылки/формулы/макросы не выполняются произвольно, внешние ресурсы не загружаются.
   Архивы и XML ограничены по расширенному размеру/записям/CRC, symlink/ZIP-slip
   отклоняются. Не ослабляй file grants ради редактирования.
5. Дать существующему workspace/панели файлов реальную возможность посмотреть
   содержимое и предложенные изменения, скачать/сохранить результат. Внешний вид
   текущего чата/сайдбара не менять; свой функциональный viewer/editor компонент
   подключить минимально к имеющейся области файлов/артефактов.
6. Передать операции агенту как ограниченные инструменты существующего Work cycle:
   доступ только к выбранному workspace/opaque reference, отсутствие произвольных
   абсолютных путей. Новые tools выдаются только после capability negotiation;
   старый клиент не получает неподдержанную команду.
7. Вернуть результат с source version, новой версией, hash, выполненными/отклонёнными
   изменениями и ограничениями представления. Чтение текста не равно полной
   визуальной корректности: для готовых документов проверить открытие/рендер там,
   где есть отдельный разрешённый стенд.

### Где работать

desktop/windows/workspace/{office-document,office-text}.cjs и новые Office modules;
их тесты/fixtures. Новые document-workspace API/plugin и web-компоненты разместить
в отдельных файлах. workspace-service/path-guard, общие contracts, tool registry
и app.ts — минимальный интеграционный коммит для Codex. Windows main/installer
принадлежат OpenCode; browser/** — Gemini; не переписывать их в этой ветке.

### Сквозная приёмка

Один независимый бриф: обновить реквизиты и таблицу предложения в DOCX, добавить
лист/значения/формулы в XLSX, обновить текст выбранного слайда PPTX. Неправимые части
и исходники остаются целы; числа «19 700», артикул «00123», дата и «кроме доставки»
проверяются по реальным выходным байтам/чтению. Повтор с устаревшей версией получает
конфликт; отмена/отзыв папки не записывают файл. Приложи входы, выходы, diff и
результат открытия/рендера либо честно укажи, что он не проверялся.
Первый вертикальный срез обязан полностью открыть/изменить/сохранить один DOCX;
после него завершить XLSX и PPTX в пределах описанных безопасных операций.

## Как сдать полноценный результат

1. Реализованные исходники и подключение к существующему пользовательскому пути.
   Новый код, который нигде не вызывается, поставкой не считается.
2. Нужные миграции/регистрация маршрутов/контракты. Общие файлы меняй минимально,
   отдельным интеграционным коммитом; не форматируй и не переписывай их целиком.
   Коллизии номеров новых миграций согласует Codex при объединении.
3. Воспроизводимый сценарий с входными fixtures, настоящим результатом и командами.
   Внешний провайдер может быть заменён фикстурой, но твой модуль обязан реально
   читать/обрабатывать/сохранять данные. Отметь, где настоящая модель не вызывалась.
4. Проверки успеха, ошибки, отмены и отзыва доступа по риску изменения. Запусти
   относящиеся к модулю тесты, typecheck/build/lint, проверь diff и отсутствие секретов.
   Не выдавай непрогнанные проверки за прошедшие и не прячь ошибки повторным запуском.
5. Commit SHA + ветка + PR без самостоятельного merge/deploy. Добавь
   docs/handoff/TEAM_<ТВОЙ_БЛОК>_DELIVERY_RU.md: что было, что работает теперь,
   изменённые файлы, команды/результаты, ограничения, инструкции интеграции и отката.

Если среда не умеет push/запуск команд: отдай ZIP с настоящими файлами по путям
репозитория, BASE_SHA.txt, git diff/patch и DELIVERY.md. Не называй такой пакет
слитым, собранным или протестированным. Не ограничивайся псевдокодом, картинкой,
списком TODO или ответом «Processing completed successfully».

Не размножай задачи и другие чаты вместо реализации этого блока. Выполни первый
полезный сквозной сценарий, затем доведи оставшиеся пункты. В конце перечисли
реальные функции поставки, способ запуска и только фактически оставшиеся границы.
