## Независимые проверки

Все эксперименты выполнены только на локальном экземпляре/собственных
тестовых данных, без запросов к чужим системам и без настоящих учётных данных.

1. **Сессия из общедоступного ключа.** Конструктор безопасности снова выводит
   master key из публичной константы. Сформированный вне движка подписанный
   токен незарегистрированного пользователя принят как owner. На живом
   localhost HTTP POST /api/v1/kosmora/features/execute получен HTTP 200.
   Формальная проверка Bearer и tenant_id этого не исправляет.
2. **Нет файловой изоляции.** executeInSandbox прочитал собственный контрольный
   файл аудитора вне рабочего каталога и вернул его содержимое с exit_code=0.
   В исходнике OCI-режим только ищет docker/podman, затем выполняет обычный
   host spawnSync. Не запускать недоверенный код этим путём.
3. **История перезаписывается.** saveArtifactRevision повторно записал тот же
   revision_id/version с другим содержимым. В SQLite осталась одна строка с
   новым текстом, а не неизменяемая исходная ревизия. Используется INSERT OR REPLACE.
4. **F481 игнорирует задачу.** Подан ADD HALT при max_stack_limit=0. Адаптер
   сообщил staticVerificationPassed=true и returnValue=100. Другой вход
   PUSH 999 HALT дал тот же результат и идентичные метрики: kernel запускает
   встроенный пример 12+8, затем умножение на 5. Обработка полей — суффикс
   хеша; собственно переданная программа не проверяется.
5. **Контур приватности не даёт заявленной гарантии.** Результат механизма
   возвращает true_value=12345 вместе с noised_value; шум вычисляется
   детерминированно из заданного вызывающим seed. Это не доказательство
   приватности выдаваемых пользователю данных. Бюджет хранится в Map.

Пункты 1 и HTTP-проверка — два отдельных воспроизведения одного дефекта.
В сумме проверены шесть ожидаемых границ; ни одна из них не обеспечена.

## Статические и типовые проблемы

- Stage5EnterpriseKernel по actorId самостоятельно выпускает admin/MFA-сессию.
  rls_tenant_guard выставляет разрешение true вместо проверки строки.
- Stage16 выбирает один из четырёх встроенных примеров по номеру feature,
  а не исполняет задачу из domainFields. Аналогичная организация встречается
  в других новых kernel; проверять каждый операция→вход→эффект отдельно.
- core/index.ts из ZIP теряет действующие экспорты intelligence-graph и другие
  API рабочей ветки. Добавленные модули не являются заменой этих контрактов.
- Строгий tsc для standalone набора с настройками репозитория выявил, в числе
  прочего, отсутствующие HostNodeCapacity/ResourceTaskSpec/StateMachineSpec
  в core barrel, вызов API с одним аргументом вместо 5–6, отсутствующий импорт
  KosmoraDagPlan и exactOptionalPropertyTypes-ошибки.
- Всего standalone check дал 198 диагностик, включая отсутствующие зависимости
  React/legacy-модули, не входящие в ZIP. Это **не** число чистых ошибок полной
  сборки репозитория. Реальная Next/monorepo сборка не сертифицирована.
- В App Router page.tsx опять есть произвольные named exports. Проверить
  настоящим Next build, а не только Babel/transpileModule/node --check.
- Скрипт не проверяет типы, изменяет проверяемый barrel, ожидает TAP без явного
  reporter и при KOSMORA_SKIP_PUSH=1 по-прежнему может создавать коммит.

## Задание Gemini на исправление

Остановить расширение каталога. Сохранить F001–F512 и реальные алгоритмы,
но убрать неподтверждённые PASS/«готово» из матрицы. Для каждого ID различать:
работающий сценарий в продукте, отдельный алгоритм, прототип, отсутствующий
адаптер. Не увеличивать verifiedCount путём изменения критериев smoke-теста.

1. Сначала перенести и сохранить исправления из 1bdb6dc: явные непубличные
   ключи, строгая валидация session claims, проверенная внешняя identity,
   запрет самоназначения admin/MFA, честный unavailable без адаптера,
   запрет исполнения host-кода и неизменяемые DB-ревизии.
2. Для каждого feature обрабатывать его реальные входные данные. Например,
   F481 обязан передавать instruction_stream и лимиты в настоящий verifier;
   ADD на пустом стеке отклоняется, PUSH 999 возвращает 999, разные программы
   дают разные трассы. Удалить выбор демонстрации через featureId % N,
   фиксированные задачи, прибавление единицы, принудительное true и суффиксы
   вместо предметного результата. Неподдержанный формат отклонять явно.
3. Подключить функции к существующим Fastify identity/owner/project gates,
   долговременным хранилищам, бюджету, privacy coordinator и production
   executor. Самостоятельный node:http сервер оставить явно экспериментальным
   до этой интеграции. Map/локальный пример не выдавать за production persistence.
4. Для криптографии и privacy убрать ложные гарантии: закрытые ключи не выводить
   из публичных строк; приватные результаты не содержат исходного значения;
   randomness и privacy-accounting проектировать под реальную модель угроз.
   Хеш сертификата или подпись демонстрационного конверта сами по себе не
   доказывают SLSA/комплаенс/удаление из всех продуктовых хранилищ.
5. Исправить настоящие типы и интеграционную сборку на актуальной базе. Не
   удалять существующие public exports. Прогонять repo tsconfig tsc --noEmit,
   Next production build и затронутые старые тесты без изменения barrel,
   поддельных package.json или ослабления проверок ради зелёного результата.
6. Ввести отрицательные тесты для шести воспроизведений выше. Тесты должны
   проверять отсутствие побочного эффекта и чужих данных, CAS/историю,
   реальный вход и отказ при отсутствии адаптера; прежние 18 сценариев
   сохранить как дополнительный набор. Проверять выходной код тестов и
   cancelled/skipped, использовать явный --test-reporter=tap.
7. Выдать ZIP и patch с точным базовым SHA, SHA-256, списком изменённых файлов
   и сырыми итогами запусков. Режим verify-only не должен переключать рабочую
   ветку, менять index, делать commit или push. Публикация — отдельный шаг
   после проверки именно того дерева, которое будет отправлено.
