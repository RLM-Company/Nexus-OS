# PR390: безопасная переработка и интеграция

Исходный пакет сохранён в PR390, commit `201b3b6192d14387785d2e27e96b64d5fa0d1f70`.
Интеграция выполнена от актуальной базы Kosmora `8b9a81a`, без замены core barrel,
второго сервера авторизации, UI или worker-приложения из старой ветки Gemini.

## Что означает готовность

Каталог сохраняет все 512 предложений. Это не 512 реализованных продуктовых функций.
Публичный модуль `@cosmora/core/apex` экспортирует каталог и ограниченный вычислительный
интерфейс. Доступны 14 ID, представляющих 6 семейств алгоритмов:

- F193–F198: анализ явно заданного конечного автомата — достижимость, тупики,
  контрпримеры и обязательное достижение принимающего состояния во всех ветвях.
- F417: ограниченная по числу шагов симуляция PID с заданными пределами управления.
- F481–F482: проверка и исполнение арифметического стекового байткода с gas limit.
- F489–F490: Pareto-фронты и crowding distance для переданной популяции кандидатов.
- F497–F498: расстояние и edit script для последовательностей AST-токенов.
- F505: эвристика сходства с помощью сжатия, без заявления доказанных аксиом метрики.

Один алгоритмический результат может обслуживать несколько связанных ID. Число ID
не является числом независимых движков. Матрица `APEX_FEATURE_READINESS.md` формируется
из того же исполняемого реестра; неподключённые позиции возвращают 501
`APEX_ADAPTER_UNAVAILABLE`, а не запускают фиксированный пример. Остальные внутренние
исходники сохранены для последующей адаптации; они не экспортированы через новый
публичный entrypoint и не подключены к HTTP. Непроверенные криптографические,
распределённые и прочие исследовательские обещания не объявляются готовыми.

## Закрытые границы

- Нет master key из публичной строки. Старый standalone-модуль требует явный ключ,
  зарегистрированного principal и совпадения claims; даже owner ограничен выданными
  workspace scopes. Production API использует существующий IdentityStore Kosmora.
- Старые node:http routes, host-execution sandbox и UI из архива не импортированы.
  Арифметическая VM не выполняет JS/Wasm, subprocess, сеть или файловые операции.
- Сохранение ревизии требует project/tenant scope; повторная запись с другим содержимым
  запрещена. История сохраняется после повторного открытия SQLite. Чтение истории
  требует обоих scopes. Это отдельная библиотека, не замена действующего CanvasStore.
- Privacy-механизм не возвращает `true_value`, не принимает caller-controlled seed и
  требует явно подключённый accountant. Это не сертификация формальной DP гарантии.
  В production этот отдельный механизм не активирован без долговременного учёта.
- Удаление данных требует настоящего адаптера сервиса; очистка Map больше не выдаёт
  сертификат удаления всех пользовательских данных.
- Idempotency legacy-адаптеров разделена по tenant/workspace/project/actor, возвращаемые
  результаты копируются, размер кэша ограничен с отказом до исполнения нового запроса.
  Это локальный кэш алгоритмического адаптера, не распределённый exactly-once сервис.
- Неизвестные инструкции, лишние поля, нечисловые значения и слишком большие входы
  отвергаются. Нет выбора алгоритма через `featureId % N`.

## API и ограничения

`GET /api/v1/apex/features` возвращает каталог, реальные статусы и схемы доступных входов.
`POST /api/v1/projects/:projectId/apex/:featureId/execute` принимает `{ "input": ... }`.
Используются существующая сессия и проверка владения проектом. Вход не может задать
owner, tenant, actor, автономность, host path или команду. Вычисления не вызывают модель,
не публикуют данные и не изменяют основной проект.

Лимиты входов ограничивают размеры массивов, число состояний, инструкции, gas, матрицы
и строки. `formal_guarantee: false` означает, что вычисление на переданной модели
не доказывает безопасность всей системы. AST diff работает с переданными токенами,
не является GumTree или компилятором. PID — симуляция, не контроллер production-кластера.
Приёмник состояний интерпретирует все заявленные переходы как возможные; guards не
принимаются как будто они вычислены.

## Проверки и неизменность интерфейса

Проверяются реальные repo tsconfig, production-сборки зависимостей/API/Next, существующие
тесты ядра и критических API. Новые отрицательные сценарии воспроизводят нарушения из
аудита: поддельный токен, чужой project/workspace, перепись истории, SQL readfile,
неподдержанный адаптер, неверный bytecode, заданный seed и отсутствие erasure backend.
Дополнительные проверки ловят ложное «liveness» при допускающей бесконечный цикл ветке,
исчерпание gas, uninitialized LOAD, выход за пределы стека и неверные размерности Pareto.
Тестовый harness Gemini, меняющий barrel/manifests, не используется как доказательство.

Визуальные изменения отсутствуют. Предложения UI вынесены в
`docs/design/VISUAL_WAITLIST.md` и ожидают отдельного запроса владельца.
