# Cosmora: краткое руководство пользователя

Это руководство относится к текущей локальной alpha-версии Cosmora. В ней доступны обычные чаты, проекты, управляемая консоль Manager, локальный Model Runtime и контрольные интерфейсы. Автономный Manager и worker-агенты, которые сами выполняют task graph и внешние действия, пока не считаются реализованными.

## Запуск на Windows

Требования репозитория: Node.js 24+ и pnpm 11.19+.

```powershell
git clone https://github.com/RLM-Company/Nexus-OS.git
cd Nexus-OS
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm dev
```

После запуска откройте `http://127.0.0.1:3000`. Локальный API работает на `http://127.0.0.1:3100`.

Для контролируемой внутренней демонстрации Manager вместо `pnpm dev` можно использовать:

```powershell
pnpm demo
```

Проверить локальную демонстрацию можно во втором терминале:

```powershell
pnpm demo:preflight
```

## Установка как приложения / PWA

1. Запустите `pnpm demo`.
2. Откройте `http://127.0.0.1:3000` в поддерживаемом браузере.
3. Используйте кнопку **Install** в Cosmora или команду установки приложения в браузере.
4. После установки Cosmora открывается в отдельном окне, но по-прежнему использует локальный API и локальную SQLite-историю.

На телефоне обычный LAN-адрес по HTTP подходит для responsive preview, но не для полноценной установки PWA на главный экран: для такой установки нужен корректный HTTPS origin.

## Обычный чат

**Новый чат** создаёт обычный чат, а не проект. Сообщения обычного чата хранятся отдельно от проектов.

Если запрос похож на большую проектную задачу, Cosmora может предложить оформить её как проект. Само предложение ничего не создаёт. Проект появляется только после явного подтверждения пользователя через действие **Оформить как проект**.

## Создание проекта

1. Начните с обычного чата и опишите задачу.
2. Если Cosmora предлагает проектный режим, проверьте предложенное название и назначение.
3. Нажмите **Оформить как проект**, только если действительно хотите создать проект.
4. После подтверждения Cosmora открывает проектную рабочую область и сохраняет дальнейший контекст в проекте.

Перезагрузка страницы не должна превращать обычный чат в проект и не должна создавать новый проект сама по себе.

## Работа с Manager

Manager Console сейчас является управляемой рабочей областью проекта. Через неё можно вести проектный диалог, видеть состояние выполнения, переключаться между проектными представлениями и использовать уже подключённые контрольные механизмы.

Текущую консоль не следует воспринимать как полностью автономного сотрудника: автономный Manager/worker runtime и произвольное выполнение внешних инструментов ещё не входят в готовую alpha-функциональность. Если интерфейс показывает действие, требующее подтверждения или отдельного разрешения, не обходите этот контроль.

## Контекст проекта

В проекте доступна вкладка **Контекст**. Сейчас это безопасный browser-local preview, а не подключённая к Manager Runtime память.

- Перед подключением нового источника Cosmora показывает его preview.
- Подключение и отключение меняют только локальное UI-состояние текущего проекта.
- Состояние разных проектов хранится раздельно.
- Размер показывается как mock-оценка с лимитом 64 000 токенов.
- Ключи, bearer-токены и похожие секреты скрываются; повреждённое локальное состояние сбрасывается на безопасные mock-данные.
- **Очистить контекст** отключает локальные источники после явного подтверждения; чат, проект и документы не удаляются.

## Skills и GitHub

**Skills** сейчас работает как каталог разрешений и возможностей в режиме Preview only. Разрешены только read/preview-сценарии; произвольный код, установка пакетов, subprocess, OAuth и внешние write-действия отключены.

Без локальной настройки **GitHub** показывает безопасное состояние «не подключён». Для read-only
подключения создайте fine-grained personal access token только для нужных репозиториев. Дайте только
права чтения Metadata, Contents, Issues, Pull requests и Checks, затем добавьте его локально в `.env`:

```dotenv
GITHUB_TOKEN=your-local-fine-grained-token
```

Перезапустите API и откройте вкладку **GitHub**. Токен используется только серверным процессом и не
передаётся в браузер, UI, логи или ответы API. Интеграция отображает репозитории, ветки, commits,
issues, pull requests и CI. Создание ветки, комментарии, merge и deploy в продукте отключены.

## Image, Video и Sound

Эти рабочие области позволяют подготовить prompt и настройки локально. Пока соответствующая внешняя модель не подключена, prompt **не отправляется наружу и не считается сохранённым результатом генерации**. Интерфейс сообщает, что prompt только подготовлен локально.

## Что означают статусы

Разные поверхности могут использовать близкие технические названия, например `queued` вместо пользовательского `waiting`. По смыслу ориентируйтесь так:

- `waiting` — запрос принят и ожидает начала выполнения. В некоторых местах это состояние называется `queued`.
- `running` — выполнение уже началось, но текстовый поток ответа ещё может не идти.
- `streaming` — ответ поступает частями в реальном времени.
- `completed` — выполнение успешно завершено.
- `failed` — выполнение завершилось ошибкой; прочитайте сообщение интерфейса и при необходимости повторите запрос.
- `stopped` — выполнение остановлено пользователем, отменой или защитным механизмом и не должно продолжаться само.

## Безопасное добавление `MODEL_API_KEY`

Ключ должен находиться только в локальном `.env`. Не вставляйте реальный ключ в чат, issue, PR, документацию, скриншот или исходный код.

Создайте локальный файл из шаблона:

```powershell
Copy-Item .env.example .env
```

Затем откройте `.env` локально и заполните нужный профиль провайдера, в том числе:

```dotenv
MODEL_API_KEY=your-local-secret
```

Файл `.env` уже исключён через `.gitignore`. Перед любым коммитом всё равно полезно проверить:

```powershell
git status --short
```

В выводе не должно быть `.env`. Страница состояния модели показывает только безопасные метаданные подключения и не должна отображать значение ключа.

## Смартфон в доверенной локальной сети

Телефон и компьютер должны находиться в одной доверенной частной Wi-Fi/LAN-сети. Не используйте этот режим в публичной или недоверенной сети.

На компьютере запустите:

```powershell
pnpm demo:lan
```

Узнайте IPv4-адрес компьютера через `ipconfig` и на телефоне откройте:

```text
http://<IPv4-компьютера>:3000
```

В этом режиме наружу публикуется web-интерфейс, а API остаётся привязанным к loopback и доступен web через прокси. Если Windows Firewall спрашивает разрешение, разрешайте доступ только для доверенной частной сети. После проверки остановите локальные процессы.

## Частые проблемы

### API недоступен

Проверьте, что запущена команда `pnpm dev`, `pnpm demo` или `pnpm demo:lan` и что API слушает порт 3100. Для демонстрационного режима выполните:

```powershell
pnpm demo:preflight
```

Если ошибка временная и интерфейс предлагает **Повторить**, сначала используйте эту кнопку. Не публикуйте в issue или чат содержимое `.env` ради диагностики.

### Порт 3000 или 3100 занят

Посмотрите, какой процесс держит порт:

```powershell
Get-NetTCPConnection -LocalPort 3000,3100 | Select-Object LocalPort,State,OwningProcess
```

Затем проверьте конкретный PID:

```powershell
Get-Process -Id <PID>
```

Остановите только тот процесс, который вы действительно запускали для Cosmora или другого известного локального сервиса. Не завершайте все процессы Node без проверки.

### Модель не отвечает

Откройте страницу **Подключение модели** из статуса Cosmora. Если runtime остаётся в mock-режиме или credential не настроен, внешний провайдер не подключён. После локальной настройки `.env` можно выполнить безопасную проверку без платного запроса:

```powershell
pnpm manager:preflight
```

В репозитории также есть защищённый `pnpm manager:smoke`, но это уже не preflight: он отправляет ровно два платных model-запроса и требует отдельного явного разрешения через временную переменную текущего shell. Для обычной локальной alpha-проверки его не запускайте. Наличие `MODEL_API_KEY` само по себе не является разрешением на платный smoke-тест.

Если внешний провайдер недоступен и `MODEL_FALLBACK_TO_MOCK=false`, Cosmora должна показать ошибку, а не подменить ответ синтетическим.

### Активирован Emergency Stop

Emergency Stop является защитой, а не обычной ошибкой. Не пытайтесь обходить его перезапуском запроса. Откройте Control Center и проверьте область остановки: выбранный проект или весь процесс.

Для обычной пользовательской alpha-сессии восстановление выполняется только через предусмотренный контролируемый clearance-поток. Если process-wide stop был включён локальной переменной `RUNTIME_EMERGENCY_STOP=true`, интерфейс не должен самостоятельно его снимать: сначала полностью остановите приложение, исправьте локальную конфигурацию только если это осознанное действие владельца, затем запустите систему заново.

## Как полностью остановить локальное приложение

Если Cosmora была запущена одной командой `pnpm dev`, `pnpm demo` или `pnpm demo:lan`, вернитесь в этот терминал и нажмите `Ctrl+C`. Дождитесь возврата приглашения PowerShell.

Если web и API были запущены в разных терминалах, выполните `Ctrl+C` в каждом из них. После этого можно убедиться, что порты свободны:

```powershell
Get-NetTCPConnection -LocalPort 3000,3100 -ErrorAction SilentlyContinue
```

Пустой вывод означает, что локальные серверы на этих портах больше не слушают соединения.
